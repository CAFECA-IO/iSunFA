# 已知問題：路網資料只有台灣，境外陸運段全數為推估

**狀態**：設計上的部署範圍限制，非程式缺陷。報告已揭露材性（2026-08-01），**是否擴充路網覆蓋為產品決策**
**發現於**：2026-08-01，比對 `R01-AIR_台北市政府-曼徹斯特博物館` 與 `R02-AIR_東京大學-羅浮宮`
**影響範圍**：物流碳足跡計算的所有陸運段（LAND）

---

## 現象

同一份系統對不同地區的陸運段給出不同品質的距離：

| 路線 | 陸運段 | 距離來源 |
|---|---|---|
| R01 | 台北市政府 → 松山機場 | **實際路網** 7.12 km |
| R01 | Manchester Airport → 曼徹斯特博物館 | 直線 × 1.2 推估 15.95 km |
| R02 | 東京大學 → 羽田機場 | 直線 × 1.2 推估 21.91 km |
| R02 | Paris-Le Bourget → 羅浮宮 | 直線 × 1.2 推估 16.1 km |

只有台灣境內的段落取得真實路徑。

## 成因

`dockerfiles/osrm/Dockerfile` 只下載台灣的 OSM 萃取檔：

```dockerfile
RUN curl -L -o map.osm.pbf https://download.geofabrik.de/asia/taiwan-latest.osm.pbf
```

OSRM 對範圍外的座標無法規劃路徑，計算端因此落到 `直線距離 × 1.2` 的推估並標記 `isFallback`。

這是**刻意的部署範圍**而非故障——完整的全球路網萃取檔數十 GB，`osrm-extract` / `osrm-partition` / `osrm-customize` 的處理需要大量記憶體與時間，映像檔體積也不現實。

## 已處理：材性揭露

原本的揭露只有距離欄旁的小字 `est.` 與頁尾一句「該段無路網資料」。那句話是真的，但讀者無從判斷**這件事有多重要**——三段裡一段推估且占總排放 0.03%，與三段裡兩段推估且占 40%，是完全不同的兩份報告。

現在頁尾會揭露段數與排放占比：

> 本報告 3 段中有 2 段缺乏路網路徑資料，以直線距離 × 1.2 推估（見上表 est. 標記），合計占逐段排放 0.07%。

R02 的 0.07% 說明推估對這份報告的結論不構成實質影響——長程空運段主導了排放，市區接駁的絕對量極小。**這正是查核者需要的判斷依據。**

### 為何報告不宣稱覆蓋範圍

在程式碼裡另寫一份「覆蓋台灣」的宣告，就是第二個必須與 Dockerfile 手動同步的事實。本輪已修過兩個同類問題（列印端漏抄 `metersPerPixel`、CSS 字型家族名與系統家族名不符），不再增加第三個。報告只陳述資料本身能證實的事：幾段推估、占多少排放。

## 若要擴充覆蓋範圍

`est.` 對短程接駁段影響有限（占比通常 <1%），但若業務需要**境外陸運為主**的路線（例如歐洲境內卡車運輸），推估的誤差就會直接進入申報數值。屆時的選項：

1. **改用區域萃取檔**——按業務需要的地區各自建立 OSRM 實例（如 `europe/great-britain`、`asia/japan`），計算端依座標選擇端點。體積可控但需要路由層。
2. **改用外部路徑服務**——例如商用 API。省下維運成本，但引入外部依賴與逐次呼叫費用，且要確認其資料來源可否作為審計依據。
3. **維持現狀並依賴揭露**——目前的作法。推估佔比由報告揭露，使用者自行判斷是否可接受。

選項一與二都會改變「距離從哪來」這個審計證據鏈，需要一併更新報告的來源揭露。
