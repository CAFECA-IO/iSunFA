## 一、測試的可信度（假綠圖鑑）

送審前對每一條新測試問一次：**把被測行為改壞，這條會紅嗎？** 不確定就真的改壞跑一次。以下八種形狀都能讓答案是「不會」。

### 1.1 掃描型測試的掃描根 = 剛好被修的那個檔案

同一個形狀在 PR #6652 犯了三次：`route_params_contract` 只掃 `src/app/api`、`payment_fulfillment_visibility` 只覆蓋 webhook 不覆蓋 checkout、收據確認只掃 `token.service.ts`（而全 repo 另有 20 處未確認的收據等待）。

- **掃描型測試的價值等於它的掃描根。** 掃描根必須是整個 `src`（或整個 `src/app`），不是被修的那幾個檔案。
- 範圍真的無法一次收斂時，用**明列例外清單** + 一條「清單長度不得增加」的測試（見 `chain_receipt_status.test.ts`、`invite_endpoint_throttle.test.ts`）。清單只能變短。
- 例外清單裡的每一項都要寫明「為什麼這次不修」，而不只是列路徑。

### 1.2 把被測模組整包 `jest.mock`

`retention`、`gate`、`user_document` 三檔都是這個形狀：repo 與 service 兩側都 mock 掉之後，剩下的只證明「編排正確」，不證明「被編排的東西正確」。三檔守的都是隔離或條款承諾。

- mock 邊界應該落在**外部世界**（DB、SMTP、鏈、LLM），不是落在被測邏輯與它的協作者之間。
- 一旦決定 mock 掉某支協作者，就要另有一支測試直接測那支協作者。

### 1.3 測試自己的前提沒有生效

`key_vault_aad.test.ts` 設的是 `VAULT_MASTER_KEY`，而程式讀的是 `SECRET_VAULT_MASTER_KEY`。本機五條全綠——因為 `.env` 裡有真的那一個；CI 沒有 `.env`，五條全部以 `Server configuration missing` 失敗。

- 測試設定的環境變數名要與程式讀的**同一個常數來源**；靠字串各寫一次就會有這種事。
- **推送之前**跑一次 `npm run test:no-dotenv`（見 §7.1）。
- 同理：任何「本機剛好有」的東西（DB 裡剛好有資料、剛好有某個檔案）都不能是綠燈的原因。

> **這條犯了兩次，第二次是在修好第一次的同一輪。** `key_vault_aad.test.ts` 修好之後，`faith_memory_aad_backfill.e2e.test.ts` 又忘了自備主密鑰，而我是在**推送之後**才做無 `.env` 驗證的——CI 因此紅了 22 分鐘。兩次都不是「想不到」，是**本機測不出來**：本機有 `.env`，CI 沒有。所以它不該是一條要記得的規則，而該是推送前的一個指令。

### 1.4 fixture 不是真實資料的形狀

免費版人數上限被繞過將近一整輪，原因是所有單元測試都餵一個 `planId: FREE` 的訂閱列，而**真實的免費團隊根本沒有 `TeamSubscription` 列**（建團隊只寫 `Team` + `TeamMember`）。程式第一行的 `if (!subscription) return` 因此讓上限一次都沒執行過。

- 問一次：**這個 fixture 在生產資料裡真的長這樣嗎？** 特別是「查無資料」那一種狀態。
- 這一類漏洞不會被更多 mock 抓到。針對關鍵防線補一支**對真資料庫**的 e2e（見 `free_plan_invite_cap.e2e.test.ts`）：自己建資料、自己清乾淨、`$disconnect`。
- e2e 不得觸發真實外部副作用。上例刻意不呼叫 `inviteMemberByEmail`，因為 SMTP 是設定好的——擋門若失效就會真的寄信給真實信箱。

### 1.5 兩邊都是 `undefined` 的假通過

`expect(ledger.poolBalanceAfter).toBe(ACTIVE_WALLET.unallocatedBalance)` 通過了，而 fixture 根本沒有 `unallocatedBalance` 這個欄位——兩邊都是 `undefined`。

- 斷言的期望值要是**字面常數**，不要是「從 fixture 上再讀一次」。
- 對 fixture 缺欄位特別警覺：TypeScript 對 `as unknown` 之後的物件不會幫你。

### 1.6 門檻式斷言

`expect(calls.length).toBeGreaterThanOrEqual(6)` ——第七支鏈上操作不加確認也不會紅。

- 需要「數量不得減少」的語意時，改成精確值 + 一句「新增時請一併更新」的註解，讓下一個人被迫看見。

### 1.7 行為斷言測到「函式」，沒測到「接線」

限流的測試從文字比對改成行為斷言之後，commit 訊息寫的是「改成行為斷言」。**改的是那支函式，不是它有沒有被接上去。**

```
Mutation：在 route 裡刪掉 `if (limited) return limited;`（保留那行呼叫）
→ 限流完全失效，而全部測試仍然綠（實跑確認：25 passed）
```

因為「函式會不會擋」有了行為證據，「**有沒有真的擋在使用者走的那條路徑上**」仍然只有 `indexOf` 順序比對。

- 判準一句話：**這支測試有沒有匯入使用者實際打的那個 handler？** 沒有的話，它證明的是零件，不是裝配。
- 本 repo 先前沒有任何測試匯入 `@/app/api/...`，那正是這個缺口能存在的原因。第一支是 `invite_route_wiring.test.ts`——mock 邊界落在 service（會碰 DB 與寄信），閘與限流器都用真的。
- 斷言要**成對**：擋下來時「回應是 429」**且**「service 沒有被多呼叫一次」。只驗前者，改成「擋了但還是做了」也會通過；只驗後者，改成「一律擋」也會通過。

### 1.8 mock 沒有照實模擬被 mock 的東西

寫「刪除預算不該被失敗吃掉」的測試時，前兩版都綠得很假：

| 版本 | mock 的問題 | 結果 |
|---|---|---|
| 第一版 | `listExpired` 的 mock **不理會 `limit`**，一次回傳全部 | 整批一次處理完，而上界是在批與批之間才檢查——正確與錯誤的寫法結果一模一樣 |
| 第二版 | 同一個 mock **不會把刪掉的列移除** | 已刪的列一再被撈回來、又被刪一次，迴圈永遠不結束 |

兩次都不是斷言寫錯，是**被 mock 的那個世界不可能存在**。真的 `listExpired` 會照 `take` 切、刪掉的列不會再被查到；mock 少了這兩件事，測到的就是自己編的世界，而它「通過」與程式對不對無關。

- 每一個被 mock 的參數都要問：**真的那支會不會照它做事？** 不照做就等於那個參數在測試裡是死的——而你想測的往往正是它。
- **有狀態的東西要真的有狀態**：刪除要讓後續查詢查不到、寫入要讓後續讀取讀得到、排除清單要真的被排除。
- 判斷方法很簡單：把 mock 換成真的實作（或一支對真資料庫的 e2e），結論應該一樣。不一樣就代表 mock 在替程式回答問題。
- 相關的兩個形狀：§1.2（整包 mock 只證明編排）與 §1.4（fixture 不是真實資料的形狀）。這三條的共同點是**測試的前提比被測的程式更可疑**。

### 1.9 判準本身與「缺陷發生了」相容

PDF 的文字層修補（把 Chrome 寫成康熙部首的碼位改回漢字）附了一條實測憑證：**「修完抽回來，相容區部首 0 個」**。那句話是真的，而它證明不了任何事。

第一版的修補用 regex 掃全部 4 位十六進位碼位，**連 CMap 的來源側（glyph id）一起改**：`<2F42> <6587>` 變成 `<6587> <6587>`，那條對照從此整條失效。於是：

| 實際狀態 | 目標側還是部首嗎 | 抽回來的部首數 | 那條判準 |
|---|---|---|---|
| 真的修好了 | 不是 | 0 | ✓ |
| **改壞了**（來源側被改寫） | 也不是（entry 整條失效） | **也是 0** | **✓** |

兩種狀態被那個觀測量塌成同一個值。而「改壞了」比原本的缺陷更糟 —— 原本那個字至少搜得到一個錯字，改壞之後它抽不出來。

- 判準一句話：**這條驗收在缺陷發生時，會不會照樣通過？** 不是「它抓不抓得到我想到的那個缺陷」。
- 這與 §1.5、§1.7 不同：斷言有綁到真實行為、接線也覆蓋了，**壞的是「量什麼」** —— 選到的觀測量不足以區分成功與失敗。
- 修法是換一個**有能力區分**的觀測量：那次補的是直接讀 CMap 結構（來源側是否落在相容區、`lo <= hi` 是否成立），而不是繼續看抽出來的文字。**衍生值救不了衍生值**：兩條都從同一份被改壞的資料算出來。
- 同一個形狀在觀測領域也犯過（同一支 PR）：`activity extraction result` 把「模型沒回這個鍵」「回了空陣列」「這次沒帶 `withActivities`」「回超過上限整批 throw」四種上游狀態全部印成 `0`。**塌成同一個值**在 log 裡的後果是查不出成因，在驗收裡的後果是偵測不到缺陷。

### 1.10 驗證工具的替身，會很有說服力地指錯方向

同一支驗收腳本要查 CMap 的結構不變量，第一版**自己另寫了一份 parser**。它回報「25 個非法區間」，位置與碼位都印得清清楚楚 —— 而真正的答案是 **0**：那份替身的 regex 跨 entry 配對，把不相鄰的兩個碼位當成一組。

假警報比漏報難處理，因為它**看起來很可信**：它給的是具體數字與具體位置，而人的第一反應是去查產品。

- 判準一句話：**驗收與產品要讀同一支實作。** 另寫一份的代價不是多寫幾行，是把「兩支會不會分岔」變成一個新的失效點 —— 而分岔那天，驗收會很有說服力地指著錯的地方。
- 做法：把產品內部用的那支 parser／抽取器 `export` 出來給驗收用（該 PR 最後是 UAT 匯入產品的 `parseCMapEntries` 與 `extractPdfTextLayer`）。**驗收的價值來自它與產品同源，不是來自它獨立。**
- 「獨立實作以交叉驗證」在這裡不成立：交叉驗證的前提是兩邊都對得起自己的規格，而驗收腳本沒有自己的規格 —— 它的規格就是產品的行為。
- 代價寫成一句話（作者自己的話，值得照抄）：**會亂叫的驗收沒有人會再看它。** 所以驗收腳本自己的 bug 要當成一級缺陷處理：先假設是自己錯，再假設是產品錯。

## 二、決定論與不變式

### 2.1 「查無資料」不等於「跳過檢查」

`if (!subscription) return` 是本 PR 代價最高的一行。**空值有語意**：查無訂閱列＝免費版，不是「不適用任何規則」。

- 每一個 `if (!x) return` 都要問：**這個提早返回是在表達什麼業務語意？** 那個語意寫在註解裡了嗎？
- 判斷「什麼是免費版／什麼是有效方案」這類問題**只能有一個判斷點**（此處是 `resolveEffectivePlanId(null)` 回 `FREE`）。同一個問題出現第二個答案處，兩者遲早分岔。
- 型別窄化需要非空時，寫一道 fail-fast 並註明「為什麼到不了這裡」，不要用 `!`。

### 2.2 上界不變式：估算必須覆蓋實際

預扣（hold）是成本上界，`settleSpend` 只退不補。因此**任何注入 prompt 的內容都必須計入 hold**，而估算與注入必須是同一份字串。

本 PR 踩到兩次：長期記憶注入沒計入；短期記憶只算內容長度，沒算渲染後的標頭與每輪前綴。

- 有「上界／下界」語意的數值，檢查它與被界定的對象是否**同源**（同一個函式產出）。
- 兩邊各算一次就是「估的是 A、送的是 B」，而巧合能掩蓋很久（`FAITH_PROMPT_OVERHEAD_TOKENS` 剛好吸收得掉）。

### 2.3 帳本恆等式：新分錄型別要先問它站在哪一側

守恆式是 `Σ(PURCHASE + ADJUST + CONSUME + REFUND) = 池餘額 + Σ 分配餘額`，`ALLOCATE` / `REVOKE` 被排除是因為它們只在池與分配之間搬動（淨額為零）。

沖銷分配時若沿用 `REVOKE`，右側少一筆而左側不動 → 下一輪勾稽判為違反守恆並**凍結錢包**。

- 新增或改用任何分錄型別時，回去看守恆式的定義，確認它該不該進左側。
- 財務／碳排的守恆式（`A = L + E`、`期初 + 採購 = 消耗 + 期末`）同理：改動任何一項都要問恆等式還成不成立。

### 2.4 冪等鍵

- 語意不同的操作**不共用鍵**（收回 `revoke-all:` vs 沖銷 `write-off:`）。
- 鍵要含**週期**（單期上限的檢查若跨期共用鍵，第二期會被當成重放）。
- 重放分支的回傳值要與首次執行一致——本 PR 有一條測試是**繞著 bug 寫的**：mock 了負數金額去抵銷程式的 `Number(-existing.amount)`。看到測試裡有「為了讓它通過而刻意扭曲的資料」就是警訊。

## 三、資料與併發

### 3.1 Prisma 的 `undefined` 條件會被靜默忽略

`where: { ownerPublicKey: undefined }` 等於**沒有條件**，會列出全站資料。這是跨租戶外洩的標準形狀。

- 進 `where` 的每一個變數，若型別上可能是 `undefined`／空字串，就在進 Prisma 前擋掉並回空集合。
- 型別擋得住不代表安全：`as` 與未來的簽章變動都會繞過它。

### 3.2 先查後改 = 雙倍

「查 status → 判斷 → 無條件 update」兩個請求可以同時通過判斷。一封轉寄出去的邀請被兩人同時點開，就是一個付費席次進兩個人。

- 狀態轉移用 `updateMany` 帶上**來源狀態條件**做原子 claim，回 `count === 0` 即「沒搶到」。
- 呼叫端必須把「沒搶到」與「成功」分開處理，不能回一個「已完成」的假象。

### 3.3 唯一鍵與正規化

`victim@gmail.com` / `victim+1@gmail.com` / `v.ictim@gmail.com` 是同一個收件匣，卻產生不同的唯一鍵與不同的冪等鍵——每一封都真的刷一次 OWNER 的卡。

- 「同一個對象」的判定要有**單一 canonical 函式**，且**只用於鍵，不用於投遞**（把使用者的地址改寫再寄出，是替他決定他的地址）。
- 正規化規則只套用在**確定成立的網域**（點號規則只有 Google 系列）。過度正規化會把兩個人判成同一個，受害者是無辜的第三方。

### 3.4 硬刪 vs 改狀態要一致

撤回邀請用硬刪、拒絕邀請用改狀態——同一件事的兩個方向，稽核強度不同，於是「曾經邀請過誰、由誰撤回」查不到。

- 同一條路徑上的相似動作，稽核強度要對齊。
- 保留與實刪的分界寫成一句話：**「沒有對外發生過的紀錄」可以實刪**（信寄不出去的回滾），已經動過錢或對外送出的一律留痕。

### 3.5 稽核欄位要有讀者

`acceptedEmailMatch` 寫得很認真，而全 repo 沒有任何 query、API、UI 或告警讀它。**稽核欄位沒有讀者，稽核價值就是零。**

- 新增稽核欄位時一併回答：誰會看到它？在哪個畫面／哪個告警？
- 只給有處置權的人看（本例限 OWNER / ADMIN），而且不要給「恆為 false 的欄位」——那會被前端讀成「已驗證通過」。

## 四、秘密與端點

### 4.1 秘密不進 URL

放在 path 或 query 的 token 會進**三個控制不到的地方**：access log（保留數週、常被集中收容，讀 log 的人遠多於能讀 DB 的人）、瀏覽器歷史、以及 `Referer`。

- 一次性連結把 token 放在 **fragment**（`#` 之後不送伺服器），前端讀出後立刻 `replaceState` 抹掉，再以 POST body 送回。
- 為此犧牲「read 用 GET」的語意是可以的，但要在註解寫明原因，否則下一個人會順手改回 GET。

### 4.2 未登入端點

- 限流維度只剩 IP，而 `x-forwarded-for` 是**用戶端可偽造的**：取第一個值（部署形態決定），且只作限流維度，**不作授權判斷**。
- 取不到 IP 時回固定字串，不要回隨機值或 `undefined`——每次不同的維度等於沒有限流。
- **狀態變更**的未登入端點（例如 `decline` 讓邀請作廢、席次釋出）一定要節流並記錄呼叫者。
- 錯誤回應不得構成 oracle：失效／逾期／已使用一律回同一個 404。

### 4.3 權限閘

- 端點的權限閘（誰能操作）與**授予範圍**（能授予什麼角色）是兩件事。本 PR 漏的是後者：ADMIN 可以邀請新帳號直接成為 OWNER，接受後就能反過來把原 OWNER 降級。
- 角色組合（`OWNER || ADMIN`）不要以字面字串散落各處，收斂成一個函式；每一處手寫都是一次拼錯機會，而拼錯的方向通常是放寬。

## 五、外部世界

### 5.1 鏈上：送得出去 ≠ 做成了

`waitForTransactionReceipt` 對 revert 的交易一樣正常回傳收據，只有逾時才拋。因此**每一處都要檢查 `receipt.status`**，並收斂到單一確認函式。

- 更根本的一條：**ABI 宣告的函式不代表部署的合約有**。本 PR 的 `ABIS.CREDIT_POINT` 宣告了 `burn(address, uint256)`，而合約只有 `burnAndUnlock(uint256)`（燒 `msg.sender` 自己的餘額）——那個「收回」從來沒有成功過，而 `receipt.status` 沒被檢查，reverted 交易被回報成成功。
- 涉及鏈上能力的功能，去讀 `contracts/*.sol`，不要只讀 ABI。
- 外部呼叫失敗時的補償路徑，要確認它**真的會被觸發**（把成功誤判成功，補償永遠不會執行）。

### 5.2 系統設定：DB + 簽章

營運設定存 DB（ADR 017），env 只放部署環境差異。

- 直接用 SQL 改 `system_setting` 會讓 manifest digest 失配，快照轉 `UNTRUSTED`，而該狀態下 `get()` 對**每一個**設定丟錯——OAuth、LLM、SMTP 一起停掉。
- 缺鍵時的生效值來自 `SYSTEM_SETTING_FALLBACKS`（程式碼常數），不是 env。「DB 沒有那一列」常常已經是想要的值。
- `.env.example` 裡的每一個鍵都被視為**必填**。新增選填 env（例如限流閾值）不要寫進去，否則既有部署重啟就掉進「尚未初始化」狀態。

### 5.3 沒有 migrations 目錄

schema 以 `prisma db push` 套用，欄位新增與資料回填是分開的兩件事，順序錯了不會噴錯，只會安靜停擺。

- 改 schema 的 PR 一律在**部署檢查表**寫下：新增了哪些欄位、需要哪支回填、以及做錯順序的症狀。
- Prisma 表達不了的約束（partial unique index）用 nullable 唯一欄位替代，寫在 schema 裡才帶得走。

### 5.4 「做不到」要查對因果：能力不存在，還是用錯機制

結論對、**理由錯**的診斷，比錯誤的結論更難清除：它會被抄進註解、ADR、部署檢查表、測試說明、法務 ToDo，然後導出一個錯誤的補救方向，而每一份都看起來有憑有據。

本 PR 的實例（第六輪之後才發現）：扣費第二層要扣成員的個人鏈上點數，實作用的是**平台側 `burn(address, uint256)`**，部署的合約沒有那個函式。我讀了 `.sol`、確認函式不存在，於是下結論「合約層面做不到，要恢復須改合約並重新部署」——那句話進了六個檔案與四份文件。

錯在只問了「這個做法能不能成立」，沒問「**這件事在這個 repo 裡已經有沒有另一種做法**」。同一套程式裡，顧問分析、上傳、未綁帳簿的會話**早就在扣個人點數**，走的是持有人簽章：建待付訂單 → 402 → 成員的智慧錢包 `transfer` 給金庫（託管帳戶由伺服器代簽）→ 重送同一則即放行。合約完全不必動。缺的不是鏈上能力，是這一層沒接上那條路。

而錯誤的補救方向恰好是最糟的一個：加一個平台可單方面呼叫的銷毀函式，等於讓平台能在無授權下銷毀使用者資產——與條款明文承諾的「扣除需經您簽章確認」相反。

- 判定「平台做不到 X」之前，先 grep「**產品裡有沒有已經在做 X 的地方**」。有的話，缺口是接線而不是能力。
- 「平台單方面做不到」與「這件事做不到」是兩件事。中間差的是**誰簽章**，而那通常正是條款要求的那個人。
- 把診斷抄進多份文件之前先停一次：抄十份的成本是十份都要更正，而只有第一份會被仔細讀。
- 缺陷的**起點**也要記下來。這次是一份宣告了合約沒有的函式的 ABI（見 §5.1），它讓錯的做法看起來成立。只修結果、不修起點，下一個人會再走一次。

## 六、文件與程式碼的一致性

系統宣稱的東西必須真的存在。本 PR 的三個實例：

- 規範與 ADR 都寫「密文與列綁定」，而 `createCipheriv` 之後**沒有 `setAAD`**——密文只綁 purpose，複製到別人的列上照樣解得開。
- 條款寫「90 天後刪除」，而讓那句話成立的兩支函式在同一輪被測試覆蓋刪掉。
- 條款寫「可收回分配點數」，而實際做不到（點數在成員錢包裡，移出需持有人簽章，而收回的對象不會去簽）。**當事實與條文衝突時，改條文**（改成「分配後不可收回」），不要寫一句同樣不實的替代說法（例如「經客服協助」——客服也做不到）。
- 反過來也要查：**條文寫得對、實作沒接上**，不要急著改條文。同一批條款裡「額度不足時得以個人點數支付，該項扣除需經您以帳戶憑證簽章確認」是**對的**，而且產品裡已經在運作；壞的只有其中一條路徑（見 §5.4）。當時我準備建議法務加註免責——那會為了掩蓋一個實作缺口而弱化一句正確的承諾。

檢查方式：

- 改動涉及條款／隱私政策／設計書承諾時，反向確認「這句話的執行者是哪一支程式？它有測試嗎？」
- 文件裡的 API 路徑、URL 格式、欄位名，隨程式一起改。
- 文件引用程式碼的常數值時（例如「預設 N」），加一條會紅的檢查，而且**掃整個 `documents`**：只讀一份文件的話，同一個不一致會原封不動留在另一份裡（本 repo 犯過，見 §1.1 的同一個道理）。

### 6.1 跨 PR：共用檔案要對照 base 做三方比對

`develop` 前進之後，雙方各自新增的東西可能**在單邊 review 裡完全看不出來**。本 PR 的實例：兩邊都新增了錯誤碼 `NF000017`，一邊是「團隊不存在」、另一邊是「這個人不是這個帳本的員工」（後者刻意不回 403 以免洩漏「這個信箱在系統裡有員工檔」）。`API_ERRORS` 以**鍵**索引，兩個鍵並存不會有型別錯誤——只有 code 字串撞號，而對外契約正是那個字串。

- 共用的「命名空間型」資源要列出來三方比對：錯誤碼、enum 值、rate limit bucket、schema model／enum 名、i18n key、環境變數名。
- 比法是 `base` / `develop` / `branch` 各取一份，算「雙方各自新增」的交集——不是讀 diff。
- 順手補一支**同檔唯一性**的測試（`error_dictionary_codes.test.ts`）。它看不到別的分支，擋不住「合併前」的撞號，但擋得住合併之後的狀態與同檔重複——而本 PR 加上它的當下，就抓出**另外三組分支自己的重複**，其中一組的兩條測試各自斷言同一個碼、**同時通過正是因為撞號**。

## 七、送審前的自我檢查

### 7.1 推送前一定要跑的三個指令（順序有意義）

```bash
npx tsc --noEmit        # 測試檔的型別沒有其他守門人（CI 也是先跑這個）
npm run test            # lint + 全套 + 時區敏感的那一組
npm run test:no-dotenv  # 同一套測試，但在「沒有 .env」的條件下跑
```

第三個指令是這輪加的（`scripts/jest_without_dotenv.mjs`）。它把 `.env` 暫時移開、只以環境變數傳 `DATABASE_URL`——**與 CI 容器完全同一個形狀**——跑完再用 `finally` 還原。用 script 而不是手寫一行，是因為手寫的版本在測試失敗或按 Ctrl-C 時會把 `.env` 留在移開的狀態，而那會讓接下來每一次執行都是壞的、原因又很難猜。

它抓的是 §1.3 那種缺陷：**測試自己忘了準備前提，而本機剛好有那個值**。驗證過它真的抓得到——把 e2e 裡設主密鑰的那一行拿掉，一般跑法 2 passed、`test:no-dotenv` 2 failed。

「推送前」三個字是重點：這一輪我是推上去之後才做這件事，於是 CI 先紅了才被修好。順序錯了，這個檢查就只是事後解釋。

### 7.2 逐項確認

1. 每一條新測試都改壞過被測行為，確認會紅。**這是唯一不能跳的一步。**
2. 掃描型測試的掃描根是整個 `src`，或有一份只能變短的例外清單。
3. `npm run test:no-dotenv` 綠（見 §7.1），而且是在**推送之前**跑的。
4. 對關鍵防線問一次：真實資料在這條路徑上長什麼樣？必要時補真 DB e2e，並清乾淨測試資料。
5. 每個 `if (!x) return` 都寫得出它的業務語意。
6. 改到金流／額度時，恆等式與冪等鍵各檢查一次。
7. 改到 schema 時，部署檢查表寫了欄位、回填與順序錯誤的症狀。
8. 秘密沒有出現在 URL、log、錯誤訊息裡。
9. 條款／設計書的敘述與實作一致；不一致時改的是**錯的那一邊**，不是好寫的那一邊。
10. PR 的形狀本身是訊號：**若每一輪都在「修好三條、帶進三條新的」，那是 PR 太大**——新引入的缺陷都在新功能裡，因為每次擴張都在未被 review 過的表面上再加一層。該拆。
11. 每一條驗收判準問一次：**缺陷發生時它會不會照樣通過？**（§1.9）驗收工具與產品讀的是不是同一支實作？（§1.10）

### 7.3 引用 review 意見之前，先確認那份意見是不是最新的

GitHub 的 comment 可以被編輯，而 UI 上只有一個很小的「edited」標記。這一輪的實例：我拿著自己先前抓下來的副本回覆「這份意見沒有被改過」，而它其實被改過（`created_at` 05:57:35、`updated_at` 06:06:21，9,590 → 6,223 字元），**而且那次編輯刪掉了一整條 finding**（反向代理的 XFF 深度）。我當下的「檢查」是把現在的內容跟自己的副本比——那份副本是編輯**之後**才抓的，所以必然相同。

- 引用或宣稱某條意見的內容之前，比 `created_at` 與 `updated_at`（`gh api` 就有；要看改了什麼用 `userContentEdits`）。
- 兩者不同就重讀全文並**逐條對照自己的待辦清單**：被刪掉的那條不會有任何提示。
- 「我比對過所以沒變」要能說出比對的兩份各自是什麼時候取得的。副本比副本不是驗證。
