# Code Review 檢查清單

- 版本：v1.0（2026-08-18，Luphia）
- 來源：PR #6652（席次計費／email 邀請／費思記憶）三輪 review 的實際失效樣本
- 適用：所有送審的 MR，以及自我 review

> 這份清單裡的每一條都**真的發生過**，而且多數在當下是全綠的。因此它的順序不是按嚴重度，而是按「多容易在 review 時看漏」。
>
> 一句話總結那三輪的教訓：**綠燈不是證據，是尚未被反駁。**

## 一、測試的可信度（假綠圖鑑）

送審前對每一條新測試問一次：**把被測行為改壞，這條會紅嗎？** 不確定就真的改壞跑一次。以下六種形狀都能讓答案是「不會」。

### 1.1 掃描型測試的掃描根 = 剛好被修的那個檔案

同一個形狀在 PR #6652 犯了三次：`route_params_contract` 只掃 `src/app/api`、`payment_fulfillment_visibility` 只覆蓋 webhook 不覆蓋 checkout、收據確認只掃 `token.service.ts`（而全 repo 另有 20 處未確認的收據等待）。

- **掃描型測試的價值等於它的掃描根。** 掃描根必須是整個 `src`（或整個 `src/app`），不是被修的那幾個檔案。
- 範圍真的無法一次收斂時，用**明列例外清單** + 一條「清單長度不得增加」的測試（見 `chain_receipt_status.test.ts`、`invite_endpoint_throttle.test.ts`）。清單只能變短。
- 例外清單裡的每一項都要寫明「為什麼這次不修」，而不只是列路徑。

### 1.2 把被測模組整包 `jest.mock`

`retention`、`gate`、`user_document` 三檔都是這個形狀：repo 與 service 兩側都 mock 掉之後，剩下的只證明「編排正確」，不證明「被編排的東西正確」。三檔守的都是隔離或條款承諾。

- mock 邊界應該落在**外部世界**（DB、SMTP、鏈、LLM），不是落在被測邏輯與它的協作者之間。
- 一旦決定 mock 掉某支協作者，就要另有一支測試直接測那支協作者。

### 1.3 測試自己的前提沒有生效

`key_vault_aad.test.ts` 設的是 `VAULT_MASTER_KEY`，而程式讀的是 `SECRET_VAULT_MASTER_KEY`。本機五條全綠——因為 `.env` 裡有真的那一個；CI 沒有 `.env`，五條全部以 `Server configuration missing` 失敗。

- 測試設定的環境變數名要與程式讀的**同一個常數來源**；靠字串各寫一次就會有這種事。
- 會讀 env 的測試，送審前**把 `.env` 暫時移開跑一次**。
- 同理：任何「本機剛好有」的東西（DB 裡剛好有資料、剛好有某個檔案）都不能是綠燈的原因。

### 1.4 fixture 不是真實資料的形狀

免費版人數上限被繞過將近一整輪，原因是所有單元測試都餵一個 `planId: FREE` 的訂閱列，而**真實的免費團隊根本沒有 `TeamSubscription` 列**（建團隊只寫 `Team` + `TeamMember`）。程式第一行的 `if (!subscription) return` 因此讓上限一次都沒執行過。

- 問一次：**這個 fixture 在生產資料裡真的長這樣嗎？** 特別是「查無資料」那一種狀態。
- 這一類漏洞不會被更多 mock 抓到。針對關鍵防線補一支**對真資料庫**的 e2e（見 `free_plan_invite_cap.e2e.test.ts`）：自己建資料、自己清乾淨、`$disconnect`。
- e2e 不得觸發真實外部副作用。上例刻意不呼叫 `inviteMemberByEmail`，因為 SMTP 是設定好的——擋門若失效就會真的寄信給真實信箱。

### 1.5 兩邊都是 `undefined` 的假通過

`expect(ledger.poolBalanceAfter).toBe(ACTIVE_WALLET.unallocatedBalance)` 通過了，而 fixture 根本沒有 `unallocatedBalance` 這個欄位——兩邊都是 `undefined`。

- 斷言的期望值要是**字面常數**，不要是「從 fixture 上再讀一次」。
- 對 fixture 缺欄位特別警覺：TypeScript 對 `as unknown` 之後的物件不會幫你。

### 1.6 門檻式斷言

`expect(calls.length).toBeGreaterThanOrEqual(6)` ——第七支鏈上操作不加確認也不會紅。

- 需要「數量不得減少」的語意時，改成精確值 + 一句「新增時請一併更新」的註解，讓下一個人被迫看見。

## 二、決定論與不變式

### 2.1 「查無資料」不等於「跳過檢查」

`if (!subscription) return` 是本 PR 代價最高的一行。**空值有語意**：查無訂閱列＝免費版，不是「不適用任何規則」。

- 每一個 `if (!x) return` 都要問：**這個提早返回是在表達什麼業務語意？** 那個語意寫在註解裡了嗎？
- 判斷「什麼是免費版／什麼是有效方案」這類問題**只能有一個判斷點**（此處是 `resolveEffectivePlanId(null)` 回 `FREE`）。同一個問題出現第二個答案處，兩者遲早分岔。
- 型別窄化需要非空時，寫一道 fail-fast 並註明「為什麼到不了這裡」，不要用 `!`。

### 2.2 上界不變式：估算必須覆蓋實際

預扣（hold）是成本上界，`settleSpend` 只退不補。因此**任何注入 prompt 的內容都必須計入 hold**，而估算與注入必須是同一份字串。

本 PR 踩到兩次：長期記憶注入沒計入；短期記憶只算內容長度，沒算渲染後的標頭與每輪前綴。

- 有「上界／下界」語意的數值，檢查它與被界定的對象是否**同源**（同一個函式產出）。
- 兩邊各算一次就是「估的是 A、送的是 B」，而巧合能掩蓋很久（`FAITH_PROMPT_OVERHEAD_TOKENS` 剛好吸收得掉）。

### 2.3 帳本恆等式：新分錄型別要先問它站在哪一側

守恆式是 `Σ(PURCHASE + ADJUST + CONSUME + REFUND) = 池餘額 + Σ 分配餘額`，`ALLOCATE` / `REVOKE` 被排除是因為它們只在池與分配之間搬動（淨額為零）。

沖銷分配時若沿用 `REVOKE`，右側少一筆而左側不動 → 下一輪勾稽判為違反守恆並**凍結錢包**。

- 新增或改用任何分錄型別時，回去看守恆式的定義，確認它該不該進左側。
- 財務／碳排的守恆式（`A = L + E`、`期初 + 採購 = 消耗 + 期末`）同理：改動任何一項都要問恆等式還成不成立。

### 2.4 冪等鍵

- 語意不同的操作**不共用鍵**（收回 `revoke-all:` vs 沖銷 `write-off:`）。
- 鍵要含**週期**（單期上限的檢查若跨期共用鍵，第二期會被當成重放）。
- 重放分支的回傳值要與首次執行一致——本 PR 有一條測試是**繞著 bug 寫的**：mock 了負數金額去抵銷程式的 `Number(-existing.amount)`。看到測試裡有「為了讓它通過而刻意扭曲的資料」就是警訊。

## 三、資料與併發

### 3.1 Prisma 的 `undefined` 條件會被靜默忽略

`where: { ownerPublicKey: undefined }` 等於**沒有條件**，會列出全站資料。這是跨租戶外洩的標準形狀。

- 進 `where` 的每一個變數，若型別上可能是 `undefined`／空字串，就在進 Prisma 前擋掉並回空集合。
- 型別擋得住不代表安全：`as` 與未來的簽章變動都會繞過它。

### 3.2 先查後改 = 雙倍

「查 status → 判斷 → 無條件 update」兩個請求可以同時通過判斷。一封轉寄出去的邀請被兩人同時點開，就是一個付費席次進兩個人。

- 狀態轉移用 `updateMany` 帶上**來源狀態條件**做原子 claim，回 `count === 0` 即「沒搶到」。
- 呼叫端必須把「沒搶到」與「成功」分開處理，不能回一個「已完成」的假象。

### 3.3 唯一鍵與正規化

`victim@gmail.com` / `victim+1@gmail.com` / `v.ictim@gmail.com` 是同一個收件匣，卻產生不同的唯一鍵與不同的冪等鍵——每一封都真的刷一次 OWNER 的卡。

- 「同一個對象」的判定要有**單一 canonical 函式**，且**只用於鍵，不用於投遞**（把使用者的地址改寫再寄出，是替他決定他的地址）。
- 正規化規則只套用在**確定成立的網域**（點號規則只有 Google 系列）。過度正規化會把兩個人判成同一個，受害者是無辜的第三方。

### 3.4 硬刪 vs 改狀態要一致

撤回邀請用硬刪、拒絕邀請用改狀態——同一件事的兩個方向，稽核強度不同，於是「曾經邀請過誰、由誰撤回」查不到。

- 同一條路徑上的相似動作，稽核強度要對齊。
- 保留與實刪的分界寫成一句話：**「沒有對外發生過的紀錄」可以實刪**（信寄不出去的回滾），已經動過錢或對外送出的一律留痕。

### 3.5 稽核欄位要有讀者

`acceptedEmailMatch` 寫得很認真，而全 repo 沒有任何 query、API、UI 或告警讀它。**稽核欄位沒有讀者，稽核價值就是零。**

- 新增稽核欄位時一併回答：誰會看到它？在哪個畫面／哪個告警？
- 只給有處置權的人看（本例限 OWNER / ADMIN），而且不要給「恆為 false 的欄位」——那會被前端讀成「已驗證通過」。

## 四、秘密與端點

### 4.1 秘密不進 URL

放在 path 或 query 的 token 會進**三個控制不到的地方**：access log（保留數週、常被集中收容，讀 log 的人遠多於能讀 DB 的人）、瀏覽器歷史、以及 `Referer`。

- 一次性連結把 token 放在 **fragment**（`#` 之後不送伺服器），前端讀出後立刻 `replaceState` 抹掉，再以 POST body 送回。
- 為此犧牲「read 用 GET」的語意是可以的，但要在註解寫明原因，否則下一個人會順手改回 GET。

### 4.2 未登入端點

- 限流維度只剩 IP，而 `x-forwarded-for` 是**用戶端可偽造的**：取第一個值（部署形態決定），且只作限流維度，**不作授權判斷**。
- 取不到 IP 時回固定字串，不要回隨機值或 `undefined`——每次不同的維度等於沒有限流。
- **狀態變更**的未登入端點（例如 `decline` 讓邀請作廢、席次釋出）一定要節流並記錄呼叫者。
- 錯誤回應不得構成 oracle：失效／逾期／已使用一律回同一個 404。

### 4.3 權限閘

- 端點的權限閘（誰能操作）與**授予範圍**（能授予什麼角色）是兩件事。本 PR 漏的是後者：ADMIN 可以邀請新帳號直接成為 OWNER，接受後就能反過來把原 OWNER 降級。
- 角色組合（`OWNER || ADMIN`）不要以字面字串散落各處，收斂成一個函式；每一處手寫都是一次拼錯機會，而拼錯的方向通常是放寬。

## 五、外部世界

### 5.1 鏈上：送得出去 ≠ 做成了

`waitForTransactionReceipt` 對 revert 的交易一樣正常回傳收據，只有逾時才拋。因此**每一處都要檢查 `receipt.status`**，並收斂到單一確認函式。

- 更根本的一條：**ABI 宣告的函式不代表部署的合約有**。本 PR 的 `ABIS.CREDIT_POINT` 宣告了 `burn(address, uint256)`，而合約只有 `burnAndUnlock(uint256)`（燒 `msg.sender` 自己的餘額）——那個「收回」從來沒有成功過，而 `receipt.status` 沒被檢查，reverted 交易被回報成成功。
- 涉及鏈上能力的功能，去讀 `contracts/*.sol`，不要只讀 ABI。
- 外部呼叫失敗時的補償路徑，要確認它**真的會被觸發**（把成功誤判成功，補償永遠不會執行）。

### 5.2 系統設定：DB + 簽章

營運設定存 DB（ADR 017），env 只放部署環境差異。

- 直接用 SQL 改 `system_setting` 會讓 manifest digest 失配，快照轉 `UNTRUSTED`，而該狀態下 `get()` 對**每一個**設定丟錯——OAuth、LLM、SMTP 一起停掉。
- 缺鍵時的生效值來自 `SYSTEM_SETTING_FALLBACKS`（程式碼常數），不是 env。「DB 沒有那一列」常常已經是想要的值。
- `.env.example` 裡的每一個鍵都被視為**必填**。新增選填 env（例如限流閾值）不要寫進去，否則既有部署重啟就掉進「尚未初始化」狀態。

### 5.3 沒有 migrations 目錄

schema 以 `prisma db push` 套用，欄位新增與資料回填是分開的兩件事，順序錯了不會噴錯，只會安靜停擺。

- 改 schema 的 PR 一律在**部署檢查表**寫下：新增了哪些欄位、需要哪支回填、以及做錯順序的症狀。
- Prisma 表達不了的約束（partial unique index）用 nullable 唯一欄位替代，寫在 schema 裡才帶得走。

## 六、文件與程式碼的一致性

系統宣稱的東西必須真的存在。本 PR 的三個實例：

- 規範與 ADR 都寫「密文與列綁定」，而 `createCipheriv` 之後**沒有 `setAAD`**——密文只綁 purpose，複製到別人的列上照樣解得開。
- 條款寫「90 天後刪除」，而讓那句話成立的兩支函式在同一輪被測試覆蓋刪掉。
- 條款寫「可收回分配點數」，而合約層面做不到。**當事實與條文衝突時，改條文**（改成「分配後不可收回」），不要寫一句同樣不實的替代說法（例如「經客服協助」——客服也做不到）。

檢查方式：

- 改動涉及條款／隱私政策／設計書承諾時，反向確認「這句話的執行者是哪一支程式？它有測試嗎？」
- 文件裡的 API 路徑、URL 格式、欄位名，隨程式一起改。

## 七、送審前的自我檢查

1. 每一條新測試都改壞過被測行為，確認會紅。**這是唯一不能跳的一步。**
2. 掃描型測試的掃描根是整個 `src`，或有一份只能變短的例外清單。
3. `.env` 移開跑一次（會讀 env 的測試）。
4. 對關鍵防線問一次：真實資料在這條路徑上長什麼樣？必要時補真 DB e2e，並清乾淨測試資料。
5. 每個 `if (!x) return` 都寫得出它的業務語意。
6. 改到金流／額度時，恆等式與冪等鍵各檢查一次。
7. 改到 schema 時，部署檢查表寫了欄位、回填與順序錯誤的症狀。
8. 秘密沒有出現在 URL、log、錯誤訊息裡。
9. 條款／設計書的敘述與實作一致；不一致時改的是**錯的那一邊**，不是好寫的那一邊。
10. PR 的形狀本身是訊號：**若每一輪都在「修好三條、帶進三條新的」，那是 PR 太大**——新引入的缺陷都在新功能裡，因為每次擴張都在未被 review 過的表面上再加一層。該拆。
