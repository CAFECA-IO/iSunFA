## 🛰️ 3. 座標校準作業（最重要的前置）

### 3.1 為什麼不能用地圖標註值

不是精度問題，是**系統性偏移**：

- 地圖標的是建物中心或門牌位置，演示時人站在某層樓的某個房間
- 室內定位主要靠 Wi-Fi 輔助，**同一台裝置在同一位置會穩定偏向某個方向**，不是隨機誤差
- 兩者疊加：標註點偏 200 公尺 + 室內偏移 150 公尺 = 500 公尺圍欄只剩 150 公尺餘裕

### 3.2 校準程序

**必須用演示當天要用的那台裝置、那個瀏覽器、站在演示要站的位置。**

不同裝置的定位來源不同（有無 GPS 晶片、Wi-Fi 資料庫差異），**別台裝置量的值不能用**。手機地圖 App 顯示的座標也不能用 —— 那經過廠商修正，與瀏覽器 `navigator.geolocation` 拿到的不是同一個值。

| 步 | 動作 |
|---|---|
| 1 | 在演示位置開啟校準頁（§3.4），**等待 30 秒讓定位穩定**（剛開頁的第一筆通常最不準） |
| 2 | 連續取樣 **5 次**，每次間隔 10 秒 |
| 3 | **取中位數**，不是平均 —— GPS 偶爾噴一個離群值，平均會被拉走，中位數不會 |
| 4 | 記下 5 筆的 `accuracy`，**最差的那個值 × 2** 就是圍欄半徑的下限參考 |
| 5 | **走到會場／工區的各個角落各量一次**，取最遠一點到中位數中心的距離 |
| 6 | 半徑 = 步驟 5 的距離 + 步驟 4 的下限 + 100 公尺餘裕，**四捨五入到 50 的倍數** |
| 7 | 寫入 `DEMO_SITE_A_LAT` / `DEMO_SITE_A_LNG`，半徑寫入 seed |
| 8 | 執行圍欄不重疊驗證（展示資料 §4.2），特別檢查與板橋本部的距離 |

> **步驟 6 算出來如果超過 500 公尺，就用算出來的值，不要硬套 500。**
> 500 是計畫書給的起始值，不是必須遵守的數字。**唯一不能發生的事是主角站在現場打不了卡。**

### 3.3 校準當天要順便確認的三件事

1. **會場有沒有 Wi-Fi、要不要密碼** —— 沒有 Wi-Fi 只靠 4G，室內定位精度會明顯變差
2. **HTTPS 是否正常** —— `navigator.geolocation` 在非 HTTPS 環境（localhost 除外）根本不會啟動，症狀是「一直定位中」
3. **會場能不能連到 `accounts.google.com` 與 `www.googleapis.com`** —— 後者是 JWKS 驗簽用的，擋掉會讓登入在最後一步失敗

### 3.4 建議做一個校準頁（約半小時的工）

`/hr_management/attendance/_calibrate`，demo 專用：

```
┌─────────────────────────────────┐
│  座標校準                        │
│                                 │
│  目前：25.012845, 121.465102     │
│  精度：±18 公尺                  │
│                                 │
│  已取樣 3 / 5                    │
│  中位數：25.012838, 121.465094   │
│  最差精度：±31 公尺               │
│                                 │
│  [ 取樣 ]  [ 重設 ]              │
│                                 │
│  DEMO_SITE_A_LAT=25.012838      │
│  DEMO_SITE_A_LNG=121.465094     │
│  ← 複製這兩行貼進 .env           │
└─────────────────────────────────┘
```

直接吐出可貼上的 env 兩行，就不會有人抄錯小數位。

## ⚙️ 4. 環境設定與「壞掉時長什麼樣」

**每一項後面那欄比設定本身重要** —— 症狀能反推回原因，才有可能在 30 秒內判斷是哪裡出問題。

### 4.1 必要設定

| 設定 | 來源 | 沒設定的症狀 |
|---|---|---|
| `GOOGLE_OAUTH_CLIENT_ID` / `_CLIENT_SECRET` | 系統設定（ADR 017）或 env | **登入頁上根本沒有 Google 按鈕**（`social_login_buttons.tsx` 會自動隱藏未就緒的 provider） |
| Google Console 的 redirect URI | Google Cloud Console | 授權後跳轉失敗，Google 端顯示 `redirect_uri_mismatch` |
| `HR_PII_KEY_V1` | env | **seed 直接中止**；若跳過 seed，打卡回 500（`encryptPii` 拋 `HrPiiKeyError`） |
| `HR_PII_BLIND_INDEX_PEPPER` | env | 同上（建立員工時） |
| `NEXT_PUBLIC_APP_URL`（HTTPS） | env | 打卡頁**一直停在「定位中」**，且沒有任何錯誤訊息 |
| `DEMO_SITE_A_LAT` / `_LNG` | env | seed 中止（刻意設計，見展示資料 §10.1） |
| `DEMO_ALLOW_MANUAL_COORDINATE=true` | env | 示範模式的座標輸入框不出現，**P2 演不了** |

### 4.2 三個最難診斷的症狀

| 症狀 | 為什麼難 | 判別方式 |
|---|---|---|
| **打卡回 500** | 錯誤訊息不會說是金鑰問題 | 看 server log 有沒有 `HrPiiKeyError`。**這一項無法在台上修** |
| **一直「定位中」** | 沒有錯誤、沒有逾時提示 | 先看網址列是不是 `https://`；再看瀏覽器有沒有出現權限詢問 |
| **登入到一半失敗** | 看起來像帳號問題，其實是網路 | 會場擋 `www.googleapis.com`（JWKS）時，前面的授權都會成功，只有最後驗簽失敗 |

### 4.3 Google Cloud Console 設定要點

- 用戶端類型：**Web application**
- Authorized redirect URIs 必須**完全相符**（含 `https://`、含結尾有無斜線）：`${NEXT_PUBLIC_APP_URL}/auth/callback/google`
- 若 demo 環境網址與正式不同，**兩個都要加進去**
- OAuth 同意畫面若停在「測試中」，**上台的兩個帳號必須加進測試使用者清單**，否則會被擋

### 4.4 網路

- 需要對外連線：`accounts.google.com`（授權）、`oauth2.googleapis.com`（換 token）、`www.googleapis.com`（JWKS 驗簽）
- 地圖底圖若走外部 tile 服務，也需要對外連線 —— **T−1 彩排時要確認地圖真的畫得出來**
- **備援：手機熱點。** 這是最便宜也最有效的一招，但要事先確認熱點的網路也能連上 demo 站台

### 8.1 把最常見的「故障」變成賣點

觀眾很容易當場拿出手機想試。他們會登入成功，然後看到「你的 Google 帳號尚未對應到員工檔」。

**不要道歉，把它講成設計：**

> 「對，這正是實名制的意思 —— 不在名冊上的人打不了這個工地的卡。工地上有誰，是事先建檔決定的，不是誰下載了 App 就能報到。」

這一句話同時回答了工程機關最關心的「承包商能不能亂報人頭」，而它是免費的。

### 8.2 台上的三條紀律

1. **不要在演示中重跑 seed** —— 會清掉現場剛打的那兩筆卡，而那兩筆是整場最有說服力的資料
2. **不要現場改圍欄半徑** —— 改大了 P2 就演不了（走到哪都算在工地內），而且要重新解釋一次
3. **不要用沒彩排過的裝置** —— 定位偏移是裝置相關的，換一台等於校準作廢
