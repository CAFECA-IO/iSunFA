# 薪資異動紀錄（調薪歷程）實作計劃

> Info: (20260908 - Julian) 需求：「系統可呈現薪資異動紀錄」。
>
> 釐清後的定義：**某一位員工的薪資條件隨時間如何變化** —— 什麼時候調薪、
> 從多少調到多少、誰改的、從哪一個月開始生效。
> 對象包含**外部**：會計師、勞檢、稽核。
>
> 這一點決定了整份計劃。若只是給老闆自己看，從既有的薪資紀錄推導就夠了；
> 要拿給外部看，就必須有一份「當時就記下來」的軌跡，而不是事後回推的重建。
> §2 解釋為什麼。

---

## 1. 現況：這件事今天完全沒有留痕

`SalaryCalculatorEmployee` 是**就地覆寫**的。使用者在員工列表把本薪從 40,000
改成 45,000，`UPDATE` 一下去，40,000 就不存在於任何地方了。

模組裡確實有幾份「看起來像歷史」的東西，但沒有一份回答得了這個問題：

| 既有的東西                     | 它記的是什麼                          | 為什麼回答不了「什麼時候調薪」                                       |
| ------------------------------ | ------------------------------------- | -------------------------------------------------------------------- |
| `SalaryRecord.inputSnapshot`   | 某年某月**跑薪資時**的 21 個輸入欄位  | 只覆蓋有存過紀錄的月份；且它記的是「發薪時的值」，不是「調整這件事」 |
| `SalaryRecord.createdByUserId` | 誰按下儲存                            | 是誰跑了薪資，不是誰核准了調薪                                       |
| `SalaryPaySlipDelivery`        | 薪資單寄給誰、成功或失敗              | 寄送事件，與薪資條件無關                                             |
| `AuditLog`                     | 日記帳／傳票／ESG／人事個資的存取軌跡 | **薪資模組在這張表裡是零筆** —— 已知缺口                             |

`AuditLog` 值得多說一句。它的形狀是 `dataType` / `dataId` / `action` /
`userId` / `createdAt` —— 只記「誰對哪一筆做了什麼動作」，**不記前後值**。
那個形狀對「這張傳票被誰改過」夠用，對「本薪從多少變成多少」不夠用。
所以本需求不是往 `AuditLog` 加一個 `SALARY_EMPLOYEE` 型別就能解決的；
兩者是不同的東西，§9 說明它們的關係。

## 2. 資料從哪裡來：為什麼不能只用回推

從既有的 `SalaryRecord.inputSnapshot` 回推調薪歷程，技術上完全可行：
同一位員工相鄰兩筆紀錄的快照逐欄比對，就能列出「3 月本薪 40,000、
4 月 45,000」。**不需要任何新資料表。** 那很吸引人，而且第一版的誘惑很大。

不採用它作為唯一來源，有五個理由，前三個就足以否決：

1. **只覆蓋有存過紀錄的月份。** 1 月到職、5 月才第一次跑薪資的人，
   前四個月是空白。而空白在稽核情境下會被讀成「沒有變動」。
2. **記錄的是發薪時的值，不是調整這件事。** 4/1 生效的調薪在 2/20 就決定了，
   回推只看得到「4 月的紀錄跟 3 月不同」—— 決定的時間與決定的人都不在。
3. **薪資紀錄可以重存。** 同年同月是唯一鍵，重存會覆蓋 `inputSnapshot` ——
   連回推出來的歷史本身都是可變的。對勞檢而言這一條就出局了。
4. **沒跑薪資的修改完全無痕。** 改完員工檔卻沒存紀錄，回推看不到。
5. **回推的結果會隨未來的修改而改變。** 同一個問題今天問和明天問可能不同答案，
   而稽核要的正好是「不會變」。

**結論：新增一張只增不改的異動表，在寫入員工檔的同一個交易裡追加。**

**但回推仍然有它的位置。** 新表從上線那天開始才有資料，而既有員工的過去
是真的存在過的。§8 把回推保留為**讀取時計算、畫面上明確標示為「回推」**
的第二個區塊 —— 不寫進表裡，這樣表裡每一列都是當時記下來的。

## 3. 資料模型

### 3.1 為什麼是「一次修改一列 + 前後完整快照」，而不是「一欄一列」

兩種形狀都常見：

**(a) 一欄一列**（`field` / `oldValue` / `newValue`）
畫面好做（一列就是一句「本薪 40,000 → 45,000」）、好篩選。
但一次改三個欄位變成三列、要靠 grouping 才讀得懂；而且值的型別會全部塌成
字串（本薪是 `BigInt`、投保是 `Boolean`、扶養人數是 `Int`、到職日是 `DateTime`），
之後要拿來運算或重建就得逐欄反解析。

**(b) 一次修改一列 + 前後完整快照（Json）**
diff 在讀取時算。多存了一些位元組，換來兩件事：
「2026-04-01 當天這個人的員工檔長什麼樣」可以直接回答（勞檢真正會問的問題），
而且**新增員工欄位時不必回填任何歷史列**。

**採用 (b)。** 決定性的理由是第二點與本 repo 的既有前例：

- 本專案**沒有 `prisma/migrations/`**，schema 走 `prisma db push`。
  欄位攤平的歷史表，每次 `ISalaryEmployeeProfile` 長出新欄位就要手寫回填。
- `SalaryRecord.inputSnapshot` 為了完全相同的理由選了 Json，
  而它的註解已經把這個取捨寫下來了：那兩個型別是計算引擎的契約、會隨法規年度演進。
  歷史表面對的是同一份型別，沒有理由選相反的形狀。
- diff 是純函式 → 在 `testEnvironment: "node"` 下測得到，符合本專案的測試模型。

### 3.2 為什麼前後都存，不只存「後」

只存 `after` 也能重建歷史（前一列的 after 就是這一列的 before），省一半空間。
不這麼做是刻意的：

- **一列可以獨立讀懂。** 匯出給會計師的 CSV，一列自己就說得完一件事，
  不需要讀者自己去接鏈。
- **斷鏈變得看得出來。** 若第 N 列的 `before` 不等於第 N−1 列的 `after`，
  就代表中間有一次修改沒被記到 —— 有這個冗餘，漏記是**可偵測**的；
  只存 after 的話，漏記是隱形的。稽核用途下這個冗餘值得。

### 3.3 Schema 草案

```prisma
/**
 * Info: (20260908 - Julian) 員工薪資條件的異動軌跡。**只增不改。**
 *
 * 一次寫入員工檔 = 一列。CREATE 的列沒有 before，soft delete 的列沒有 after。
 *
 * 前後快照的形狀是 `ISalaryCalculatorEmployeeSnapshot`（= `ISalaryEmployeeProfile`
 * ＋ name / number / email），用 Json 的理由與 `SalaryRecord.inputSnapshot` 相同：
 * 那是一份會隨法規年度演進的契約，而本專案沒有 migrations。
 *
 * ## recordedAt 與 effectiveFrom 不是同一件事
 *
 * 見計劃書 §4。混用這兩者是這類功能最常見的錯法。
 */
model SalaryEmployeeProfileChange {
  id String @id @default(uuid())

  // Info: (20260908 - Julian) 租戶鍵，一律是每個 where 的第一個 key
  accountBookId String      @map("account_book_id")
  accountBook   AccountBook @relation(fields: [accountBookId], references: [id])

  employeeId String                   @map("employee_id")
  employee   SalaryCalculatorEmployee @relation(fields: [employeeId], references: [id])

  // Info: (20260908 - Julian) CREATE / UPDATE / DELETE（soft delete）
  action SalaryProfileChangeAction @map("action")

  /**
   * Info: (20260908 - Julian) 修改前／後的完整員工檔快照。
   * CREATE 時 before 為 null，DELETE 時 after 為 null；UPDATE 兩者都有。
   */
  beforeSnapshot Json? @map("before_snapshot")
  afterSnapshot  Json? @map("after_snapshot")

  /**
   * Info: (20260908 - Julian) 這次修改動到哪些欄位。**衍生資料，Json 才是真相。**
   *
   * 存它是為了「只看本薪的變動，翻三年」不必全表掃描後在應用層過濾。
   * 代價是它可能與快照不一致（differ 有 bug 時篩選會騙人），
   * 因此 `salary_profile_change_diff.test.ts` 會拿 fixture 斷言
   * `changedFields === diffProfile(before, after)`。
   * 需要重算時以 Json 為準。
   */
  changedFields String[] @map("changed_fields")

  /**
   * Info: (20260908 - Julian) 從哪一個給付期間開始生效（年、月）。
   * 使用者可指定；預設為當期。與 recordedAt 的區別見 §4。
   */
  effectiveYear  Int @map("effective_year")
  effectiveMonth Int @map("effective_month")

  // Info: (20260908 - Julian) 使用者填的原因（調薪、升遷、投保級距調整…），可空
  reason String? @db.Text

  // Info: (20260908 - Julian) 誰改的。伺服器從 DeWT 取，不收前端傳入
  changedByUserId String @map("changed_by_user_id")
  changedBy       User   @relation(fields: [changedByUserId], references: [id])

  // Info: (20260908 - Julian) 何時寫下這一列（伺服器時鐘）。不可編輯
  recordedAt DateTime @default(now()) @map("recorded_at")

  @@index([accountBookId])
  // Info: (20260908 - Julian) 主要查詢：某位員工的歷程，新的在前
  @@index([accountBookId, employeeId, recordedAt])
  @@map("salary_employee_profile_change")
}

enum SalaryProfileChangeAction {
  CREATE
  UPDATE
  DELETE
}
```

**沒有 `updatedAt`，也沒有 `deletedAt` —— 這是刻意的。** 這張表不該有任何
「被改過」或「被刪掉」的概念；schema 上就不給那兩個欄位，
是讓「只增不改」這件事在型別層面就成立，而不是靠紀律。

**待確認（機器上線後）**：

- `SalaryCalculatorEmployee` 是否有 `createdAt`／`updatedAt`（影響 §8 的回填能否誠實標日期）。
- schema 裡是否已有 `String[]` 的用例（Postgres array 在本 repo 的先例）；
  若沒有，`changedFields` 改存 `Json`（字串陣列）以免多引入一種型別慣例。

## 4. `recordedAt` 與 `effectiveFrom`：這一節是整份計劃的重點

薪資實務上有三個不同的時間：

| 時間                 | 例子                        | 存在哪                             |
| -------------------- | --------------------------- | ---------------------------------- |
| **決定／輸入的時刻** | 3/28 有人在系統上把本薪改掉 | `recordedAt`                       |
| **生效的期間**       | 這次調薪從 **4 月**起算     | `effectiveYear` / `effectiveMonth` |
| **發薪的時刻**       | 4/5 跑 4 月薪資             | 既有的 `SalaryRecord`              |

把前兩者混為一談，會在兩個真實情境下給出錯的答案：

- **補登**：4/20 才輸入一筆「4 月起生效」的調薪。只有 `recordedAt` 的話，
  問「這個人 4 月的本薪是多少」會答錯 —— 因為 4/1 那天表上還是舊值。
- **預先輸入**：3/28 輸入「5 月起生效」。只有 `recordedAt` 的話，
  4 月的薪資會被算成新值。

所以兩個都要存，而且**兩者都不能推導出另一個**。

### 4.1 但目前的 UI 沒有「生效月份」這個欄位

員工編輯彈窗今天就是填完存檔，沒有期間的概念。三個選項：

**(a) 第一版用當期當預設，不加 UI 欄位。**
最省，但補登與預先輸入都會記錯，而且**錯得看不出來** —— 表上每一列都長得很正常。
對外部稽核用途，這等於交出一份看起來可信但有系統性偏差的資料。**不建議。**

**(b) 編輯彈窗加一個「生效月份」，預設當期。**
UX 成本是所有使用者都多看到一個欄位（可摺疊在「進階」下）。
換到的是這張表真的能回答勞檢的問題。**建議這一個。**

**(c) 只在「薪資本體欄位有變動」時才問。**
最貼近直覺（改個 email 不必問生效月份），但條件式欄位的實作與測試成本
比 (b) 高，而且「哪些欄位算薪資本體」這個判斷會同時出現在前端與後端兩處。
可作為 (b) 的後續優化。

**採 (b)，並在同一支 PR 完成**（20260908 拍板）—— 若拆開，(a) 期間寫進去的列
永遠是不可信的，而事後無從修正（那需要人去回憶每一次調薪的生效月）。

## 5. 寫入路徑

### 5.1 追加必須發生在 repository，而且在同一個交易裡

```
route → service → repository
                    └─ $transaction([ findUnique(before), update, create(change) ])
```

三個要求，每一個都對應一個真實的失敗模式：

1. **在 repository，不在 service。** 員工檔的寫入有三個入口
   （員工列表新增／編輯、計算機的「直接新增員工」、soft delete）。
   放在 service 就是三個地方各記一次，而漏掉其中一個**不會有任何症狀** ——
   直到有人發現某條路徑改的薪資沒留痕。放在 repository 是唯一的收口。
2. **在同一個交易裡。** 分兩次寫，中間失敗就會出現「檔改了、沒有紀錄」
   或「有紀錄、檔沒改」。前者是靜默的資料遺失，後者是假的歷史。
3. **`before` 必須是資料庫當下的那一列，不能用前端送來的值。**
   前端有它自己那份（載入時抓的）舊值，用它省一次 query —— 但那份可能已經過期
   （別人剛改過），也可能被偽造。**歷史的 `before` 只能來自 `findUnique`。**

### 5.2 三種動作

| 入口                             | action   | before     | after            |
| -------------------------------- | -------- | ---------- | ---------------- |
| 新增員工（含計算機「直接新增」） | `CREATE` | `null`     | 建出來的完整快照 |
| 編輯員工                         | `UPDATE` | 資料庫當下 | 寫入後           |
| 移除員工（soft delete）          | `DELETE` | 資料庫當下 | `null`           |

**「沒有實際變動的儲存」不寫列。** 使用者打開彈窗、什麼都沒改就按儲存，
`diffProfile` 回空陣列 → 不追加。否則歷史會被無意義的列淹沒，
而淹沒的後果是真正的調薪找不到。這一條要有測試。

### 5.3 soft delete 之後歷史必須還在

`SalaryCalculatorEmployee` 是 soft delete（`activeNumber` 設 null，列還在），
所以外鍵不會斷 —— 這是既有設計的順帶好處。但要釘住：
**歷史列不隨員工消失**，且移除後仍查得到（否則「這個人被刪掉了，
他的調薪歷程也一起消失」= 稽核軌跡可以用刪除來規避）。

## 6. 讀取端

### 6.1 端點

```
GET /api/v1/user/account_book/:account_book_id/salary_calculator/employee/:employee_id/history
```

掛在員工底下而不是另開一層：查詢的對象就是那一位員工，
而它與員工列表共用同一組租戶與授權判斷（形狀照 `salaryRecordDeliverApi` 的先例）。

查詢參數：`page` / `limit`（沿用 `parsePositiveInt`）、`fields`（只看某些欄位的變動）、
`from` / `to`（生效期間範圍）。

**分頁是必要的，不是可選的。** 一位員工三年下來的列數不多，但匯出情境
（§7）會一次要全部 —— 那一支走 export，不是把 `limit` 開到無限大。

### 6.2 回應形狀

```ts
export interface ISalaryProfileChange {
  id: string;
  action: "CREATE" | "UPDATE" | "DELETE";
  effectiveYear: number;
  effectiveMonth: number;
  recordedAt: number; // Unix 秒，沿用本模組的慣例
  reason: string | null;
  changedBy: { id: string; name: string | null };
  /**
   * Info: 逐欄的前後值。伺服器算好，前端不自己 diff ——
   * 「哪些欄位算變動」的判斷只能有一份（§9.2）。
   */
  changes: {
    field: keyof ISalaryEmployeeProfileSnapshot;
    before: string | number | boolean | null;
    after: string | number | boolean | null;
  }[];
}
```

`changes` 由伺服器從兩份快照算出來，而不是把 Json 原封不動丟給前端。
理由：diff 的規則（哪些欄位比、金額怎麼正規化、`BigInt` 怎麼轉）
只能有一份實作，而它必須在有測試的那一側。

### 6.3 權限 —— 這裡有一個新問題

沿用 `SalaryAccess.READ`（OWNER + EDITOR）是最省的做法，但**外部觀眾這個
需求暴露了一個既有的缺口**：

> 今天要讓會計師看得到薪資，唯一的辦法是把他設成 `EDITOR` ——
> 而 `EDITOR` 改得動薪資、也改得動這本帳的傳票。

20260908 我建議過**不要**把 `READ` 拆成兩級，理由是「唯讀成員本來就不在
這個模組的使用者清單上」（計畫書 §10.8）。**那個理由被這次的需求推翻了。**
外部稽核正好是「要看、不准改」的那一類人，而現在沒有那個角色。

三個選項，建議 (a)：

- **(a) 新增 `SalaryAccess.AUDIT`（唯讀，含歷程與匯出），開給一個新的
  帳本層級角色或既有的 `VIEWER`。** 乾淨，但要決定「`VIEWER` 是否從此看得到薪資」——
  那與 20260908 的決策相反，需要產品重新拍板。
- **(b) 不動權限，第一版只給 OWNER + EDITOR，外部觀眾靠匯出的 CSV／PDF 拿到。**
  最省，而且對「勞檢來要資料」這個真實流程其實夠用（他們要的是一份文件，不是帳號）。
- **(c) 沿用 `READ`，另外做一次性的分享連結。** 不建議 —— 那是一套新的授權機制。

**決策（20260908）：走 (b)。外部觀眾拿到的是匯出檔案，不是帳號。**

這同時是對「勞檢來要資料」這個真實流程的正確建模 —— 他們要的是一份可以帶走、
可以歸檔的文件，不是一個登入權限。附帶的好處是 20260908 的角色決策
（`VIEWER` 一律擋下）不必因為這支功能而重開。

`SalaryAccess.AUDIT` 這個角色仍然記在這裡，作為日後真的需要「外部人員長期
自助查詢」時的解法 —— 但那是另一個需求，不是這一個。

## 7. 匯出

外部觀眾的主要交付形式。沿用既有的匯出機制，不另造一套：

- `salary_record_csv.ts` 已經處理過 CJK 的 BOM 與欄位轉義 —— 抽共用，不複製。
- `salaryRecordExportApi` 的形狀（掛在被匯出的對象底下）與下載工具
  （`lib/utils/download_file.ts`）照用。
- **每一列要帶齊「誰、何時記錄、何時生效、前值、後值、原因」** ——
  匯出檔案要能獨立閱讀，收到它的人手上沒有這個系統。
- 檔頭要寫明資料範圍：`本表記錄自 YYYY-MM-DD 起`（見 §8）。

PDF 暫不做：既有的 PDF 路徑（`salary_pay_slip_pdf.service.ts`）為薪資單的
版面而生，而 CJK 字型在生產環境的渲染**至今未驗證**（薪資單計畫書的未結項）。
不要讓一個新功能去踩一個已知未驗證的相依。

## 8. 上線之前的歷史：兩種來源，讀得出差別

新表從上線那天才有資料。**這件事必須在畫面上說出來。**
一張沒說明起點的異動表，讀者會把「空白」讀成「沒有變動」——
對稽核而言那比沒有這張表更糟。

處置：

1. **表裡不塞任何回填列。** 每一列都是當時記下來的。
2. **畫面與匯出檔頭固定顯示**「本紀錄自 YYYY-MM 起」。
3. **從 `SalaryRecord.inputSnapshot` 回推的部分，作為讀取時計算的第二個區塊**，
   標題明確寫「以下自薪資紀錄回推，非當時記錄」，並列出它的兩個限制
   （只覆蓋有存過紀錄的月份；紀錄重存會改變回推結果）。

為什麼不把回推結果寫進表裡（`source: RECORDED | DERIVED` 一欄了事）：
混在同一張表裡，日後總會有人寫出忘記過濾 `source` 的查詢，
而那個 bug 的症狀是「回推的猜測被當成當時的紀錄」—— 在稽核情境下這是最糟的一種錯。
分開放，誤用需要刻意。

## 9. 與既有機制的關係

### 9.1 與 `AuditLog` 的分工

兩者都在記「誰改了什麼」，但形狀不同、用途不同，**不合併**：

|        | `AuditLog`             | `SalaryEmployeeProfileChange` |
| ------ | ---------------------- | ----------------------------- |
| 記什麼 | 誰對哪一筆做了什麼動作 | 前後值                        |
| 讀者   | 系統管理／個資事故調查 | 老闆、會計師、勞檢            |
| 呈現   | 一條時間軸             | 一位員工的條件變化            |

合併的代價是 `AuditLog` 要長出 `before` / `after` 兩個 Json 欄位，
而 JOURNAL / VOUCHER / EMPLOYEE_PII 三種型別都不需要它們 ——
那會讓一張已經在用的表為了一個型別而變寬。

**但薪資模組在 `AuditLog` 裡是零筆這件事仍然是缺口**，且與本需求無關：
「誰刪掉了 3 月那筆薪資紀錄」「誰匯出了全帳本的薪資」要靠它回答。
另案處理，不夾帶。

### 9.2 與 `ISalaryEmployeeProfile` 的分類表

`documents/architecture/salary_employee_profile_plan.md` §1 有一張 35 欄的分類表，
而 `salary_employee_profile.test.ts` 拿它與型別對拍 —— 新增欄位忘了分類就會紅。

**差異表也要接上那張表**：新增一個員工檔欄位時，
「它算不算薪資異動、要不要預設顯示」必須是一個被迫回答的問題。
做法是讓 diff 的欄位清單從同一份型別推導（`keyof`），
並由測試斷言「每一個欄位都被歸進『預設顯示』或『預設隱藏』其中一類」——
漏掉就紅。

**記錄全部欄位，只在顯示時篩選。** 反過來（寫入時就篩掉）省下來的是位元組，
賠掉的是拿不回來的資料。預設顯示：本薪、伙食費、兩種其他加給、
三個投保旗標、扶養人數、自提勞退比例、僱用型態、到職／離職日。
預設隱藏：email、行業別代碼、`baseSalary30Days`、姓名／編號的更正。

## 10. 誠實的邊界：可稽核 ≠ 不可篡改

外部觀眾這個需求容易被讀成「要做一份不可篡改的紀錄」。**本 repo 做不到那件事**，
把話說清楚比留下錯誤的印象重要：

**做得到的：**

- 應用層只增不改 —— 沒有任何 API 路徑可以 update 或 delete 這張表的列。
  由測試釘住（掃 repository 的原始碼，禁止對這個 model 出現 `update` / `delete`）。
- 出處齊全：誰、何時記錄、何時生效、前後值。
- 員工被移除後歷史仍在（§5.3）。

**做不到的：**

- 有資料庫權限的人可以直接 `UPDATE`。任何純應用層的方案都擋不住這件事。

**刻意不做的：hash 鏈（`prevHash` / `rowHash`）。**
它能讓靜默的竄改**可被偵測**，但前提是有人去驗證那條鏈 —— 而目前沒有驗證者。
一個沒人檢查的 hash 欄位是表演，不是保證。
§3.3 的 schema 之後要加這兩欄不需要改寫既有列，所以現在不加不會付未來的代價。
真的需要時，同時要有的是一支驗證端點與一個會看它的人。

## 11. 保存期限：離職後五年（20260908 決策）

**離職員工的調薪歷程保存五年。** 與勞基法對工資清冊的保存要求同一個量級
（§23 第 2 項要求置備工資清冊並保存五年 —— 確切引用與適用範圍仍建議法務確認，
但五年這個數字本身已經拍板，實作不必等它）。

### 11.1 第一版怎麼實作這個決策：什麼都不刪

聽起來像沒做事，但這是對的實作，理由有三：

1. **五年是下限。** 不刪除必然滿足它，而且滿足得毫無疑義。
2. **系統上線至今不到五年**，第一批可刪的資料在 2031 年之後才會出現。
   現在寫一支刪除工作，等於寫一支五年內不會執行、也因此五年內不會被測到的程式碼 ——
   而它第一次真的跑起來的那天，寫它的人已經不在了。
3. **刪錯的代價不對稱。** 多留的代價是儲存成本與個資面的檢討空間；
   刪錯的代價是勞檢要資料時拿不出來，且不可回復。

所以第一版**不寫任何刪除或歸檔邏輯**，並把這個決策寫進 schema 註解與本節，
讓 2031 年接手的人知道「不刪」是決定，不是忘了做。

### 11.2 但起算點現在就要能算得出來

五年從**離職日**起算，所以能不能執行這個決策，取決於 `resignDate` 可不可靠。
今天它是選填的、也沒有任何東西保證它被填 —— 一個沒填離職日的離職員工，
未來的刪除工作**算不出到期日**，只能永遠留著（fail safe，但與決策不符）。

第一版不修這件事，但要記著：日後真的要做保存期限管理時，
第一步是「離職日的完整度」，不是寫刪除工作。

### 11.3 反方向的風險仍然存在

個資法要求特定目的消失時應刪除，而「不刪」在五年之後就站到了那條規定的對面。
這與薪資單計畫書 §10.1 未結的薪資資料分級（ADR 018）是同一個問題。
五年這個下限已經定了，**上限**（超過五年是否必須刪）留給那個決策。

## 14. 實作後的實況（20260908）

PR A（資料層）、C（生效月份）、B（讀取端點）、D（畫面）已實作。
PR E（匯出）尚未做 —— **而它是外部觀眾唯一的介面**（§6.3），所以這支功能
對「拿給會計師／勞檢看」這個原始需求還沒完成。

以下三件事與計劃書當初寫的不同，理由記在這裡而不是只留在程式碼裡。

### 14.1 §8 的「回推區塊」沒有做，改成指路

計劃書原本要在畫面下半部放一個「以下自薪資紀錄回推，非當時記錄」的區塊。
實作時決定不做，改成一句說明加上「請查閱各月薪資紀錄的輸入內容」。

理由是回推的東西**會變**：薪資紀錄 `(帳本, 員工, 年, 月)` 唯一、重存即覆寫
（薪資單計畫書 D3），所以同一段回推歷程今天算和下個月算可能不同答案。
把一個會變的區塊放在一張只增不改的表底下，即使標了字，
遲早會有人把它讀成當時的紀錄 —— 而那正是 §8 第 3 點想避免的事，
只是當初以為「標清楚」就夠。

指路比重建誠實：使用者仍然拿得到更早的資料（薪資紀錄的輸入快照就在那裡），
但他是**在薪資紀錄那一頁**看到它，而那一頁從來沒有聲稱自己是稽核軌跡。

### 14.2 沒有期間範圍篩選

§6.1 列了 `from` / `to`。第一版只做欄位篩選與分頁。

一位員工幾年下來是數十列，畫面一次載得完（50 筆一頁、可載入更早的）。
而 `(effectiveYear, effectiveMonth)` 的範圍比較在 Prisma 上要展開成四個
OR 子句，或另外加一個可排序的複合欄位 —— 那個複雜度換到的是一個
沒有人抱怨過的篩選。

真正需要它的是匯出（外部觀眾要「某段期間的異動」）。到 PR E 再決定
要不要加欄位，而不是現在先猜一個形狀。

### 14.3 排序用 `recordedAt`，不是生效期間

這一條計劃書沒寫，但它是個決定，值得留下來。

清單按**寫下來的順序**排（新的在前），不按生效期間。改用生效期間排序的話，
一筆 4/20 補登的「4 月起生效」會被插回 4 月的位置 ——
而「這筆是後來才補的」正是稽核最需要看見的那件事，排序一動就藏起來了。

畫面兩個時間都顯示，而且**只在兩者不同月時加一個標籤**（「補登」／「預先設定」）：
兩個日期並排時讀者通常只看第一個，標籤才會讓人真的注意到差異。

### 14.4 護欄的連帶調整

- `salary_repo_scope.test.ts`：`listProfileChanges` 進了生命週期分類表
  （`NO_SOFT_DELETE`），而且它的三支查詢替身**必須加進租戶斷言的清單** ——
  漏掉的話那一支會空過（驅動器呼叫得到它，但檢查的替身裡沒有它交出去的查詢）。
  該檔的 `everyCall.length > 0` 哨兵就是為了讓「沒有被問」與「問了而通過」分得開。

## 15. 把差額搬到使用者本來就在看的地方（20260908 修正）

### 15.1 回饋：「這個異動紀錄並不好用」

原話描述的場景是：

> 王小明原本的薪資是 29000，從九月份起上調為 30000，
> 則王小明九月份薪資紀錄的金額欄位（或多一格欄位）會標示出 +1000

**這個回饋是對的，而問題不在資料，在位置。**

§6 到 §14 做出來的是一個獨立的稽核視圖，藏在員工列表的按鈕後面 ——
它要求使用者「先想到要去查」。而真實情境裡他沒有在查任何東西，
他在看九月的薪資紀錄，那個 `+1,000` 應該**自己送上來**。

兩者不是替代關係：`+1,000` 回答「變了多少」，調薪歷程回答
「為什麼、誰改的、從哪個月起生效」。前者是標題，後者是點開才要看的註腳。

### 15.2 來源仍然是異動表，不是「跟上一筆紀錄相減」

相減看起來更省 —— 不需要異動表，兩筆快照一減就有數字。不採用，有三個理由：

1. **「上一筆」可能不是上一個月。** 八月沒存紀錄的話，九月的上一筆是七月，
   而 `+1,000` 沒有說清楚是跟誰比。要說清楚就得在畫面上寫「較 7 月」——
   而那句話會讓使用者以為八月漏存了。
2. **數字會被別人改動。** 薪資紀錄 `(帳本, 員工, 年, 月)` 唯一、重存即覆寫
   （薪資單計畫書 D3）。有人重存八月，九月的差額就**靜靜地變成別的數字**。
   異動表只增不改。
3. **說不出為什麼。** 相減只有數字，沒有原因、沒有誰、沒有生效月份。

而 `effectiveYear` / `effectiveMonth` 的語意正好就是「從九月起」——
所以這裡問的是「有沒有一筆異動是這個月生效的」，不是去比對相鄰紀錄。
§4 那個「生效月份必須與記錄時刻分開」的決定，在這裡才真正兌現。

### 15.3 差額標在本薪，不標在實發金額（20260908 產品決策）

列表原本的三個金額是實發金額、應稅薪資、雇主成本 —— 都不是本薪
（本薪在 `inputSnapshot.baseSalaryTaxable` 裡，列表的回應本來沒有帶）。
所以新增一欄「本薪」。

**不標在實發金額上**，理由是實發會因為加班、請假、健保補收而動：
一個加了班的月份會顯示 `+8,200`，而使用者會把它讀成調薪。
**誤導比沒有更糟** —— 一個沒有差額的欄位只是少了資訊，
一個標錯的差額會讓人以為自己知道發生了什麼。

本薪只有調薪會動，所以那個 `+1,000` 說的就是調薪。

「這個月實發比上個月多多少」是另一個問題（月對月差異），
它需要的不是一個數字而是一份拆解（加班多了幾小時、健保補收多少），
留給日後。

### 15.4 三個容易做錯的地方

**建檔不算調薪。** `CREATE` 的 `changedFields` 是全部欄位、`before` 是 null。
算進來的話，新員工的第一筆薪資紀錄會顯示 `+29,000` —— 讀起來像一次巨額調薪，
實際上只是「這個人被建立了」。查詢只認 `action = UPDATE`。

**同月多筆取淨變動，而且要說出筆數。** `29,000 → 31,000 → 30,000` 的淨變動
是 `+1,000`；只取第一筆會顯示 `+2,000`、只取最後一筆會顯示 `-1,000`，
兩個都不是這個月實際發生的事。而淨變動本身也會被讀成「調了一次」，
所以 `count > 1` 時畫面必須說出來 —— 沒有筆數，中間那個 31,000 就消失了。

**一次撈整批。** 逐筆查是 N+1：一頁 20 筆就是 21 次往返。它不會壞掉，
只會慢 —— 而「只會慢」的缺陷通常活很久，因為沒有任何測試會紅。
`salary_base_salary_delta.test.ts` 把它變成會紅的事。

### 15.5 順帶抓到一個真的錯誤組合

詳情彈窗會比對「這個月試算用的本薪」與「異動後的本薪」，不一致時出一句警告。

那個組合是真的會發生的：有人把員工檔調成 9 月起 30,000，
但九月的薪資是在調整**之前**就算好存下的（或試算時手動改回舊值）——
於是薪資單上的本薪是 29,000，而員工檔說 30,000。

兩個數字都不是錯的（一個是條件、一個是那次試算的事實），
但它們不一致這件事**只有並排時看得出來**，而詳情彈窗正好並排。
不擋、不自動修，只說出來 —— 要不要重算是使用者的判斷。

### 15.6 為什麼是彈窗，不是就地展開那一列

`DataTable` 不支援展開列，而它有 16 個頁面在用。為了這一個功能改共用元件
是錯的交換 —— 20260906 那次「`IDataTableColumn.className` 只到 `<th>`」
的事故是同一個教訓：那次的正解是改自己這一頁的版面，不是改 16 個頁面共用的東西。

彈窗夠小、標題直接寫著「2026 年 9 月起的本薪異動」，
所以「我還在看九月」這件事沒有丟掉。從它再往下有一個
「查看完整調薪歷程」，開啟 §13 做好的那個彈窗 ——
兩者不同時出現（點過去時詳情先關掉），否則關掉上層會撞回下層，
而使用者以為自己按的是「關閉」。

為此把 `EmployeeHistoryModal` 的 `employee` 參數從
`ISalaryCalculatorEmployee` 收窄成 `{ id, name, number }`：
它只拿這三個欄位做事，而收整個員工物件會讓薪資紀錄頁開不了它
（那一頁手上只有 `record.employee`）。型別窄到剛好用得到的欄位，
呼叫端就自然變多。

### 15.7 連帶調整的護欄

`salary_delivery_ui_contract.test.ts` 有一條「repository 的每一條讀取路徑
都帶上最近一次寄送」，它掃的是整檔的 `include:`。這支 repository 現在多了
一次對**另一張表**的查詢（異動表），它自然帶著自己的 include —— 於是那條紅了，
而紅的原因與「寄送關聯有沒有帶」完全無關。

改成數量對拍：**每一次 `prisma.salaryRecord.{find*, upsert}` 都要有一個
`include: RECORD_INCLUDE`。** 新增薪資紀錄的讀取路徑時仍然自動納入
（那才是原本要守的事），而對別張表的查詢不再被誤算。
驗證過原本的缺陷（某條讀取路徑漏掉 include）仍然轉紅。

### 15.8 仍未做

- **實發金額的月對月差異**（§15.3 最後一段）—— 它需要一份拆解，不是一個數字。
- **PR E（匯出）**。`listRecordsByIds` 已經帶上本薪異動，所以匯出接得上，
  但欄位與檔頭還沒做。外部觀眾仍然拿不到東西。

## 16. 差額改由紀錄本身算（20260908 第二次修正）

### 16.1 實測撞到的事

§15 把差額掛在 `baseSalaryChange`（員工檔的異動紀錄）上。實測的結果是
**兩個月本薪差一萬，畫面上什麼都沒有**：

```
2026 年 9 月   劉安安 443   44,000   42,145
2026 年 8 月   劉安安 443   54,000   51,996
```

原因不是 bug，是設計：異動紀錄只在**寫入員工檔**時產生。而在計算機上改本薪、
按儲存時，系統會問「順便更新員工資料嗎？」——

- 選「更新員工資料並儲存」→ 寫員工檔 → 有異動紀錄 → 差額出現
- 選「只存這一次」→ **員工檔不動 → 沒有異動紀錄 → 什麼都沒有**

而那個彈窗的說明只寫了「員工資料維持原樣」，完全沒提這個選擇也決定了它會不會
進歷程。**使用者不可能知道自己剛剛放棄了什麼。**

### 16.2 為什麼這是設計錯誤，不只是文案問題

我把「調薪」定義成「有人明確編輯了員工檔」，而使用者的心智模型是
「這兩個月的數字不一樣」。後者是他眼前的事實。

前者要求一種紀律 —— 每次調薪都得記得在那個彈窗按對按鈕 —— 而
**忘記按不會有任何症狀**，只是三個月後歷程上少一筆，沒有人會發現。
把功能建立在一個看不出被違反的紀律上，正是本 repo 的檢查清單一再要避免的形狀，
而我在 §5.1 才剛用同樣的理由把追加寫入收口到 repository。

### 16.3 兩層資料：差額一律有，歸因有的時候才有

|                    | 來源         | 何時有                       | 回答什麼                     |
| ------------------ | ------------ | ---------------------------- | ---------------------------- |
| `baseSalaryDelta`  | 紀錄自己     | **一律**（只要有更早的紀錄） | 變了多少、跟哪個月比         |
| `baseSalaryChange` | 員工檔異動表 | 有編輯員工檔時               | 誰改的、原因、從哪個月起生效 |

第二層缺席時**不是留白，而是明說它缺席**：
「這個月的本薪與上一筆不同，但沒有對應的員工資料異動紀錄。請到員工列表編輯異動原因。」

一句陳述加一個動作。20260908 的初版還多寫了一句推測
（「多半是在計算機上選了『只存這一次』」），後來拿掉 ——
使用者要的是下一步，不是系統對他做過什麼的猜測。
文案以繁中為準，其餘四個語系對齊它。

**指示必須說到生效月份（20260908 修正）。** 初版寫的是
「請到員工列表編輯異動原因」，而照著做**不會補上這一個月的原因** ——
員工列表的編輯會產生一筆**新的**異動列，生效月份是使用者在那裡選的
（預設當期）。於是他照做完之後回到這一頁，仍然看到「沒有對應的異動紀錄」。

那是最難查的一種錯：指示看起來清楚、使用者照做了、系統也沒出錯，
只是那兩件事對不上。

所以文案改成「請到員工列表編輯，並把生效月份設為 {{year}} 年 {{month}} 月」，
而且**年月由 `record` 帶進文案**，不寫「本月」——
「本月」在這裡有歧義（這一筆的期間 vs 今天所在的月份），
而猜錯的那個人會把原因掛到今天這個月。

**被否決的另一條路**：讓使用者直接補登過去那一筆異動的原因。
那需要「編輯既有異動列」的能力，與整張表「只增不改」的前提直接衝突
（§10：那張表在 schema 上就沒有 `updatedAt`）。
在稽核軌跡上開一個可寫的洞，換一個文案能解決的問題，不值得。

同時把「順便更新員工資料嗎？」的說明補上那個後果 ——
一個藏著看不見後果的選擇，是這次的根因。

### 16.4 `previousYear` / `previousMonth` 為什麼一定要帶

「上一筆」不保證是上一個月：八月沒存紀錄的話，九月的上一筆是七月。
一個光禿禿的 `−10,000` 那時候就是一句沒說清楚的話，而使用者會默認
它是跟上個月比。畫面一律寫出「較 8 月」——即使真的就是上個月。
永遠寫出來比「有時候寫」簡單，而且永遠不會錯。

### 16.5 為此新增了一個純量欄位

`SalaryRecord.baseSalary`（`@map("base_salary_snapshot")`）。

**為什麼非得抽出來**：差額要比「上一筆」，而上一筆通常不在當前那一頁 ——
一頁 20 筆、三十位員工的話，一頁連一個月都放不完，於是**沒有任何員工的
上一筆會在同一頁**；就算放得下，每一頁的最後一列也永遠沒有前一筆。
頁內計算會在小資料量下「看起來對」，而那是最糟的一種對。

所以必須另外查。而本薪原本只在 `inputSnapshot` 這個 Json 裡，
Json 取不出單一欄位 —— 要拿上一筆的本薪就得撈回那些員工所有紀錄的完整快照
（一本三年三十人的帳約一千列、每列兩 KB，也就是每次翻頁多傳兩 MB）。
抽成純量之後那個查詢只回三個小欄位。

**Json 仍然是真相**：純量欄位是 `inputSnapshot.baseSalaryTaxable` 的投影，
由 `upsertRecord` 從**同一份 input** 取值（不由呼叫端另外傳一個參數）——
所以兩者不可能分岔。分岔的症狀會是「列表上的本薪與點開薪資單看到的不一樣」，
沒有任何錯誤訊息。

**回填是這次改動的一部分，不是選項。** 本專案沒有 `prisma/migrations/`，
新欄位必須帶 `@default(0)`（否則既有列 push 不上去），而 `0` 不是空值、
**是錯的值**：一筆本薪為 0 的紀錄會讓下一個月顯示「較上月 +44,000」。
`scripts/backfill_salary_record_base_salary.ts` 就是那次改動的 migration 紀錄，
刻意留在版控裡，並登記在 `transaction_layering.test.ts` 的維運腳本清單上。

刻意**不做**「純量是 0 就退回讀 Json」的保險：那會讓忘記回填這件事被永久遮住，
換來兩份實作與一個沒人知道還在的分支。沒回填的列顯示本薪 0 ——
大聲、看得見、查得出來。

### 16.6 差額為 0 時不顯示

兩個月本薪一樣是常態（多數人多數月份沒調薪），而每一列都掛一個
`較 8 月 +0` 會把真正有變動的那幾列淹掉。

### 16.7 一道護欄被搬到型別上

`salary_delivery_ui_contract.test.ts` 的「每一條讀取路徑都帶上最近一次寄送」
原本掃「檔案裡每一個 `include:` 都要是 `RECORD_INCLUDE`」。
20260908 一天內紅了兩次，**兩次都與寄送關聯無關**：

1. repository 多了一次對別張表的查詢（異動表），它帶著自己的 include
2. 又多了一次只取純量欄位的投影查詢（`select:`，算差額用），它不需要 include

改成數量對拍之後第二次仍然紅（投影查詢也是一次 `findMany`）。
那種紅指向沒有壞掉的地方，而最快的修法都是錯的 ——
把投影塞進 `RECORD_INCLUDE`，或刪掉那條測試。

**真正的守門一直是型別**：`toSummary` / `toDetail` 的參數型別
`SalaryRecordWithEmployee` 要求 `employee` 與 `paySlipDeliveries`，
少了 include 的查詢交給 mapper 就是編譯錯誤（實測：拿掉 `listRecordsByIds`
的 include，`tsc` 直接報 missing properties）。

所以那條測試改成只釘型別守不住的那一半：**有人把型別本身放寬**
（把 `paySlipDeliveries` 改成選填、或把 mapper 的參數改成 `SalaryRecord`）。
驗證過那個 mutation 會轉紅。

### 16.8 仍未做

- **實發金額的月對月差異** —— 它需要一份拆解（加班多幾小時、健保補收多少），
  不是一個數字。
- **PR E（匯出）。** `listRecordsByIds` 已經帶上差額與異動，所以匯出接得上，
  但欄位與檔頭還沒做 —— 外部觀眾仍然拿不到東西。

## 17. 「異動原因」的入口現況與缺口（20260908）

### 17.1 四條寫入路徑，只有一條問得到原因

| 入口                             | 生效月份                          | 異動原因                |
| -------------------------------- | --------------------------------- | ----------------------- |
| **編輯員工**（員工列表）         | 使用者選（`input[type="month"]`） | **有，使用者填**        |
| **計算機「更新員工資料並儲存」** | 計算機當下選的年月                | **有（20260908 補上）** |
| 新增員工                         | 伺服器補當期                      | 沒有                    |
| 移除員工                         | 伺服器補當期（無 request body）   | 沒有                    |

### 17.2 第三、四列沒有原因是可以接受的

建檔的原因就是「入職」，移除的原因就是「不在名單上了」——
問一個答案永遠一樣的問題，只是讓那兩個動作變麻煩。

### 17.3 **第二列不可接受**

那是實務上最常見的調薪動作：在計算機上算薪水時順手把本薪改掉，
存檔時系統問「順便更新員工資料嗎？」，按下「更新」。

於是「為什麼調薪」這個問題**最需要答案的地方，正好是唯一問不到的地方** ——
大多數異動列的 `reason` 會是 `null`，畫面上顯示「—」。
員工列表的編輯彈窗有那個欄位，但那條路走的人少
（多數人不會為了調薪先去員工列表編輯，再回計算機算薪水）。

### 17.4 已完成（20260908）：原因欄加在差異確認彈窗上

**位置：`profile_diff_modal.tsx`。**

那個彈窗已經在列出差異、已經在問「要不要寫進員工檔」——
它就是「這次要寫員工檔」那個時刻，而異動原因只在那個時刻有意義。

**不加在計算機主畫面上**：那裡的欄位描述的是「這個月的薪資怎麼算」，
而原因描述的是「這次為什麼改員工檔」。放在主畫面會讓一個
「這次不寫員工檔」的使用者也看到它、也填它，而填了不會有任何效果。

實作是一條路：彈窗多一個選填輸入 → 傳給
`salary_result_section.tsx` 的 `updateProfileAndSaveHandler` →
併進已經在傳的 `{ effectiveYear, effectiveMonth }`。
**後端一行都沒改** —— `ISalaryProfileChangeRequest.reason` 早就在了、
route 的 zod 也早就收了。

### 17.4.1 三個實作上的判斷

**只有「更新」那一條收原因。** `updateAndSaveHandler` 的簽名變成
`(reason?: string) => Promise<void>`，而 `saveOnlyHandler` 不收 ——
選「只存這一次」時員工檔不動、不會產生異動紀錄，那句話沒有地方可以去。
兩條都收的話，使用者填了原因卻選「只存這一次」，那句話會靜靜消失。

**標題明說「只在更新員工資料時記錄」。** 使用者有權在填之前就知道這件事，
而不是填完之後發現它不見了。

**空字串一律送 `undefined`。** 空字串進了資料庫，「沒填原因」與
「填了一個空的原因」在型別上就分不開了 —— 而畫面對前者顯示「—」、
對後者顯示一片空白，讀者以為資料壞了。

**位置在提示之後、按鈕之前。** 讀完「這裡問的只是要不要把員工資料也一起改掉」
之後，使用者才知道這個欄位是給哪一條出路用的。放在差異清單上方會讓它
看起來像「這次薪資的備註」，而它不是。

### 17.5 順帶記下：回填腳本的退場條件

20260908 被問過「開發機跑完了，`backfill_salary_record_base_salary.ts`
還有保留的必要嗎」。有，而且判斷不能只看一台機器：

1. **其他環境還沒跑** —— production、staging、其他開發者的本機、
   CI 的 e2e 資料庫。任何一個沒跑過的地方，本薪都是 0。
2. **它是那次 schema 改動唯一的紀錄。** 沒有 `prisma/migrations/`，
   刪掉之後 `@default(0)` 就變成一個沒有說明的地雷。

退場條件寫在腳本的檔頭註解裡：所有還會被部署的環境都跑過了，
且不存在任何早於那個欄位的分支還可能被部署。那一天刪掉它的同時，
要把「為什麼那一欄有 `@default(0)`」搬到 schema 註解 ——
那個預設值本身刪不掉（沒有 migrations），所以它需要一個解釋活著。

`scripts/` 底下已經有五支同類的回填腳本，保留也是這裡的既有慣例。

## 18. 匯出（PR E，20260908 完成）

### 18.1 不是新做一支，是加八個欄位

`salary_record_csv.ts` 早就存在（20260904 的薪資紀錄 CSV 匯出），
而它已經處理過這份檔案真正的坑：公式注入、跳脫順序、BOM + CRLF、
千分位、比率欄。所以 PR E 的實際內容是**在既有的欄位表上加八欄**，
不是新造一套匯出。

| 欄位                 | 來源                                 | 何時有值             |
| -------------------- | ------------------------------------ | -------------------- |
| 月本薪（設定）       | `record.baseSalary`                  | 一律                 |
| 本薪較上一筆期間     | `baseSalaryDelta.previousYear/Month` | 有更早的紀錄時       |
| 本薪較上一筆差額     | `baseSalaryDelta.delta`              | 同上                 |
| 員工檔本薪異動前／後 | `baseSalaryChange.before/after`      | 有員工檔異動時       |
| 員工檔本薪異動原因   | `baseSalaryChange.reason`            | 同上（且使用者填了） |
| 員工檔本薪異動記錄者 | `baseSalaryChange.changedBy.name`    | 同上                 |
| 員工檔本薪異動記錄日 | `baseSalaryChange.recordedAt`        | 同上                 |

### 18.2 為什麼兩組欄位不合併

「較上一筆」一律有；「員工檔異動」有的時候才有。**最常見的一列是
「差額有值、異動欄位空著」** —— 在計算機上改了本薪、選了「只存這一次」。

合成一組的話，收到 CSV 的人會把「沒有異動紀錄」讀成「沒有調薪」。
那是這份檔案最不能出的錯，因為它的讀者手上沒有這個系統、也不會來問。

### 18.3 標題必須自己說得完

CSV 沒有地方放說明文字（加一行前言會讓試算表的表頭解析錯位），
所以「員工檔本薪異動…」這幾個字要自己交代來源。§8 給畫面用的那句
「本紀錄自 YYYY-MM-DD 起」在 CSV 裡沒有位置 ——
這是這個格式的限制，記在這裡而不是假裝解決了。

### 18.4 「月本薪（設定）」與既有的「本薪（應稅）」是兩欄

前者是這個人這個月的本薪**設定**，後者是實際計入的**金額** ——
月中到職的人那兩個數字不一樣（後者按比例算過），而那個差異正是對帳要看的。
合成一欄的話，比例計算過的金額會被當成他的月薪。

### 18.5 抓到一個既有的坑：負數會被中和成文字

`FORMULA_TRIGGER` 包含 `-`（試算表會把 `-` 開頭的欄位當公式求值），
而「本薪較上一筆差額」是這份 CSV **第一個可能為負**的欄位。

減薪的 `-10000` 會被補成 `'-10000` —— 在 Excel 裡那是一格**文字**：
整欄加總不起來、排序變成字典序。而檔案打得開、看起來完全正常，
只有拿去算的人會發現，而他多半會以為是自己的公式寫錯。

在這之前所有金額都非負，所以這個坑一直沒有出現。

處置是給欄位一個 `numeric?: true` 的出口，並且**做成 opt-out 而不是 opt-in**：
預設仍然中和。反過來（只對「使用者輸入的欄位」中和）需要正確標記每一個
文字欄位，而標錯一個的後果是公式注入回來了；預設安全、明確標記例外，
標錯的後果就只是「一個數字變成文字」。

配對的測試有兩條：負數不被中和、以及**使用者輸入的欄位仍然被中和**
（姓名與異動原因）。第二條是防止「把 `-` 放行」在下一次重構時
變成「整列都放行」。

### 18.6 沒有值一律留空字串

不是「0」也不是「無」。「0」會被加總 —— 一份把「最早那一筆」算成
「差額 0」的報表，在統計調薪幅度時會把分母算大。
「無」會讓那一欄變成混合型別，排不了序。

### 18.7 這支功能到此對外可用

外部觀眾（會計師、勞檢、稽核）拿到的是這份 CSV：
每一列自己讀得懂，帶著本薪、變動、以及（有的時候）誰改的與為什麼。
§6.3 那個「不新增唯讀稽核角色」的決策到這裡才真正成立 ——
在此之前那個決策等於「外部觀眾什麼都拿不到」。

### 18.8 仍未做

**實發金額的月對月差異。** 它需要一份拆解（加班多幾小時、健保補收多少）
而不是一個數字，所以它是另一個功能，不是這個功能的欄位。
