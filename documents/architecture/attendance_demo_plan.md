## 🎯 1. Demo 要證明的五件事（兩段，約 9 分鐘）

兩段的目標聽眾不同：第一段講給**工務與職安**，第二段講給**主管與稽核**。

### 第一段：「工地上現在有誰」（約 4 分鐘）

| #      | 主張                                                             | 演示方式                                                          |
| ------ | ---------------------------------------------------------------- | ----------------------------------------------------------------- |
| **P1** | 員工用既有的公司 Google 帳號就能簽到                             | 在打卡頁上點「使用 Google 登入」→ 選帳號 → **自動回到打卡頁**，顯示自己的姓名、工號與今日班別      |
| **P2** | **人不在現場就打不了卡** —— 圍欄是到班的定義，不是事後標記       | 現場打卡成功；切遠處座標 → **地圖上的藍點跑出圓圈外**，按下去 403「距工區 3.2 公里」 |
| **P3** | 系統隨時答得出「哪個工地現在有幾個人、分別是誰、誰排了班卻沒到」 | 現場頁：地圖 + 在班／未打下班卡／未到工三個數字 + 名單 + CSV 匯出 |

### 第二段：「出勤對不對得上」（約 5 分鐘）

| #      | 主張                                                           | 演示方式                                                                                         |

## 🧭 2. 八條核心設計決策

### 2.1 固定班表是彈性班表的特例 —— 因此沒有 `shiftType` 欄位（P4）

`ShiftPattern` 六個欄位全部 NOT NULL：窗起、窗迄、核心起、核心迄、應工作分鐘、休息分鐘。
**固定班就是「窗＝核心」的彈性班。** 因此：

- 資料庫沒有 `shiftType`（有的話它唯一能做的事就是在有人改了時間卻忘了改它的那天開始說謊）
- 判定引擎沒有 `switch`，四條規則覆蓋兩種制度
- 前端顯示的 `kind`（固定／彈性）是**衍生值**，由六個欄位的值算出來
- 未來加第三種制度，**改的是資料不是程式碼**

### 2.2 `User` 與 `Employee` 之間本來沒有橋

登入身分是 `User`，出勤事實掛在 `Employee`，母文件沒有處理這個缺口。
決策：`Employee.userId String? @unique`。**綁定本身永遠是那個欄位**，差別只在它是怎麼被填上的。

**OAuth 身分**：首登以 `UserIdentity` 裡**已驗證的公司信箱**比對 `Employee.email` 自動填入。
email 比對只是首次綁定的引導 —— 公司信箱可以變更（改名、調動），而打卡歷史不該跟著飄移。
且 `personalEmailCipher` 是密文、DB 端查不了，用個人 Gmail 登入的人本來就對不上（ADR 018 §7 的必然結果，不是 bug）。
同帳本內兩筆員工檔的信箱只差大小寫時**擋住不猜**（`CF_EMPLOYEE_EMAIL_AMBIGUOUS`）—— 任選一筆綁定就是讓某人以另一個人的身分打卡。

**Passkey 身分走不到這條路徑。**
`User` 這張表**沒有 email 欄位**，passkey 使用者也不會產生 `UserIdentity` ——
候選信箱永遠是空的，`resolveEmployee` 必定丟 `NF_EMPLOYEE_FOR_USER`。
passkey 證明的是「你持有註冊時那把金鑰」，不是「你是哪個信箱的主人」，兩者本來就問不到同一件事。
那種帳號只能由人事以 `scripts/seed/link_employee_user.ts` 手動寫入 `Employee.userId`。

**而兩者互斥。** `Employee.userId` 只能指向一個 `User`，且 `oauth.service`
**絕不用 email 自動合併既有帳號** —— 同一個人的 passkey 帳號與 Google 帳號是兩個不同的 `User`。
手動綁了 passkey，Google 首登就撞 `CF_EMPLOYEE_ALREADY_LINKED`；留給 Google 自動綁，
passkey 登入就是「尚未對應到員工檔」。因此登入卡上的 Passkey 是**環境層級的備援**
（它不需要外部網路），不是同一位員工的第二把鑰匙。

**刻意不做「登入後輸入員工編號自助認領」** —— 員工編號印在識別證上，不是秘密；
讓它成為綁定的唯一憑據，等於把偽造他人出勤的成本降到零，而出勤紀錄依勞基法 §30 要保存五年。

### 2.3 圍欄外一律拒絕，而「拒絕」不得外推

座標未落入任何圍欄的打卡**不會寫進資料庫**，直接 403。圍欄就是「到班」這個事實的定義本身 ——
人不在登記的地點，不是「到班了但有疑慮」，是到班沒有發生，而系統不記錄一件沒發生的事。

它也是 P3 能成立的前提：**若允許圍欄外打卡，「工地上有幾個人」這個數字立刻失去意義**，而那個數字在疏散時是要拿來對人頭的。

但這條線必須劃清楚，不能變成通則：

| 情況                   | 性質                     | 處置                                                                           |
| ---------------------- | ------------------------ | ------------------------------------------------------------------------------ |
| 圍欄命中與否           | 對「到班事實」的**定義** | 拒絕                                                                           |
| 定位精度不足           | **證據品質**不足以判定   | 拒絕，但訊息是「請重試」而不是「你不在現場」                                   |
| 瞬移偵測（G5，未實作） | 對紀錄可信度的**推測**   | 收下並標記 —— 有誤判率的啟發式一旦拒絕，就會出現「員工真的到了工地卻打不了卡」 |

### 2.4 砍掉的是快取，留下的是真相

Demo 不建 `AttendancePresence` / `AttendanceDailyResult` / `AttendanceException` 三張表，全部改為**讀取時即時推導**。

母文件 §D10.1 自己說過：「『誰現在在班』完全可由 `AttendancePunch` 推導……推導是正確的，但每次推導不可行。」
**不可行的理由是效能，而 demo 沒有那個壓力。** 一個月 × 12 人 = 372 次純函數呼叫。

這一刀省下的不只是三張表，還有同交易一致性、`rebuildPresence`、勾稽對帳、異常子表整批替換、以及整個背景 Worker。
**而 demo 寫的推導邏輯，正好就是正式版 `rebuildPresence` 與 Worker 內部要呼叫的東西。**

規模上去之後的正解是**快取**（可隨時丟棄、丟了自己會重建），不是落地（丟不掉，而丟不掉的東西就會被當成真相）。

### 2.5 判定引擎是純函數：不碰 DB、不呼叫 `Date.now()`

「現在」由呼叫端注入（`nowMinuteOfDay`）。同一組輸入永遠得到同一組輸出 ——
**可重算是這整套判定唯一的驗收方式。**

同理，A9 判定矩陣的 `evaluatedAt` 在 route 取一次往下注入，整張矩陣共用同一個時間點：
逐列各取一次「現在」，兩位員工卡在寬限那一分鐘的邊界案例可能在同一張表裡得到互相矛盾的顏色。

時區換算集中在 `attendance_time.ts`，引擎只做整數運算 ——
引擎的測試不需要任何時區設定，而時區的測試只需要針對那一個檔案。

### 2.6 `STALE` 的語意是「我不知道」，不是「他不在」

現場名單的資料來源只有打卡：打上班卡進名單、打下班卡出名單。問題出在**忘記打下班卡**。

| 做法           | 後果                                                                           |
| -------------- | ------------------------------------------------------------------------------ |
| 一直當他在現場 | 名單只進不出，一週後全是忘記打卡的人堆著。**這張名單就廢了**                   |
| 立刻當他不在   | 但他可能真的還在加班。**疏散點名漏掉一個還在樓裡的人，是這套系統最不能犯的錯** |

`STALE` 就是那條線：「等多久之後，系統承認自己不知道」。它不是懲罰也不是異常，是**誠實**。
因此 `STALE` 的人**不移出名單**，而且要標出來 —— 他們恰恰是點名時要優先打電話確認的對象。

看板上三個數字回答三個不同的問題，**缺一個就會暗示系統其實不知道的事**：

- **在班**：系統知道他在
- **未打下班卡**：系統**不知道**他在不在
- **未到工**：排了班、時間到了，系統沒有收到任何打卡

### 2.7 非法狀態擋在三層，各自服務不同的呼叫者

以「上班日必須有班別、非上班日必須沒有」這條不變式為例：

1. **TypeScript**：`IDaySchedule` 是可辨識聯集 —— 寫不出來（編譯期）
2. **Zod**：A8 的請求本體也是可辨識聯集 —— 送不進來（API 呼叫者）
3. **`assertSchedulableDay`**（repository）—— 擋種子腳本、資料遷移、排班表 Excel 匯入

第三層不是重複：前兩層擋走 API 的呼叫者，第三層擋繞過 API 的路徑，
而**排班表匯入正是一次寫入上千筆、最可能把兩個欄位配錯的地方**。

> **為什麼不拆表**：ADR 019 對 `ProcessTask` 的解法是拆表讓非法狀態不可表示。這裡拆成
> `ScheduledWorkDay` / `ScheduledOffDay` 會**弄丟 `@@unique([accountBookId, employeeId, workDate])`** ——
> 「同一人同一天既排班又排休」變成新的非法狀態。
> **判準不是「有沒有 discriminator 欄位」，是「拆完之後非法狀態的總量有沒有變少」。**

### 2.8 工時只輸出分鐘，不換算金額

加班費、時薪、假日加給屬薪資模組職責（ADR 020）。**分鐘 → 金額的乘法絕不在本模組發生。**
被問到加班費時的正確答案：「出勤系統負責把時間算對，錢由薪資模組算 —— 兩邊各算一次，遲早會對不起來。」

## ⚖️ 3. 判定表（12 條中實作 11 條）

由上而下，第一個命中即決定當日狀態。

| #   | 條件                                        | 狀態          | 異常                                   |
| --- | ------------------------------------------- | ------------- | -------------------------------------- |
| 1   | `dayType ≠ WORK` 且無打卡                   | `OFF_DAY`     | —                                      |
| 2   | `dayType ≠ WORK` 且有打卡                   | `OFF_DAY`     | — （**假日出勤是加班事實，不是異常**） |
| 3   | 無排班紀錄                                  | `NO_SCHEDULE` | — （**不判曠職**）                     |
| 4   | 應出勤、完全無打卡、已過窗迄                | `EXCEPTION`   | `ABSENT`                               |
| 5   | 應出勤、完全無打卡、當日未結束              | `NORMAL`      | —                                      |
| 6   | 有 `CLOCK_OUT` 無 `CLOCK_IN`                | `EXCEPTION`   | `MISSING_CLOCK_IN`                     |
| 7   | 有 `CLOCK_IN` 無 `CLOCK_OUT`、已過窗迄+寬限 | `EXCEPTION`   | `MISSING_CLOCK_OUT`                    |
| 8   | `firstIn > coreStart + 寬限`                | `EXCEPTION`   | `LATE`                                 |
| 9   | `lastOut < coreEnd − 寬限`                  | `EXCEPTION`   | `EARLY_LEAVE`                          |
| 10  | 工作分鐘 < 應工作分鐘                       | `EXCEPTION`   | `INSUFFICIENT_HOURS`                   |
| 11  | G5 瞬移偵測                                 | `EXCEPTION`   | `SUSPICIOUS_JUMP`（**未實作**）        |
| 12  | 以上皆不成立                                | `NORMAL`      | —                                      |

**8–10 可同時成立**，因此引擎回傳的是**異常清單**而不是單一狀態。
**工作分鐘** = `clamp(lastOut, 窗內) − clamp(firstIn, 窗內) − breakMinutes`，為負取 0。

### 三條「不判為異常」的刻意設計 —— 演示時比任何一個異常更值得講

| 情境                     | 為什麼不判                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------ |
| **無排班**（#3）         | 判曠職等於系統自己發明了一個不存在的出勤義務。**沒有班表就沒有比較基準** —— 這是「零捏造」在本模組的具體形狀 |
| **當日未結束**（#5、#7） | 判定的前提是「這一天已經過完」。提早下結論會讓早班同仁每天早上都收到曠職通知                                 |
| **假日出勤**（#2）       | 標紅會讓真正的異常被淹沒                                                                                     |

> **它們證明系統知道自己不知道什麼。一套會把「沒排班」判成曠職的系統，產出的每一個數字都不能信。**

### P4 的四條規則對照（這張表就是演示腳本）

| 判定     | 統一規則                         | 本部行政班（固定）     | 工程師彈性班（核心 10–16）               |
| -------- | -------------------------------- | ---------------------- | ---------------------------------------- |
| 遲到     | `firstIn > coreStart + grace`    | 09:47 → **遲到 47 分** | 09:47 → **正常**                         |
| 早退     | `lastOut < coreEnd − grace`      | 17:30 → 早退           | 17:30 → 正常                             |
| 工時不足 | `工作分鐘 < requiredWorkMinutes` | 正常出勤時恆滿足       | 10:00–16:00 只有 360 < 480 → 不足 120 分 |
| 窗外時間 | 打卡先 clamp 進 `[窗起, 窗迄]`   | 08:00 到班不多算工時   | 06:00 到班不多算工時                     |

**同樣的 09:47，兩種制度得到相反結論，而中間沒有一行程式碼在區分它們。**

### 另外三個實作時的技術陷阱

1. **Prisma 產生的是字面量聯集，`@/constants` 的是 TS string enum（名義型別）。**
   enum 成員 → 字面量聯集可以，反向**編譯失敗**。因此凡是從 DB 讀出來要餵進引擎的欄位都要明寫轉換，
   值域一致由 `hr_enum_mirror.test.ts` 保證。
2. **`OFFICE-98` 原設定 09:00–18:00 的餘裕為零** —— 窗長 540 扣休息 60 = 480，與應工作分鐘完全相等，
   於是任何一分鐘的遲到都會同時觸發 `INSUFFICIENT_HOURS`。**寫判定引擎測試時才發現**：
   在「窗＝核心」的嚴格固定班下，遲到必然連帶造成工時不足，除非應工作分鐘 <（窗長 − 休息）。已改為 18:30。
3. **`AttendancePunch` 的 `id` 刻意沒有 `@default(uuid())`** —— 它是 PII 加密 AAD 的一部分，
   而加密發生在 insert 之前，等資料庫產生就來不及了（ADR 018 §3）。

> **需求原文**：「所有工作人員都要能看到現場人員名單。若發現人手不足，要有能夠銷假的功能。」
> **決策日**：2026-08-13　**目標**：下一週的演示

### 8.1 「銷假」在現在的資料庫裡沒有東西可以銷

先講清楚落差，因為它決定了整個工作量。

專案裡**沒有假單**。`WorkDayType.LEAVE` 只是 `EmployeeShiftDay` 上的一個裸旗標 ——
沒有假別、沒有起迄、沒有申請人、沒有核准人、沒有原因，也沒有任何異動軌跡
（`updateScheduleDay` 只留一行 `logger.info`）。而判定引擎對它的處理是：

```ts
if (schedule.dayType !== WorkDayType.WORK) return OFF_DAY;
```

`LEAVE` 與國定假日、例假、休息日**完全無法分辨**。

所以「銷假」若照最省的做法實作，就只是「把 dayType 從 LEAVE 改回 WORK」——
而那件事 A8 已經做得到了，等於這個需求不必寫任何程式碼。**那正是問題所在**：
現場如果問「這筆銷假是誰決定的、原本請的是什麼假、員工同意了嗎」，
系統一個字都答不出來，而這三個問題正是主管機關會問的。

**決策：做完整假單模型。** 銷假是對一個真實存在的物件的操作，不是對一個旗標的覆寫。

### 8.2 三張表，各自回答一個問題

| 表 | 回答的問題 | 為什麼不能併進上一張 |
|---|---|---|
| `LeaveRequest` | **為什麼不用來** —— 假別、原因、申請人、核准人、狀態 | — |
| `LeaveDay` | **哪幾天不用來** —— 一張假單逐日展開 | 假單是區間、排班是逐日；不展開就無法與 `EmployeeShiftDay` 對位，也無法只銷其中一天 |
| `LeaveRecall` | **誰要求誰回來、對方答應了嗎** | 徵詢會被婉拒，而婉拒過幾次是有意義的事實。做成 `LeaveRequest` 的狀態，第二次徵詢會抹掉第一次 |

**`LeaveDay` 是假單與排班之間的對位點。** `EmployeeShiftDay` 仍然是判定引擎唯一的輸入 ——
假單不改判定，假單**投影**成排班日；核准時寫 `dayType = LEAVE`，銷假時寫回 `WORK`。
這條路徑與 2.4 節「砍掉的是快取，留下的是真相」不衝突：排班不是快取，它是排班。

#### 讓「同一人同一天有兩張生效假單」不可表示

依 ADR 019，這種狀態要擋在資料庫，不是擋在 service。做法是 nullable partial unique：

```prisma
model LeaveDay {
  // Info: 僅在假單生效時填入 "employeeId:workDate"，其餘狀態為 null
  activeKey String? @unique @map("active_key")
}
```

Postgres 的 unique index 不約束 NULL，因此已駁回、已撤回、已銷假的日子可以無限多筆重複，
**而生效中的只能有一筆**。撤銷即把 `activeKey` 設回 null，不刪列 —— 刪掉的話「他曾經請過這天」就消失了。

同理，`LeaveRecall` 用 `pendingLeaveDayId String? @unique` 擋掉「同一天同時有兩張待回應的徵詢」。

### 8.3 銷假必須是徵詢，不是命令

**勞基法 §38 III：特別休假期日由勞工排定之。** 雇主僅得基於企業經營上之急迫需求，
「與勞工協商調整」。也就是說 —— 一個主管單方按下去就生效的「銷假」鍵，在法律上站不住腳。

因此流程是三段，而不是一個動作：

1. 主管在現場頁發起**銷假徵詢**，`reason` 必填（那就是「急迫需求」的書面記載）
2. 員工在自己的打卡頁看到徵詢，按**同意**或**婉拒**
3. 同意才寫回 `dayType = WORK`；婉拒則假單原封不動，並留下婉拒紀錄

**徵詢期間員工仍在假中。** 這一點必須在資料上成立而不只是口頭上：
主管按下去的當下如果就把那天改回 WORK，員工還沒回應就已經處在「排了班卻沒到」的狀態，
系統會把他算進未到工 —— 那是用系統事實去施壓，而那正是 §38 III 想避免的事。

> **這在演示上是加分題，不是負擔。** 兩台裝置的來回互動本來就演得出來，
> 而「系統懂勞基法」對主管機關是比任何一個功能都有力的訊號。

### 8.3.1 徵詢必須指名「回來上哪一班」

實作時補上的一條：`LeaveRecall.shiftPatternId` 非空。

「請你回來上班」不是一個完整的請求 —— 員工同意的必須是一個具體的班別，
而不是一個待定的時間。它同時讓「同意之後那天沒有班別」不可表示：
投影回 `EmployeeShiftDay` 時 `dayType = WORK` 與 `shiftPatternId` 一起寫入，
`assertSchedulableDay` 因此永遠成立，不需要在同意的那條路徑上再猜一次他平常上哪一班。

### 8.4 銷假只能往前，不能往後

**只能對「今天（含）以後」的假日發起徵詢。**

過去的假日改回 WORK，會讓那一天的判定從 `OFF_DAY` 變成 `ABSENT` —— 一個人的歷史出勤紀錄
因為今天的一次操作而多出一筆曠職。§7.3 第 3 順位標記過的那個洞（排班異動無軌跡、
會無聲改寫歷史判定），如果讓銷假走過去，就從「理論上的洞」變成「每天都在用的功能」。

這條限制擋在 validator，不是擋在 UI。

### 8.5 現場名單：全看得到，但精確位置分級

需求要的是「所有工作人員都看得到現場人員名單」，而現場名單等於**每位同事此刻在哪個工地**。
§7.3 第 1 順位已經標記過：這份程式碼接上真實員工資料就是全員位置揭露。

**決策：名單與人數全開放，地圖與座標只給主管。**

| 看得到 | 一般員工 | 主管 |
|---|---|---|
| 各工區在班／未打下班卡／未到工人數 | ✅ | ✅ |
| 各工區到班名單（姓名、工號、職稱） | ✅ | ✅ |
| **今日請假名單** | ✅ | ✅ |
| **圍欄地圖與座標** | ❌ | ✅ |
| 緊急點名 CSV 匯出 | ❌ | ✅ |
| 發起銷假徵詢 | ❌ | ✅ |

理由：工地實名制的正當理由是「我要知道現場現在有誰」——
那個理由支撐得起名單，支撐不起一張畫著所有人所在位置的地圖。
**名單回答「有誰」，地圖回答「在哪」，而需求問的是前者。**

「主管」的判定用 `Department.managerId === employee.id`（是否為任一部門的主管）。
**這不是權限矩陣**，是一個刻意最小的視野分級 —— §7.3 第 1 順位仍然是第 1 順位。

### 8.6 這兩個需求其實是同一個需求

現在的現場頁**看不到請假的人**：`expectedAbsentees` 硬性 gate 在 `dayType === WORK`，
請假的人既不在班、也不算未到工，他在畫面上完全不存在。

所以「人手不足要能銷假」的前提，是**先看得到誰在放假**。
兩個需求接在同一個地方：現場頁多一張「今日請假 N 人」的卡與名單，
而銷假徵詢的入口就在那份名單的每一列上。

這也讓演示的因果鏈完整：**看到缺口 → 看到誰能補 → 徵詢 → 對方同意 → 缺口補上**，
四個畫面串成一件事，而不是四個功能各演一次。

### 8.7 對既有設計的影響

| 既有設計 | 影響 |
|---|---|
| 判定引擎（`evaluateAttendanceDay`） | **完全不動**。銷假改的是 `EmployeeShiftDay`，引擎照樣是純函數 |

## 🔁 9. 登入方式的兩次改動（W17）

> 這一節記錄的不是「改了什麼」，是**為什麼同一件事改了兩次，而兩次的判斷都成立**。

### 9.1 事情的順序

1. 原始設計：Google 登入。理由是接得上公司既有帳號，而且**「他是誰」由公司信箱說了算，不是他自己填的**
2. 中途改 Passkey：`GOOGLE_OAUTH_CLIENT_ID` / `_CLIENT_SECRET` 申請不到。Passkey 不需要任何外部憑證
3. 改回 Google：憑證取得了

**變的是外部條件，不是判斷。** 值得記下來的是第 2 步暴露出來的東西 —— 它們在改回來之後仍然成立。

### 9.2 第 2 步留下的三件事

| 留下的 | 為什麼改回來之後仍然有用 |
|---|---|
| **閘門自己查 provider** | `SocialLoginButtons` 沒有可用 provider 時 `return null`。Google 一旦是唯一主要入口，那個 `null` 就是一張**空白登入卡** —— 標題、說明、註腳都在，中間什麼都沒有，看起來像按鈕壞了。這個問題已經真實發生過一次 |
| **`link_employee_user.ts`** | 從必要步驟降級為**救援工具**。現場信箱對不上（大小寫、別名、綁到別的 `User`）時，它是唯一能在 30 秒內處置的方式 |
| **`passkey_login.ts`** | 登入儀式從 `auth_modal` 抽出來的那一份。閘門與 modal 共用同一支，兩邊只有「登入之後做什麼」不同 |

### 9.3 OAuth 與 Passkey 的結構差異

**Passkey 是就地登入，OAuth 是離開再回來。**

`auth_modal` 對 OAuth 做的事只有一件：渲染 `<SocialLoginButtons>`。按下去之後整頁導向 Google，
modal 就被丟下了 —— 它從來沒有看過 OAuth 的結果。完成登入的是 `/auth/callback/google`。

因此「登入後留在打卡頁」不是免費的，要靠 `returnTo`（閘門傳 `usePathname()`，
經簽名的 state token 往返）。而 callback 有一條例外：

```tsx
if (role === SUPER_ADMIN || role === ADMIN) router.replace("/admin/dashboard");
else router.replace(payload.returnTo || "/user/account_book/");
```

**演示帳號不能是管理員**，否則第一步就跳離打卡頁。這條擋不在程式碼裡，只能寫在檢查清單上。

### 9.4 改回來之後回到清單上的三個依賴

1. **憑證**：`GOOGLE_OAUTH_CLIENT_ID` / `_CLIENT_SECRET`，**寫在系統設定（DB）並經 SUPER_ADMIN passkey 簽章**（執行手冊 §3.2）。
   讀取優先序是 DB 已驗簽 > env > 保底值，因此不放 `.env` —— 同時放兩處只會製造「改了 env 卻沒生效」
2. **origin**：OAuth 只能在 `NEXT_PUBLIC_APP_URL` 那個 origin 上完成；別的網址按鈕會 disabled 並說明
3. **網路**：`accounts.google.com`、`oauth2.googleapis.com`、`www.googleapis.com`（JWKS 驗簽）。
   最後一個最難診斷 —— 前面的授權全都會成功，只有最後一步失敗，看起來像帳號問題

## 📱 10. 全程用手機演示的補完清單

> **前提變更（2026-08-13）**：演示全程在手機上進行，沒有筆電。
> 這推翻了 §6 剛寫進去的「P2 用 DevTools 感應器」——**手機沒有那個面板**。
> 本節列出因此浮現的缺口，每一條都標明「誰要做、什麼時候做完」。

### 10.1 最大的一塊：手機根本連不到 demo 站台

`NEXT_PUBLIC_APP_URL` 目前是 `https://isunfa.localhost` —— 那是**開發機自己的名字**，
手機的 DNS 解析不到它。而這一頁需要的三件事**全部要求安全來源（secure context）**：

| 需要 | 沒有 HTTPS 會怎樣 |
|---|---|
| `navigator.geolocation` | 完全不啟動，畫面一直停在「定位中」 |
| Google OAuth | redirect_uri 必須與 Console 註冊的完全相符 |
| WebAuthn（Passkey 備援） | API 根本不存在 |

**所以手機演示必須有一個真的、有憑證的網址。** 兩條路：

| 方案 | 做法 | 代價 |
|---|---|---|
| **隧道（建議）** | `cloudflared tunnel` / `ngrok http 3000`，拿到 `https://xxx.trycloudflare.com` | 每次重啟網址會變 → Google Console 的 redirect URI 與 `NEXT_PUBLIC_APP_URL` 都要跟著改，**而後者是 build-time 內聯，改完一定要重啟** |
| 區網 IP + 自簽憑證 | `https://192.168.x.x:3000` + mkcert | 手機要安裝根憑證；iOS 還要到「關於本機 → 憑證信任設定」手動信任 |

> **T−5 就要決定並固定下來。** 這件事沒做，其他每一條都不用談。

### 10.2 P2 改用「真的走出去」

DevTools 不可用之後，剩下三條路，**建議第一條**：

| 方案 | 可行性 |
|---|---|
| **把 demo 工區圍欄半徑改小（60–80 公尺）** ✅ | 主講走出去 20–30 步就被拒絕，約 30 秒。**比偽造座標更有說服力** —— 觀眾看到的是一個人真的走出範圍，而不是一個輸入框。只需改 seed 參數 |
| Android + USB 連筆電遠端偵錯 | 要線材與 adb，且只有 Android。演示現場不建議 |
| P2 改播 T−3 錄好的螢幕錄影 | 保底，但那一段的張力會掉一半 |

**採第一案要注意**：`DEMO_GEOFENCE_RADIUS_METERS = 500` 是全域預設，
而現場的 `LOC-A` 要另外給一個小半徑。台詞要誠實：
「這個工區我們登記的範圍是 60 公尺，實際工程案場會依工區大小量測」——
**不要說「系統的圍欄是 60 公尺」**，那會讓觀眾以為 500 公尺那個數字是假的。

> ⚠️ 半徑改小之後，**定位精度的門檻相對變嚴**：精度 35 公尺對 60 公尺的圈已經是一半。
> `DEMO_MAX_ACCURACY_METERS = 200` 要跟著調到 50 以下，否則「站在圈內卻被判在圈外」會變成常態。
> 這一條在 T−5 場勘時要用當天那兩支手機實測。

### 10.3 兩支手機本身要先設定好

- [ ] **精確位置打開** —— iOS「設定 → 隱私權 → 定位服務 → Safari → 精確位置」；
      關閉時 iOS 只給約 1–3 公里的粗定位，會直接觸發 G3 的「定位精度不足」
- [ ] **不要用 App 內建瀏覽器**（LINE、FB）—— Google 會以 `disallowed_useragent` 拒絕登入
- [ ] **關閉低耗電模式** —— 會降低定位更新頻率
- [ ] 兩支各自登入不同的 Google 帳號
- [ ] **螢幕不要自動鎖定**（演示中鎖屏會中斷定位）

### 10.4 畫面在手機上的已知問題

| 頁面 | 問題 | 現況 |
|---|---|---|
| 打卡頁地圖 | **單指拖曳會被地圖吃掉，使用者捲不動頁面**，而打卡按鈕就在地圖下方 | 已在 `punch_map.tsx` 留 `ToDo`。正解是 `dragPan: false` + 「點一下啟用」遮罩，或雙指才平移 —— 要在真機上量過才知道哪種不誤觸 |
| 排班月曆 | 寬表格，手機上必須橫向捲動 | 未驗證。**第二段的 P4／P5 靠這兩張方格圖**，投影時橫向捲動很難看 |
| 出勤總覽 | 同上，欄數更多 | 同上 |
| 現場頁 CSV 匯出 | iOS Safari 的下載行為與桌機不同 | 未驗證 |

> **第二段（P4／P5）是否還要在手機上演，需要一個決定。**
> 若方格圖在手機上不可讀，替代方案是第二段改用**投影筆電**或**事先截圖**。
> 這一條要在 T−1 彩排前確認 —— 它會改變演示的裝置配置。

### 10.5 觀眾怎麼看到手機畫面

四十個人看不到一支手機。需要其中一項：

- AirPlay 到會場投影（要同一個網路，而會場網路常擋 mDNS）
- HDMI 轉接線（iPhone 需 Lightning／USB-C 轉 HDMI）
- 擷取卡 + 筆電（最可靠，但要多帶一組設備）

**T−5 場勘時要實地試一次**，這是唯一在現場才知道行不行的一項。
