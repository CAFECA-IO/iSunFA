# 架構決策紀錄 (ADR) 014: 真實 ESG / 溫室氣體盤查報告的匯入可行性評估

> **Date**: 2026-07-30
> **Author**: Tzuhan
> **Status**: Proposed(第 1 階段已實作,第 2–4 階段待排)
> **Branch**: `feature/esg_report_ingestion`(自 develop 切出,已併入 `feature/carbon_report_consolidated`)
> **Question**: 使用者上傳一份真實世界的 ESG 報告,我們的 AI 有辦法整理成系統要的 33 節格式嗎?

---

## 結論(先講)

**可以,但前提是上傳的必須是「溫室氣體盤查報告書」而非「永續報告書」。** 這兩者在市場上都被叫做「ESG 報告」,但結構完全不同,而我們的 33 節大綱只對得上前者。

用一份真實的盤查報告(高興昌鋼鐵 2023 年度,64 頁)實測,**28 個實質節有 26 節可在原文中定位到對應章節,結構近乎 1:1**。相對地,三份上市公司永續報告書實測下來,ISO 14064 專屬的那幾節(組織邊界方法、計算細節、查證範圍、實質性門檻、保證等級)系統性地不存在——因為它們本來就在另一份查證聲明書裡。

技術面原本有一個硬阻塞:PDF 一律走 Gemini inlineData,超過 14 MB 直接拒收,而真實報告經常超過。**本次已實作「文字層優先 + 品質閘門」解除此限制**,實測四份報告中原本被擋掉的兩份現在都能進來。

## 一、實測基準(四份真實文件)

| 文件                                | 類型           |    大小 | 頁數 | 文字層字/頁 | 解碼失敗字元 | 需要 OCR      |
| :---------------------------------- | :------------- | ------: | ---: | ----------: | -----------: | :------------ |
| 高興昌鋼鐵 溫室氣體盤查報告書(2023) | **盤查報告書** | 2.02 MB |   64 |         888 |            0 | 否            |
| 台積電 永續報告書(2024)             | 永續報告書     | 30.3 MB |  278 |       1,035 |            0 | 否            |
| 三星科技 永續報告書(2024)           | 永續報告書     | 17.4 MB |  106 |         791 |            0 | 否            |
| 世德工業 永續報告書(2024)           | 永續報告書     | 13.9 MB |   94 |         422 |    88(0.52%) | 否,但數字失真 |

兩個貫穿全案的事實:

1. **四份都有可用的文字層,沒有一份需要 OCR。** 這推翻了「published PDF 一定要走視覺模型」的預設。
2. **文字層可用 ≠ 文字層可信。** 世德那份 40 頁裡有 88 個字元解不出來,而且**集中在數字上**——原文「民國113年」被抽成「民國███年」。ESG 報告的價值就是數字,這種失真不能無聲放行。

## 三、AI 能力邊界:它負責什麼、不負責什麼

現行 `ReportImportService` 的設計是對的,重點在它**沒有**做什麼:

- LLM 只做「語意定位 + 逐字照抄」:提示詞明寫 `content 逐字照抄原文,嚴禁改寫、摘要、翻譯或補充`,`quantity 原樣照抄為字串,嚴禁換算`。
- `paragraphId` 由 Gemini `responseSchema` 的 `format: "enum"` 鎖死在 33 節 id 內,回傳後 TypeScript 再白名單複驗一次;越界的段落**降級到 `unmapped` 而非丟棄**(使用者看得到 AI 沒放進去的東西)。
- 溫度 0,活動數據的類別與單位同樣以 enum 鎖死,逐筆 Zod 裁決,壞的丟掉好的留下。
- **數字一律不採信**:匯入的量值要重新過確定性引擎與質量守恆勾稽才算數。

換句話說,AI 在這條管線裡是「視力極佳的字串搬運工」,不是分析師。這正是 CLAUDE.md 第 7 條的邊界,也是這個功能能上線的原因。

### 實跑結果(高興昌 64 頁盤查報告,gemini-2.5-pro)

文字層閘門判定 `text`(53,234 字 / 64 頁 / 832 字每頁 / 解碼失敗 0),符合預期。但逐章匯入**前四章全數失敗**,錯誤都是「LLM 輸出無效」——真因不是模型亂回,而是**輸出額度被思考 token 吃光**:

| 章節                  | 輸入 token | 思考 token | 輸出 token | 思考+輸出 | 結果         |
| :-------------------- | ---------: | ---------: | ---------: | --------: | :----------- |
| 第一章 組織與治理概況 |     40,526 |      7,923 |        254 |     8,177 | 截斷         |
| 第二章 報告邊界       |     40,335 |      5,255 |      2,921 |     8,176 | 截斷         |
| 第三章 溫室氣體排放   |     40,535 |      8,189 |      **0** |     8,189 | 完全無輸出   |
| 第四章 數據品質管理   |     40,313 |      2,466 |      5,710 |     8,176 | 截斷         |
| 第五~十一章           |    ~40,200 |      < 700 |     35~314 |     < 900 | **全部成功** |

四筆的「思考+輸出」都精準頂在 8,176~8,189,也就是當時設定的 `maxOutputTokens: 8192`。**thinking 模型的思考 token 與正式輸出共用同一個額度**,而逐字照抄本身就需要大輸出空間,8192 對整章匯入根本不夠;內容較少的後七章因此毫髮無傷。

**決策**:

1. 匯入任務的輸出額度提高到 32,768(`LLM_MAX_OUTPUT_TOKENS.REPORT_IMPORT`;gemini-2.5-pro 上限為 65,536)。
2. `finishReason === MAX_TOKENS` 明確辨識為截斷,拋出專屬錯誤碼 `IS_LLM_OUTPUT_TRUNCATED`(IS000019),與「模型輸出無效」分流——**截斷可靠加大額度或縮小範圍解決,重試有意義;模型亂回重試無意義**。原本兩者混為一談,呼叫端只看到「匯入失敗」而完全沒有方向。

**成本觀察**:每章都重送整份文件,11 章共約 44 萬 input token。逐章切分是為了突破輸出上限,代價是輸入重複 11 次。若要收斂,需引入 context caching 或按章節切分原文,屬後續議題。

### 第二輪實跑(額度 32,768 之後)

| 章節        | 結果                |   耗時 | 說明                                                      |
| :---------- | :------------------ | -----: | :-------------------------------------------------------- |
| 第一章      | **成功,7 節全落地** |  70.8s | 輸出 2,113 + 思考 8,725 = 10,838,遠低於 32,768;unmapped 5 |
| 第二章      | 逾時                | 120.0s | 撞上 `LLM_EXTRACTION_TIMEOUT_MS = 120_000`                |
| 第三章      | 失敗                |  71.0s | 原因不明(log 只印 `{}`)                                   |
| 第四~八章   | 失敗                |   ~10s | 整齊的 10 秒 → 重試後放棄的形狀                           |
| 第九~十一章 | 失敗                | 6~18ms | **完全沒有發出網路請求** → 額度耗盡的典型級聯             |

三個獨立結論:

1. **額度修正有效**:第一章從 0 節變成 7 節全落地(思考 8,725 + 輸出 2,113,原本 8,192 根本裝不下)。
2. **瓶頸移到逾時**:額度放寬讓模型有空間完整照抄,單章耗時從 ~53s 拉長到 ~71s,第二章直接撞 120s。→ 匯入改用專屬逾時 `LLM_REPORT_IMPORT_TIMEOUT_MS = 240_000`。
3. **然後撞上 API 額度**:11 章各重送整份文件 = 每分鐘數十萬 input token,後段章節在毫秒內失敗(沒發請求)。這是**輸入量**的問題,不是輸出。

**最關鍵的發現不是上面三點,而是「我們看不到原因」**:`logger.error(...JSON.stringify(error))` 對 Error 實例永遠印出 `{}`(message/stack 皆為不可列舉屬性)。第三章失敗至今仍不知原因。

**決策**:

1. 新增 `describeError()`(`src/lib/utils/error_message.ts`):展開 name/message、Gemini SDK 的 `status`/`statusText`/`errorDetails`、巢狀 `cause`。專案內另有 28 處 `JSON.stringify(error)` 同病,列為後續清理。
2. 匯入失敗改**四路分流**:截斷 → `IS_LLM_OUTPUT_TRUNCATED`、逾時 → `IS_LLM_TIMEOUT`、額度 → `IS_LLM_QUOTA_EXCEEDED`、其餘 → `IS_REPORT_IMPORT_FAILED`。三者的正確處置完全不同(加大額度 / 等一下 / 縮小範圍),混為一談等於沒有錯誤處理。

## 三之二、已實作:頁碼索引兩階段(輸入量收斂)

**問題**:逐章匯入為了突破輸出上限而拆成 11 次呼叫,但每次都重送整份文件——實測 64 頁報告一次匯入約 44 萬 input token,後段章節因 API 額度耗盡在 6~18ms 內失敗(根本沒發出請求)。278 頁的台積只會更糟。

**決策**:兩階段。

1. **第一階段(索引)**:一次呼叫,問「33 節各自起始於第幾頁」。文字層抽取已在每頁尾植入 `-- p.N/總頁 --` 標記,模型只需回頁碼,**輸出僅 33 個整數**。
2. **第二階段(切片)**:每章取該章各節起始頁的 min/max,前後各留 1 頁緩衝,只送這段文字。

輸入量從「整份 × 11」降到「索引 1 次全文 + 每章約 3~8 頁」,估計約降至四分之一。單章變短也順帶緩解逾時。

**護欄(這是本決策的重點)**:切片是**省成本的最佳化,不是正確性的前提**。四種情況一律退回送全文並記錄 `fellBack`:

| 情況                     | 處置                           |
| :----------------------- | :----------------------------- |
| 索引呼叫失敗或輸出不合格 | 回空索引 → 全部章節送全文      |
| 某章有任一節缺索引       | 該章送全文(不用不完整的範圍猜) |
| 文字中找不到頁標記       | 送全文                         |
| 切片結果低於 200 字      | 送全文                         |

理由:寧可多花 token,也不能讓「內容其實在文件裡卻沒被送給模型」變成靜默的資料遺失。索引由 enum 鎖死段落 id,越界者直接丟棄(索引不承載內容,無需進 unmapped)。

**其他評估過的方案**:Gemini context caching 最理想,但現行 SDK `@google/generative-ai@0.24` 不支援,需換 SDK,成本高於本方案;降低前端並行度(2 → 1)只減速率不減總量,64 頁勉強撐過,278 頁必爆。

測試:`src/__tests__/pdf_page_slice.test.ts`,10 項,涵蓋頁數切分、末頁無標記、邊界夾取、範圍顛倒、無標記、切片過短。

**尚未驗證的部分**:逐字照抄的實際失真率。實測工具已備好(`scripts/probe_report_import.ts`,會把回傳內容切 12 字視窗回比原文算命中率),但沙箱環境連不到 `generativelanguage.googleapis.com`,**需要在本機執行**:

```bash
pdftotext 高興昌鋼鐵股份有限公司溫室氣體盤查報告書.pdf /tmp/inv.txt
npx tsx scripts/probe_report_import.ts <pdf 路徑> /tmp/inv.txt
# 結果寫到 /tmp/report_import_probe.json
```

## 四、已實作:文字層優先 + 品質閘門(第 1 階段)

**原本的問題**:`import/route.ts` 對 PDF 一律 `buffer.toString("base64")` 送 Gemini inlineData,並在超過 14 MB 時直接 `VA_FILE_TOO_LARGE`。實測四份報告有兩份(台積 30.3 MB、三星 17.4 MB)**根本進不了系統**,而且沒有任何降級路徑。

**改法**(`src/lib/pdf_text_layer.ts` + `src/constants/pdf_text_layer.ts`):

1. 先抽文字層,計算品質指標:字/頁、解碼失敗字元率、**數值鄰接的解碼失敗數**。
2. 乾淨 → 送純文字(`isText: true`)。順帶解除 14 MB 限制,且 token 成本遠低於 inlineData。
3. 不乾淨 → 退回原檔走視覺模型。
4. 兩條路都不通(文字層不可信 + 原檔超過視覺上限)→ 明確拒收,不放行失真數據。

**門檻與其理由**(全部取自上表實測值):

| 門檻               | 值    | 理由                                               |
| :----------------- | :---- | :------------------------------------------------- |
| 最低字/頁          | 120   | 實測最低的真實報告是 422 字/頁;低於 120 視為掃描件 |
| 解碼失敗率上限     | 0.2%  | 世德是 0.52%,足以讓整份數據不可用                  |
| 數值鄰接失敗數上限 | **0** | 一個落在數字上的失真就足以汙染排放量,零容忍        |

「數值鄰接」以**連續失敗字元段**為單位判定而非逐字——「民國113年」整串數字會被抽成一段連續替換字元,只有頭尾鄰接得到數量語彙,逐字判定會漏算中間那幾個。

**閘門對四份真實報告的裁決**:

| 報告                    | 原本     | 現在                        |
| :---------------------- | :------- | :-------------------------- |
| 高興昌 盤查報告 2.02 MB | 視覺模型 | **純文字**                  |
| 台積 永續 30.3 MB       | **拒收** | **純文字**                  |
| 三星 永續 17.4 MB       | **拒收** | **純文字**                  |
| 世德 永續 13.9 MB       | 視覺模型 | 視覺模型(數值失真,正確退回) |

測試:`src/__tests__/pdf_text_layer.test.ts`,10 項,涵蓋掃描件、數值失真、非數值雜訊、無視覺降級可用時的明確拒絕。

**降級不得靜默**:實跑高興昌那份(上表判定應為「純文字」)時,伺服端記的是 `"decision":"vision","reason":"text_layer_unavailable","charsPerPage":0` ——文字層**連抽都抽不出來**,而 `extractPdfTextLayer` 的 `catch { return null }` 把原因整個吃掉了。後果不只是多花 token:

|                | 文字層               | 視覺降級                               |
| :------------- | :------------------- | :------------------------------------- |
| 內容忠實度     | 逐字照抄             | AI 改寫(實測 1.1 節 23 條沿革全數消失) |
| 頁碼索引兩階段 | 生效                 | **失效**(切片需要文字層的頁標記)       |
| 表格欄位歸屬   | `cellSeparator` 保留 | 依賴模型自行判讀                       |

差異這麼大的分岔,理由不能只是一個代碼字串。已改為 `logger.error` + `describeError` 記下真正的例外。

**成因定位(2026-07-31 更新)**:先前記載「pdfjs legacy build 會讓 Node core dump」是**歸因錯誤**,已更正。逐段隔離後,崩潰來自 `@napi-rs/canvas` 這個原生綁定本身:

| 條件                                                                      | 結果                                                                   |
| :------------------------------------------------------------------------ | :--------------------------------------------------------------------- |
| `import("@napi-rs/canvas")` 單獨載入                                      | **SIGBUS(core dump)**                                                  |
| pdfjs legacy build,`@napi-rs/canvas` 可解析                               | SIGBUS(pdfjs 會去載它)                                                 |
| pdfjs legacy build,`@napi-rs/canvas` 不存在                               | `ReferenceError: DOMMatrix is not defined`(模組頂層 `new DOMMatrix()`) |
| pdfjs legacy build,無 canvas + 自備 10 行 DOMMatrix/ImageData/Path2D stub | **成功**:64 頁 / 52,148 字 / 815 字每頁                                |

關鍵在於 pdfjs 的 Node 分支**無條件** `require("@napi-rs/canvas")`,而且是在檢查 `globalThis.DOMMatrix` **之前**——所以預先塞 polyfill 也躲不掉,只要這個套件裝著就會被載入(原始碼見 `pdfjs-dist/legacy/build/pdf.mjs` 的 `node_utils.js` 區段)。

推論出的設計問題比環境問題更重要:**純文字抽取根本不需要繪圖能力,卻被一個原生綁定擋在門外**。最後一列證明只要繞開 canvas,同一份 pdfjs 就能完整抽出這份報告的文字層,且數值與 `pdftotext` 交叉驗證一致。

已採取:(1) 失敗原因改為 `logger.error` + `describeError`;(2) `pdf-parse` 加入 `serverExternalPackages`(它動態載入 pdfjs 與原生 `.node`,被 bundler 處理過即失效);(3) 新增 `scripts/probe_pdf_text_layer.ts`,在 Next 之外逐段走同一條載入鏈,一次跑完即可分辨「原生綁定掛掉 / 打包破壞動態載入 / 這份檔案真的沒有文字層」——三者的修法完全不同。本機跑一次即可定案;若確認是原生綁定,則應改用不含原生依賴的抽取器(如 `unpdf` 的 serverless pdfjs build),而不是在 canvas 上繼續投資。

## 四之二、已實作:數據段落不得繞過決定論引擎

**問題**:`applyPendingImport` 以 `content: imported` 直接寫入,不像 AI 草稿路徑會先 `stripLlmTables()` 再 `injectDataTable(computedLedger)`。後果是原報告的「溫室氣體排放總量統計表」原封不動落地,而且因為它沒有 `<!-- carbon-data-table -->` 錨點,ledger 重算時 `hasInjectedDataTable()` 判定為 false,於是**永遠不會被刷新、也不會被標示**。最終產出的報告裡會有一張不是本系統算出來的排放總量表,而讀報告的人分辨不出來——這違反「所有計算收斂到確定性規則引擎」(CLAUDE.md 第 7 條)。

**決策**:匯入落地時,`isDataDriven` 的三個段落(3.4 計算細節、3.6 總量匯總、4.2 不確定性)一律 `stripLlmTables` + `injectDataTable`,敘述文字保留逐字照抄,表格改掛決定論引擎產出。原報告的數字並未消失:它們仍在匯入預覽與 `unmapped` 中可見,且原文件本身就是佐證附件。

## 四之三、已實作:結構圖(不依賴 ledger 的圖表)

**問題**:匯入完成的報告**一張圖都沒有**。現行 4 張圖表模板(範疇圓餅、範疇長條、排放源明細表、碳流量桑基)全部由 `computedLedger` 產值,而 ledger 是空的——因為活動數據萃取掛在第一章,數據卻在第三章(見下方修復)。即使修好,在使用者補齊活動數據之前,敘述章節依舊全是文字牆。

**觀察**:盤查報告的敘述本身就有大量結構性素材。以高興昌那份為例:治理架構四層(主任委員→副主任委員→管理代表→執行秘書)、範疇一/二/三與類別的對應、量化算式(活動數據 × 排放係數 × GWP = CO2e)。這些圖**不需要任何數值**。

**決策**:新增「結構圖」模板,與數據圖表分開命名空間(`carbon-diagram` vs `carbon-chart`),三張:

| 模板                                | 掛載段落 | 渲染         | 節點上限 |
| :---------------------------------- | :------- | :----------- | -------: |
| `MILESTONE_TIMELINE` 經營沿革時間軸 | 1.1      | timeline     |       30 |
| `GOVERNANCE_TREE` 治理架構          | 1.4      | flowchart TD |       12 |
| `BOUNDARY_MAP` 組織邊界             | 1.5      | flowchart TD |       12 |
| `SCOPE_CATEGORY_MAP` 範疇類別對應   | 2.3      | flowchart LR |       24 |
| `QUANTIFICATION_FLOW` 量化流程      | 3.3      | flowchart LR |       10 |

**timeline 的 parent 語意與樹不同**,這點必須明示於模板設定(`renderer`),否則會用樹的規則去驗證一條時間軸,把正確的輸入判成錯的:

|                      | flowchart  | timeline                  |
| :------------------- | :--------- | :------------------------ |
| `parent` 是什麼      | 另一個節點 | 時間標籤(如 `1966年01月`) |
| 必須存在於同批節點內 | 是         | 否                        |
| 檢查成環             | 是         | 不適用                    |
| 需回溯原文           | 是         | **是**(不可自行補年月)    |

時間軸另有兩個決定:同一時間標籤的多個事件併為一列;沒有時間標籤的事件**不丟棄**,歸入「未標註時間」——不猜時間,也不讓事件消失。事件文字內的冒號會換成連字號,否則會撐破 timeline 的分隔語法。

**生成方式(這是與鐵律的交界)**:LLM 只回「節點文字 + 父節點文字」,**mermaid 語法一律由 `carbon_report_diagram.builder` 組出**,模型不接觸語法也不決定畫哪張圖(模板由段落 id 決定,請求端無從指定)。

**核心護欄:節點文字必須能在該段原文中找到**(去空白與標點後比對),找不到即**整張不畫**。另有四道:節點數上限、單一 label 40 字上限、父節點必須存在於同批節點內、層級不得成環。

為什麼不「丟掉壞節點、留下好節點」:父子關係一旦少了中間層,剩下的圖會呈現一個原文裡並不存在的層級結構——**那比不畫更糟,因為它看起來是對的**。

驗證未過時輸出說明文字而非靜默略過:沉默地少一張圖,查核者不會知道發生過什麼。被拒的節點文字寫進 log,才有調整提示詞的依據。

測試:`src/__tests__/carbon_report_diagram.test.ts`,16 項,涵蓋原文回溯(含容忍斷行/標點)、捏造節點、過長 label、超量節點、未知父節點、環狀關係、mermaid 逸出、原地替換不疊加。

**渲染端缺口(實測才發現)**:產生器測試全綠、mermaid 文法也驗證無誤,但 timeline 在畫面上一律顯示 `Mermaid Syntax Error`。原因在前端而非產生器——`mermaid_chart.tsx` 於 render 前先以 `detectChartType()` 過濾以防 `UnknownDiagramError`,而 `MermaidChartType` 清單裡**沒有 timeline**,合法的圖被判為未知型別,`mermaid.render` 從未被呼叫。已補 `TIMELINE` 型別與偵測。

教訓:產生器的單元測試無論多完整,都測不到「產出物能否被渲染端接受」。已在 `carbon_report_diagram.test.ts` 補上跨越這條界線的測試——取出 mermaid 圍籬內的定義字串,斷言 `detectChartType()` 不回 `UNKNOWN`。任何新增渲染型別都會被這組測試擋住。

**附帶修復**:活動數據萃取原本掛在 `index === 0`(第一章 組織與治理概況),但用電量、油耗在第三章;而該次呼叫的範圍規則又明寫「與範圍無關的內容一律忽略」,兩條指令互相拉扯 → ledger 永遠是空的 → 4 張數據圖表與 3 張數據表格全部顯示佔位。改掛 `CARBON_EVIDENCE_CHAPTER_ID`。
