## 1. 需求與現況

> 因為點數不足而中斷的任務，在額度補回時要通知使用者。

今天唯一會走到這個情境的是**智能溫盤的匯入報告**（`JOB_TYPE.CARBON_REPORT_IMPORT`）：
逐章匯入、每章一次 LLM 呼叫各自計費。#6713 的起因是一個真實事故 ——
64 頁的報告匯入到一半點數用完。

狀態機在 #6712／#6714 就備好了，缺的是最後一哩：

| 元件                                                                              | 狀態                                          |
| --------------------------------------------------------------------------------- | --------------------------------------------- |
| `ResumableJob` 表（`@@unique([resourceKey, type])`、`@@index([userId, status])`） | 已有                                          |
| `PAUSED` / `RESUMABLE` 兩個狀態                                                   | 已有                                          |
| `scanResumableJobs`（每 5 分鐘、一輪 50 筆，掛在 `run_worker.ts`）                | 已有，只管團隊額度                            |
| `markResumable()`（條件更新，真的翻面才回 `true`）                                | 已有                                          |
| 個人點數的翻面                                                                    | **本 PR 新增**（`releasePaymentBlockedJobs`） |
| 告訴使用者                                                                        | **本 PR 新增**（`JOB_RESUMABLE`）             |

`RESUMABLE` 這個狀態存在的理由，常數註解自己說了：「為了讓『可以繼續了』這件事
有一個**明確的時點**」。那個時點就是通知的發射點 —— 不是硬塞一個 hook，
是把一個已經被刻意標記出來的時刻接上一個已經存在的出口。

在此之前唯一讀得到它的是 `GET /v1/user/job`，**只在碳盤查頁面載入時打一次**。
而使用者點數用完之後最可能做的事就是關掉分頁。

## 2. 伺服器不可能替他繼續，這決定了文案與型別

報告內容是端到端加密的，逐章迴圈跑在**瀏覽器**裡（`use_carbon_chat.ts` 的
`runResumableJob`），伺服器沒有金鑰。`scanResumableJobs` 只翻狀態，
**不執行也不可能執行**任何工作。

所以使用者實際要做三件事：

1. 回到那個聊天室 —— 由通知的深連結代勞（§5）
2. 按「**接著匯入**」（畫面上的字就是這四個）
3. **換過裝置或重新整理過的話，還要重新上傳同一份原始檔案**

第 3 點是真的：暫停清單存在 `CarbonPendingImport`（跟著帳號走），
但原始檔案只在 `lastImportSourceRef` —— 記憶體裡。

**兩個結論**：文案只能說「可以繼續了」，不能說「已為你繼續」；
而通知的職責是把人**放在能動手的地方**，不是報告發生了什麼。

## 3. 型別：待辦型、活算、抵達鍵取 `updatedAt`

待辦區原本有兩個來源：邀請（活算）與錢包升級（入庫）。這裡加第三個，用活算。

**為什麼活算**：`ResumableJob.status` 本身就是活狀態。按「繼續」轉 `RUNNING`、
取消轉 `CANCELLED`，兩種情況那則通知都該同步消失 —— 與邀請同一個形狀。

**為什麼不入庫**：同一個 `resourceKey` 會暫停 → 繼續 → 再暫停。入庫的話
`dedupeKey` 是永久唯一鍵，第二次就發不出來。要修得把 `activeUnreadKey`
（ADR 025 §5.1）要回來，而那是為「來源不是活狀態」設計的，這裡不是。

**抵達鍵取 `updatedAt`（這一次翻面）而不是 `createdAt`（開始匯入）**：
用後者的話，同一份匯入的兩次「可以繼續」會算出同一個 `arrivalKey`，
第二次**搖而不響、且此後永久靜音**（`ChimeGate` 的 `seenKeys` 沒有 reset）——
正是 D17 的形狀。這一條有獨立的測試，因為改成 `createdAt` 之後其他測試照樣綠。

**代價：摘要從兩趟 DB 變三趟。** 查詢本身索引撐得住（`@@index([userId, status])`、
只撈 `RESUMABLE`、`take` 有上限），但「多一趟」要乘上在線人數。
通知模組計畫書 §6 說效能從來沒量過 —— 這是該量的時機（未做，見 landing 文件 §8）。

## 4. 兩條觸發路徑，機制不同

|                              | 觸發          | 落點                                                     |
| ---------------------------- | ------------- | -------------------------------------------------------- |
| 團隊額度 `CREDITS_EXHAUSTED` | 每 5 分鐘輪詢 | `scanResumableJobs` → `markResumable`                    |
| 個人點數 `PAYMENT_REQUIRED`  | 付款到帳      | `order.tracker.service.ts` → `releasePaymentBlockedJobs` |

### 4.1 團隊額度：0 行改動

活算讓**翻成 `RESUMABLE` 這件事本身就是通知** —— 小鈴鐺下一次輪詢從
`listResumableByUser` 讀到它就出現了。`scanResumableJobs` 不需要、也不該呼叫
任何發射函式，與 `team_invitation.service` 從來不「發射」邀請是同一件事。

> 這一節原本寫著「`markResumable` 回 `true` 之後發通知」，那是把活算當成事件型在想。
> **活算沒有「發射」這個動作**，所以「誰要呼叫它」是個假問題。

### 4.2 個人點數：事件驅動，不要輪詢

掃描刻意跳過 `PAYMENT_REQUIRED`，兩層理由都仍然成立：

1. **判斷不出來**：個人點數在鏈上，要問就得發 RPC。一輪 50 筆、每 5 分鐘一次。
2. **就算查得出來也不該翻**：那個暫停原因不是「餘額不夠」，是「這筆錢需要你簽章」。

所以這條路是事件驅動：`TxTracker` 把訂單標成 `PAID` 的那一刻呼叫
`releasePaymentBlockedJobs`。一次付款配一次 DB 查詢，零額外 RPC，比輪詢更即時。

三個附帶的決定：

- **翻面前不再確認一次餘額**：先檢查會出現「檢查說夠、扣款說不夠」兩個答案，
  而使用者只會相信後者。付款確認過就翻面，夠不夠讓實際扣款說了算。
- **只翻這筆付款對應的那一份**（review #6732 的 1-A）：`ensurePersonalCreditCharge`
  把 `channel` 寫進 `Order.data.resourceKey`，釋放時以 `(userId, resourceKey)` 查。
  取不到就什麼都不翻（fail-closed）。**原本只以 `userId` 為條件** ——
  那等於把「這個人付了款」當成「他所有等付款的任務都付過了」，
  而其中只有一筆是真的付過的，其餘按下去會再撞 402，下一筆付款又把它們全部翻一次。
- **邏輯放在 `TxTracker` 外面**：那支服務 import `publicClient` 與 `viem`，
  沒有測試檔也不好加。它只把 `userId` 與整包 `order.data` 遞出去，判斷在服務層。

**放寬後的界**（review #6732 R4）：`runBilledCarbonTask` 對所有碳盤查任務
（對話、草稿、結構圖、匯入）都傳同一個 `channel`，而 `resourceKey` 就是它。所以

> 現在最多能發生的壞事 = **同一個會話內任何一筆個人付款，都會翻面該會話的匯入任務**。

在會話 X 付了一則對話的錢（5 點），X 裡那份要 50 點的匯入也會被翻成 `RESUMABLE`，
按下去再撞一次 402。比修正前窄非常多（限同一會話，不再是這個人的全部），
而且文案已經不宣稱原因，所以留著。

要再收斂的話，下一格**不是**比對消費類別（20260902 更正，review #6732 R3 二輪）：
`Order.data.category` 確實取自 `featureCode`，但 `runBilledCarbonTask` 的
**五個呼叫端一個都沒傳**，全吃預設值 —— 那個鑑別子今天恆為同一個值，
照著寫會得到一個永遠 false 的條件，而釋放路徑的失敗是靜默的。

真正的下一格是二選一：**讓那五個呼叫端各自傳出自己的 `featureCode`**
（然後才輪得到比對類別），或在 402 建單時把 `jobId` 一起寫進 `Order.data`
（更直接：不必推導，付的就是那一份）。同一個事實也讓部署檢查表的驗證 ⑥
改成從任務那一側查。

## 5. 去處：深連結到那一個會話

`/user/carbon_chatbot?session=:sessionId&openImport=1`。

> 這一節原本是頁面層級的 `/user/carbon_chatbot`，理由是那一頁當時不吃 searchParams，
> 深連結被判斷成「不夠精準，另開一項」。**實測推翻了那個判斷**：落地之後使用者
> 要自己走四層才找得到能按的東西，而通知說的那顆按鈕根本不存在。
> 深連結因此不是精準度的優化，是這則通知能不能兌現的前提。

當時做對的一件事是 **payload 帶著 `resourceKey`**：`sessionId` 直接從它切得出來
（`parseCarbonChatChannel`），不必回頭改資料。切不出來時那個鍵不存在，
`resolvePathTokens` 讓整條回 `null`，那一則渲染成不可點 —— 比帶去錯的地方好。

實作細節與踩到的兩道陷阱見 landing 文件 §2。

## 6. 實測發現：翻面的判準只看訂閱視窗額度

實測卡在「補了點數卻沒有通知」，追下去發現接線是好的，錯的是這份文件
對「點數補回」的理解。

### 6.1 那一次 `stillShort` 的追查

測試帳號：免費方案、全隊共用池、`0/14`、`CREDITS_EXHAUSTED`、`next_step_cost` 為 null。

```
resumable job scan finished {"scanned":1,"released":0,"stillShort":1,"unknown":0}
```

`stillShort` 這一格本身就排掉一半的可能：能走到它，代表那一列存在、
`pauseReason` 是 `CREDITS_EXHAUSTED`、`teamId` 不是 null、`type` 查得到扣點模式 ——
它一路走到 `canResumeNow()` 才被判否。實際的數字：

|            | limit | used | remaining |
| ---------- | ----- | ---- | --------- |
| 5 小時視窗 | 10    | 47   | 0         |
| 每週視窗   | 40    | 47   | 0         |

`resolveQuotaAvailable` 取兩者的**較小值**，所以 5 小時視窗重置也不會翻面 ——
要等三天後的週視窗。**「等重置」不是一個時刻，是兩個視窗中較晚的那一個。**

（`used 47 > limit 40` 不是資料錯亂：預扣封頂後實耗大於預扣，差額按設計記回額度；
免費方案又是全隊共用一份，那 47 點是整隊所有功能的用量。）

### 6.2 「加購點數」是一條不存在的出路

§1 曾把「等重置／加購點數／升級方案」並列。前後兩條成立，中間那條不成立：

- `canResumeNow()` 的 `chainCredits` 是**字面量 0**；
- 加購的點數在 ADR 015 之後鑄到成員錢包，正是 `isChainCreditSpendable()` 回 false 時
  扣不動、一律讀成 0 的那一筆；
- 加購也不會改變 `per5h` / `perWeek` —— 那兩個值只來自方案。

**不要單獨修 `canResumeNow`。** 讓它把鏈上餘額算進去，任務會翻成「可以繼續」，
而使用者按下去撞的是 `spendCredits` 的同一道 402 —— 那正是兩邊共用判準要防的
「說可以繼續、按下去又撞牆」。兩邊必須同時改，前提是第二層扣款恢復
（走 `ensurePersonalCreditCharge()` 的持有人簽章路徑，不是已停用的平台側 burn）。

**釘子已補**（`spend_second_layer_inert.test.ts` 的 D 類）：兩邊今天一致是因為
**都是 0**，那是巧合不是機制。旗標一翻成 true，那一條就會紅並指向該一起改的行。

### 6.3 附帶發現

- `subscriptionPlanQuotaRepo.upsertQuota()` **沒有任何呼叫端**（註解寫「後台調整額度用」，
  但 `src/app` 與 `src/components` 都搜不到）。今天要調方案額度只能直接下 SQL。
- 實測要製造「額度回來了」，最實際的做法就是調大 `subscription_plan_quota` 那一列 ——
  走的仍是完整的真實路徑：掃描 → `canResumeNow` → `markResumable` → 活算通知。

## 7. 驗收現況

| 判準                                                                      | 狀態                                             |
| ------------------------------------------------------------------------- | ------------------------------------------------ |
| 可繼續的任務進待辦節、帶得出進度                                          | 自動化測試                                       |
| 算進 `todoCount`、不算進 `completedCount`                                 | 自動化測試                                       |
| 超過清單上限時徽章仍數得出全部（`summarizeResumable`，#6742）             | 自動化測試                                       |
| 超過清單上限時清單截斷、且畫面說得出來（`hasMoreTodos` → `todos_capped`） | 自動化測試（含接線掃描）                         |
| 抵達時間取 `updatedAt` 而非 `createdAt`                                   | 自動化測試（單獨一條，見 §3）                    |
| 沒有可繼續的任務時，摘要與清單不受影響                                    | 自動化測試                                       |
| `releasePaymentBlockedJobs`：只翻這筆付款對應的那一份、翻不動的不算       | 自動化測試                                       |
| 兩支讀取查詢都帶 `userId`（跨租戶守門）                                   | 自動化測試（`resumable_job_read_scope.test.ts`） |
| TxTracker 每個標 `PAID` 的分支都接了釋放、都包 `try`、都帶 `order.data`   | 掃描測試                                         |
| 團隊額度視窗重置或方案升級後，鈴鐺出現那一則                              | **20260828 實機通過**                            |
| 其餘實機項目                                                              | **未完成**，清單見 landing 文件 §8               |

> **掃描測試證明不了的那一項**：真的付款時 `TxTracker` 到底有沒有走到
> `releasePaymentBlockedJobs`。那要在跑得動鏈上流程的環境真的付一次款 ——
> 不要用掃描的綠燈把它打勾。

## 8. 不要做的事（記下取捨，免得下次重提）

- **不要把 `PAYMENT_REQUIRED` 加進 `scanResumableJobs`** —— 見 §4.2 的兩層理由。
- **不要在翻面前查鏈上餘額** —— 一輪 50 筆 RPC，而且會製造「檢查說夠、扣款說不夠」。
- **不要入庫成事件型** —— 同一個任務會反覆暫停，永久 `dedupeKey` 擋掉第二次。
- **不要讓通知宣稱任務會自己繼續** —— 端到端加密，伺服器沒有金鑰，做不到。
- **不要讓通知宣稱翻面的原因** —— 兩條路共用一句，而「額度已恢復」對付款那條是假的。
  要分辨得先做 `resumedBy`（landing 文件 §5）。

**把活算的來源當成事件型在想**：

| 原本寫的                                   | 實際                                                          |
| ------------------------------------------ | ------------------------------------------------------------- |
| §4.1「`markResumable` 回 `true` 後發通知」 | 團隊路徑 **0 行改動** —— 活算讓翻面本身就是通知               |

活算沒有「發射」這個動作，所以「誰要呼叫它」是假問題；真正該問的是
**「誰 import 了新東西」**。

其餘實作決定：圖示用 `play` 不沿用 `check`（`check` 說「做完了」，這一則說
「可以開始了」，16px 下長得一樣的話使用者會以為匯入完成而不去按）；
TxTracker 的接線包在 `try/catch` 裡（訂單已標 `PAID`，這一步失敗不該讓整輪追蹤中止，
那會讓後面的訂單也停在 `PENDING`）。
