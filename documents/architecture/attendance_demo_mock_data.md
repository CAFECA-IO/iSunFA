## 📋 0. 設計原則

### 0.1 對工程機關而言，這套系統回答三個問題

| 問題                           | 對應功能                  | 為什麼在意                                               |
| ------------------------------ | ------------------------- | -------------------------------------------------------- |
| **今天工地上有幾個人、是誰？** | 現場人數與名單（P3）      | 出工查核；承包商回報人數與實際到工不符是公共工程的老問題 |
| **有人回報出工但實際沒到嗎？** | 曠職判定 + 未到工（P5）   | 排了班卻無打卡＝系統自己抓出來的差異，不必人工比對       |
| **出事的時候，工區裡還有誰？** | 現場名單 + CSV 匯出（P3） | 工安事故的第一個問題就是這個                             |

因此本份資料**刻意佈置成「有東西可以抓」** —— **一份全部正常的資料無法證明系統會抓異常。**

### 0.2 資料的真假界線

| 項目                       | 真 / 假                                                |
| -------------------------- | ------------------------------------------------------ |
| 機關名稱、工程名稱、工務所 | **虛構**，不使用任何實際標案名稱                       |
| 人名、工號、電話           | **虛構**（電話一律 `0912-000-0XX`，明顯可辨識為假）    |
| **身分證字號**             | **完全不建立** —— 假號碼無論通不通過檢查碼驗證都是問題 |
| 工地座標                   | **LOC-A 必須實測**，其餘用地圖標註值（§3.1）           |
| 上台演示者的 email         | **必須是真實的公司 Google 帳號**（§4.2）               |

> **Demo 環境不得匯入任何真實員工個資。** 除上台者本人的 email 外全部虛構。

| code     | name                           | 類型     | 緯度        | 經度        | 半徑    | 座標來源               |
| -------- | ------------------------------ | -------- | ----------- | ----------- | ------- | ---------------------- |

| `LOC-A`  | **大漢溪橋梁改建工程 工區**    | 點狀     | ⚠️ **實測** | ⚠️ **實測** | **500** | **演示現場，必須校準** |
| `LOC-B`  | 台北港聯外道路拓寬工程（八里） | **線形** | `25.1550`   | `121.3750`  | **800** | 地圖標註值             |
| `LOC-C`  | 林口污水管線工程（林口）       | **線形** | `25.0776`   | `121.3800`  | **800** | 地圖標註值             |

### 2.1 為什麼只有 `LOC-A` 要實測

其餘三處演示中不會有人在那裡打卡，只負責出現在地圖上與當分組依據，精度無所謂。

`LOC-A` 是唯一會被真人打卡的地點，而地圖標註值在這裡**不是精度問題，是系統性偏移**：

- 地圖標的是建物中心或門牌位置，演示時人站在某層樓的某個房間
- 室內定位主要靠 Wi-Fi 輔助，**同一台裝置在同一位置會穩定偏向某個方向**，不是隨機誤差
- 兩者疊加：標註點偏 200 公尺 + 室內偏移 150 公尺 = 500 公尺圍欄只剩 150 公尺餘裕

**完整校準程序見執行手冊 §3。** 一句話：用**當天那台裝置、站在要站的位置**取樣 5 次，**取中位數**
（不是平均 —— GPS 偶爾噴離群值，平均會被拉走）。

### 2.2 ⚠️ 圍欄不可重疊 —— seed 必須驗證

打卡命中多個圍欄時取距離最小者。重疊區的歸屬會讓現場人數失真，而**重疊的圍欄不會報錯，只會安靜地算錯**。

```
校準完成後必須驗證：LOC-A 與其餘三處的中心距離 > 各自半徑之和 + 500 m
   LOC-A ↔ LOC-HQ  需 > 1.3 km      ← 最可能撞到的一個
   LOC-A ↔ LOC-B   需 > 1.8 km
   LOC-A ↔ LOC-C   需 > 1.8 km
```

**若演示地點也在板橋一帶**，把 `LOC-HQ` 改到**汐止（`25.0630`, `121.6420`）**。

### 2.3 ⚠️ 圓形圍欄對線形工程不合用 —— 演示時必須主動說明

`LOC-B`（道路）與 `LOC-C`（管線）是**沿線分布**的。一條 3 公里的管線用一個圓涵蓋，半徑得 1.5 公里以上，
而那個圓會把沿線兩側大片與工程無關的區域都算成「在工地」。

- 圓形圍欄適合：辦公室、橋梁工區、廠站等**點狀**設施
- 線形工程需要**沿中心線的帶狀範圍**（PostGIS `ST_DWithin`），不是一個 Haversine 距離比對

母文件把 PostGIS 列為升級路徑，理由是效能。**線形工程是更早也更實質的觸發條件 —— 它不是效能問題，是幾何模型不合用。**

> **建議演示時主動提出。** 工程背景的聽眾幾秒鐘就會想到；由我們先講，展現的是知道邊界在哪；由他們先問，就變成我們沒想到。
> `LOC-B` / `LOC-C` 的 800 公尺是**刻意留下的破綻** —— 足以讓演示跑完，但不足以宣稱線形工程已經解決。

分鐘值為當日 00:00 起算，`≥1440` 表次日。

| ------------ | ------------ | ------------ | --------------------- | --------------- | --------------- | ------ | ---- | ----------- |
| `SITE-DAY`   | 工地日班     | 07:30 (450)  | 17:00 (1020)          | 450             | 1020            | 480    | 60   | `FIXED`     |
| `SITE-NIGHT` | 夜間施工班   | 20:00 (1200) | **次日 05:00 (1740)** | 1200            | 1740            | 450    | 60   | `FIXED`     |
| `ENG-FLEX`   | 工程師彈性班 | 07:00 (420)  | 20:00 (1200)          | **10:00 (600)** | **16:00 (960)** | 480    | 60   | `FLEXIBLE`  |
| `OFFICE-98`  | 本部行政班   | 09:00 (540)  | **18:30 (1110)**      | 540             | 1110            | 480    | 60   | `FIXED`     |

| 班別         | 演示用途                                                            |
| ------------ | ------------------------------------------------------------------- |
| `SITE-DAY`   | 工地主力；遲到／早退／曠職的舞台                                    |
| `SITE-NIGHT` | **跨日班** —— 證明 `workDate` 歸屬正確；也是演示當日 `STALE` 的來源 |
| `ENG-FLEX`   | **P4 的對照組** —— 與 `OFFICE-98` 同日同分鐘打卡，結論相反          |
| `OFFICE-98`  | P4 的另一半                                                         |

### 3.1 三個刻意設計的數值（其中一個是踩雷後改的）

0. **⚠️ `OFFICE-98` 由 09:00–18:00 改為 09:00–18:30。**
   原設定窗長 540 扣休息 60 = 480，**與應工作分鐘完全相等 → 餘裕為零**，
   於是任何一分鐘的遲到都會同時觸發 `INSUFFICIENT_HOURS`。
   **這是寫判定引擎測試時才發現的**：在「窗＝核心」的嚴格固定班下，
   遲到必然連帶造成工時不足，除非應工作分鐘 <（窗長 − 休息）。
   改為 18:30 後三種固定班一致有 30 分鐘餘裕。
1. **`SITE-DAY` 有 30 分鐘緩衝**（窗長 570 − 休息 60 = 510 實工 vs 應工作 480）。
   因此遲到 20 分只觸發 `LATE`，遲到 45 分會**同時**觸發 `LATE` 與 `INSUFFICIENT_HOURS` ——
   正好演示「一天可以有多個異常」。
2. **`ENG-FLEX` 的核心起 10:00 比 `OFFICE-98` 的 09:00 晚一小時。**
   09:47 打卡因此在兩種班別下得到相反結論，而中間沒有任何一行程式碼在區分它們。

**兩處例外**：

> ### ⚠️「因雨停工」只能借用 `HOLIDAY` —— 這是本份資料暴露出的 schema 缺口
>
> `WorkDayType` 五個值（`WORK` / `REGULAR_OFF` / `REST_DAY` / `HOLIDAY` / `LEAVE`）**沒有一個對**：
> 因雨、颱風、災害由機關公告停工，它不是例假、不是休息日、不是國定假日，也不是個人請假 ——
> 它是**機關單方面免除當日出勤義務**，而且是工程業的常態而非例外。
>
> 借用 `HOLIDAY` 在 demo 可行（對判定引擎效果相同），但**正式版會讓「今年停工幾天」與
> 「今年國定假日幾天」混在同一個值裡** —— 而前者是工期展延與契約計價的依據，工程機關一定會問。
>
> **正式版應新增 `WorkDayType.SUSPENDED` + `suspensionReason`**（計畫書 §7.3 第 2 順位）。

### 6.1 每筆打卡的其他欄位

| 欄位                                 | 值                                                                                                    |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| `id`                                 | `randomUUID()`（**不可用 `@default(uuid())`** —— 它是 PII 加密 AAD 的一部分，加密發生在 insert 之前） |
| `verification`                       | `GPS`                                                                                                 |
| `workLocationId`                     | 該員工所屬工務所的工地（本部與品管職安室 → `LOC-HQ`）                                                 |
| `latitudeCipher` / `longitudeCipher` | 工地座標加 ±0.0003 度隨機擾動後 `encryptPii()`                                                        |
| `accuracyMeters`                     | 8–45 隨機                                                                                             |
| `distanceMeters`                     | 依擾動後座標實算（明文）                                                                              |

> **座標擾動必須在圍欄半徑內**（±0.0003 度約 ±33 公尺，遠小於最小的 300 公尺半徑）。
> 目的是讓解密後的座標看起來像真實定位而不是同一個點 ——
> **若被問到「這些歷史紀錄的位置在哪」，解密出來要說得通。**
>
> **加密欄位名用 camelCase**（`latitudeCipher`），不是 `latitude_cipher` —— AAD 的 `field` 依既有慣例；
> 寫錯不會在寫入時報錯，會在**讀取時**變成看起來像密文損毀的驗章失敗。
