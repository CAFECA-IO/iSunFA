## 📋 0. 這份資料的設計原則

### 0.1 對工程機關而言，這套系統回答的是三個問題

| 問題 | 對應功能 | 為什麼工程機關在意 |
|---|---|---|
| **今天工地上有幾個人、是誰？** | 現場人數與名單（P3） | 出工查核；承包商回報人數與實際到工不符是公共工程的老問題 |
| **有人回報出工但實際沒到嗎？** | 曠職判定 + 未到工人數（P5） | 排了班卻無打卡＝系統自己抓出來的差異，不必靠人工比對 |
| **出事的時候，工區裡還有誰？** | 現場名單 + 匯出（P3） | 工安事故的第一個問題就是這個 |

因此本份資料**刻意佈置成「有東西可以抓」** —— 一份全部正常的資料無法證明系統會抓異常。

### 0.2 資料的真假界線

| 項目 | 真 / 假 | 說明 |
|---|---|---|
| 機關名稱、工程名稱、工務所 | **虛構** | 不使用任何實際標案名稱 |
| 人名、工號、電話 | **虛構** | 電話一律 `0912-000-0XX` 格式，明顯可辨識為假資料 |
| **身分證字號** | **完全不建立** | `Employee.nationalIdCipher` 是選填，demo 不需要。**不編造身分證字號** —— 假號碼無論通不通過檢查碼驗證都是問題 |
| 工地座標 | **LOC-A 必須實測**，其餘可用地圖標註值 | 見 §4.2 |
| 上台演示者的 email | **必須是真實的公司 Google 帳號** | 見 §6.3 |

> §12.3 已載明：**demo 環境不得匯入任何真實員工個資**。本份資料除上台者本人的 email 外，全部虛構。

## 📍 4. 工作地點（`WorkLocation`）

**全部位於新北市轄區。** 座標為 WGS84 十進位度，`Float` 型別（同既有 `Seaport` / `Airport`）。

| code | name | 類型 | 緯度 | 經度 | `radiusMeters` | 座標來源 |
|---|---|---|---|---|---|---|
| `LOC-HQ` | 工程處本部（板橋） | 辦公室 | `25.0128` | `121.4650` | **300** | 地圖標註值 |
| `LOC-A` | **大漢溪橋梁改建工程 工區** | 點狀工程 | ⚠️ **實測** | ⚠️ **實測** | **500** | **演示現場，必須校準** |
| `LOC-B` | 台北港聯外道路拓寬工程 工區（八里） | **線形工程** | `25.1550` | `121.3750` | **800** | 地圖標註值 |
| `LOC-C` | 林口污水管線工程 工區（林口） | **線形工程** | `25.0776` | `121.3800` | **800** | 地圖標註值 |

### 4.1 為什麼只有 `LOC-A` 要實測

`LOC-HQ` / `LOC-B` / `LOC-C` **演示中不會有人在那裡打卡**，它們只負責兩件事：在地圖上出現、當作名單的分組依據。精度無所謂，地圖標註值足夠。

`LOC-A` 是唯一會被真人打卡的地點，而**地圖標註值在這裡不能用** —— 這不是精度問題，是**系統性偏移**：

- 地圖標的是建物中心或門牌位置，而演示時人站在某一層的某個房間
- 室內定位主要靠 Wi-Fi 輔助，同一台裝置在同一位置會**穩定偏向某個方向**，不是隨機誤差
- 兩者疊加：標註點偏 200 公尺 + 室內偏移 150 公尺 = 500 公尺的圍欄只剩 150 公尺餘裕

**校準的完整作業程序見 `attendance_demo_runbook.md` §3。** 一句話版本：用**演示當天那台裝置、站在演示要站的位置**，讀 `navigator.geolocation` 取 5 次，**取中位數**（不是平均 —— GPS 偶爾噴離群值，平均會被拉走）。

### 4.2 ⚠️ 圍欄不可重疊 —— seed 必須驗證

打卡命中多個圍欄時取「距離最小者」（計畫書 §7.1 第 5 步）。若兩個圍欄重疊，重疊區的歸屬會讓現場人數失真。

上表三個固定地點彼此相距 8–16 公里，遠大於半徑和，**但 `LOC-A` 是實測值，可能落在任何地方**：

```
校準完成後必須驗證：LOC-A 與其餘三處的中心距離 > 各自半徑之和 + 500 m
   LOC-A ↔ LOC-HQ  需 > 1.3 km
   LOC-A ↔ LOC-B   需 > 1.8 km
   LOC-A ↔ LOC-C   需 > 1.8 km
```

**最可能撞到的是 `LOC-HQ`（板橋）** —— 若演示地點也在板橋一帶，兩者會重疊。屆時把 `LOC-HQ` 改到 **汐止（`25.0630`, `121.6420`）**，那裡距板橋約 17 公里，與其餘地點也都夠遠。

> Seed 腳本應把這個檢查寫成執行前的斷言，不合格直接中止 —— 理由同「座標沒設定就中止」：重疊的圍欄不會報錯，只會讓現場人數安靜地算錯。

### 4.3 ⚠️ 圓形圍欄對線形工程是不合適的 —— 這件事必須主動說明

`LOC-B`（道路拓寬）與 `LOC-C`（管線）是**沿線分布**的：一條 3 公里的管線，用一個圓涵蓋它，半徑就得 1.5 公里以上，而那個圓會把沿線兩側大片與工程無關的區域都算成「在工地」。

- 圓形圍欄適合：辦公室、橋梁工區、廠站等**點狀**設施
- 線形工程需要的是**沿線的帶狀範圍**（中心線 + 緩衝距離），那是 PostGIS 的 `ST_DWithin` 而不是一個 Haversine 距離比對

母文件 §13.2 已把「地理圍欄改用 PostGIS」列為升級路徑，但當時的理由是「地點數成長造成的效能瓶頸」。**線形工程是更早、也更實質的觸發條件** —— 它不是效能問題，是幾何模型不合用。

> **建議在演示時主動提出。** 工程背景的聽眾幾秒鐘就會想到這個問題；由我們先講，展現的是知道邊界在哪；由他們先問，就變成我們沒想到。
> 本份資料把`LOC-B` / `LOC-C` 的半徑設為 800 公尺，是**刻意留下的破綻** —— 足以讓演示跑完，但不足以宣稱線形工程已經解決。

| 班別 | 演示用途 |
|---|---|
| `SITE-DAY` | 工地的主力班別；遲到／早退／曠職的舞台 |

### 5.2 三個刻意設計的數值

0. **⚠️ v1.2 修正：`OFFICE-98` 由 09:00–18:00 改為 09:00–18:30。**
   原設定的窗長 540 分扣休息 60 分 = 480 分，**與應工作分鐘完全相等 → 餘裕為零**，
   於是任何一分鐘的遲到都會同時觸發 `INSUFFICIENT_HOURS`。
   這是寫判定引擎測試時才發現的：**在「窗＝核心」的嚴格固定班下，
   遲到必然連帶造成工時不足，除非應工作分鐘小於（窗長 − 休息）。**
   改為 18:30 後三種固定班一致有 30 分鐘餘裕。

1. **`SITE-DAY` 的窗長 570 分、扣休息 60 分 = 510 分實工，應工作 480 分 → 有 30 分鐘緩衝。**
   因此遲到 20 分只觸發 `LATE`；遲到 45 分會**同時**觸發 `LATE` 與 `INSUFFICIENT_HOURS` —— 這正好演示「一天可以有多個異常」（母文件 §4.2 把異常設計成子表而不是單一欄位的理由）。
2. **`SITE-NIGHT` 的窗迄是 1740（次日 05:00）。** 這個超過 1440 的值就是跨日的全部機制 —— 不需要任何特殊欄位或旗標。
3. **`ENG-FLEX` 的核心起 10:00 比 `OFFICE-98` 的 09:00 晚一小時。** 09:47 打卡因此在兩種班別下得到相反結論，而中間沒有任何一行程式碼在區分它們（§8.3）。

> ### ⚠️ 「因雨停工」目前只能借用 `HOLIDAY`，這是本份資料暴露出的 schema 缺口
>
> `WorkDayType` 現有五個值：`WORK` / `REGULAR_OFF`（例假） / `REST_DAY`（休息日） / `HOLIDAY`（國定假日） / `LEAVE`（請假）。
>
> **因雨、颱風、災害而由機關公告停工，五個都不對**：它不是例假、不是休息日、不是國定假日，也不是個人請假 —— 它是**機關單方面免除當日出勤義務**，而且是工程業的常態而非例外。
>
> 借用 `HOLIDAY` 在 demo 可行（兩者對判定引擎的效果相同：不需出勤、有打卡也不算異常），但**在正式版會讓「今年停工幾天」與「今年國定假日幾天」混在同一個值裡** —— 而前者是工期展延與契約計價的依據，工程機關一定會問。
>
> **建議正式版新增 `WorkDayType.SUSPENDED`（停工）**，並在 `EmployeeShiftDay` 加一個 `suspensionReason String?`（因雨／因颱風／因災害／機關指示）。這條列入計畫書 §12.3 的補完清單。

### 8.1 每筆打卡的其他欄位

| 欄位 | 值 |
|---|---|
| `id` | `randomUUID()`（**不可用 `@default(uuid())`** —— 它是 PII 加密 AAD 的一部分，加密發生在 insert 之前） |
| `verification` | `GPS` |
| `workLocationId` | 該員工所屬工務所的工地（本部與品管職安室 → `LOC-HQ`） |
| `latitudeCipher` / `longitudeCipher` | 工地座標加上 ±0.0003 度的隨機擾動後，以 `encryptPii()` 加密 |
| `accuracyMeters` | 8–45 之間的隨機值 |
| `distanceMeters` | 依擾動後座標與圍欄中心實算（明文） |
| `piiKeyVersion` | `HR_PII_CURRENT_KEY_VERSION` |

> **座標擾動要在圍欄半徑內。** ±0.0003 度約 ±33 公尺，遠小於最小的 300 公尺半徑（`LOC-HQ`）。擾動的目的是讓解密後的座標看起來像真實定位而不是同一個點 —— **若被問到「這些歷史紀錄的位置在哪」，解密出來要說得通**。

## 🧾 10. Seed 腳本結構

`scripts/seed/seed_attendance_demo.ts`（不動既有 `seed.ts`）：

```typescript
/**
 * Info: (20260813 - Julian) 工程機關版簽到系統展示資料。
 *
 * 資料規格見 documents/architecture/attendance_demo_mock_data.md。
 * 演示日期寫死在 DEMO_DATE——改期必須改這裡並重跑，因為所有相對日期
 * （歷史打卡、排班、STALE 的夜班）都是從它推算的。
 *
 * 執行前必須設定 HR_PII_KEY_V1，否則 encryptPii 會拋 HrPiiKeyError。
 */
const DEMO_DATE = "2026-08-13";

async function main() {
  await seedAccountBook();      // §1
  await seedDepartments();      // §2（先建部門再回填 managerId，因為互為外鍵）
  await seedJobTitles();        // §3
  await seedWorkLocations();    // §4 —— LOC-A 座標由 env 帶入，強迫實測
  await seedShiftPatterns();    // §5
  await seedEmployees();        // §6 —— phoneCipher 走 encryptPii
  await backfillDepartmentManagers();
  await seedShiftDays();        // §7 —— 依規則產生，兩處例外硬寫
  await seedHistoricalPunches();// §8 —— 先產生正常打卡，再以異常清單覆寫
  await seedTodayPunches();     // §9.2 —— **跳過 EMP005 / EMP006**
}
```

### 10.1 五個實作要點

| # | 要點 | 為什麼 |
|---|---|---|
| 1 | `LOC-A` 座標由 env（`DEMO_SITE_A_LAT` / `_LNG`）帶入，**沒設定就中止** | 逼實測。預設值會被沿用，而沿用的後果是演示當天打不了卡 |
| 2 | 每筆 punch 先 `randomUUID()` 再加密 | AAD 綁定 `AttendancePunch:{id}:{field}:{keyVersion}`（ADR 018 §3） |
| 3 | 加密欄位名用 **camelCase**（`latitudeCipher`），不是 `latitude_cipher` | AAD 的 `field` 依既有慣例；寫錯不會在寫入時報錯，會在**讀取時**變成看起來像密文損毀的驗章失敗 |
| 4 | 排班先產生規則、再套用兩處例外 | 例外硬寫在規則之後覆寫，比在迴圈裡塞 if 好讀，也好改期 |
| 5 | 腳本可重複執行（先依 `accountBookId` 清空本 demo 帳本的相關資料） | 彩排會跑很多次 |

> **要點 5 的清空範圍必須限定在 `demo-book-public-works`。** 一支會清掉整張表的 seed 腳本，遲早會有人在錯的環境跑它。
