## 0. 摘要

原本要做的事是「補上薪資單缺的法定必載欄位：雇主名稱」。

**核對條文之後，那個前提兩邊都不成立：**

- **工資明細**（細則 §14-1）是四款、全是金額、沒有雇主名稱 —— 而薪資單四款都有
- **工資清冊**（本法 §23 II）列舉發放工資、各項目計算方式明細、工資總額
  —— 同樣全是金額，也沒有雇主名稱

所以 **#6795 描述的缺口不存在，這一頁沒有任何法遵依據**。
剩下的理由是實務慣例與「公司資訊無處可存」，兩個都是「有比較好」。
**建議降為產品選項排優先度。**

**但核對過程撞到兩個真的缺口，都排在這一頁之前：**

| 缺口                                                                          | 性質       | 位置 |
| ----------------------------------------------------------------------------- | ---------- | ---- |
| 工資清冊缺特休的**期日**與**未休日數**，且沒有法定的**年度書面通知**（§38 V） | **法遵**   | §2.1 |
| `vacationToPay` 的稅務分類與費率基礎（§38 IV、細則 §24-1）                    | **算錯錢** | §7.1 |

兩者是**同一個欄位**的兩面。

另外要修掉三個檔案裡一句錯誤的法律敘述（§1.3）—— 那句話正是這一頁的起因。

## 1. 先修正前提：§14-1 到底寫什麼

### 1.1 條文原文

> **第 14-1 條**
> 本法第二十三條所定工資各項目計算方式明細，應包括下列事項：
> 一、勞雇雙方議定之工資總額。
> 二、工資各項目之給付金額。
> 三、依法令規定或勞雇雙方約定，得扣除項目之金額。
> 四、實際發給之金額。
>
> 雇主提供之前項明細，得以紙本、電子資料傳輸方式或其他勞工可隨時取得及得
> 列印之資料為之。

**四款，全部是金額。沒有雇主名稱，沒有勞工姓名，也沒有工資給付期間。**

### 1.2 薪資單其實四款都有

| 款  | 內容           | 薪資單上的位置                               |
| --- | -------------- | -------------------------------------------- |
| 一  | 工資總額       | `totalMonthlySalary`（應稅＋免稅合計）       |
| 二  | 各項目給付金額 | 本薪／加班費／津貼／伙食費，應稅與免稅分列   |
| 三  | 得扣除項目金額 | 勞保、健保、二代健保、所得稅、請假扣款、其他 |
| 四  | 實際發給金額   | `totalPayment`（表頭的「實際發放金額」）     |

**所以 §14-1 沒有缺口。** #6795 應該以「案由不成立」關閉，而不是實作。

### 1.3 ⚠️ 三個檔案裡有一句錯誤的法律敘述，必須修

| 檔案                                                          | 內容                                                                                                                 |

| `src/lib/utils/pay_slip_meta.ts:48`                           | 「§14-1 的工資明細六項必載是：雇主名稱、勞工姓名、工資給付期間、工資各項目給付金額、依法扣除項目金額、實際發給金額」 |
| `documents/architecture/salary_record_module_plan.md:221`     | 「薪資單缺雇主名稱（施行細則 §14-1 六項必載只有五項）」                                                              |

三處**互相一致，所以彼此看起來像佐證** —— 而它們是同一段文字複製三次。
這正是 `code_review_checklist §6` 那條原則要處理的情況：
**當事實與條文衝突時，改條文。**

修法：三處都改成四款原文，並在 `pay_slip_meta.ts` 那則註明

只是接在錯的前提後面。

> **這個錯誤怎麼來的值得記一句**：六款列舉裡的「勞工姓名、工資給付期間」
> 不是明細（§14-1）的內容，看起來是實務範本或其他來源混進來的。
> `salary_pay_slip_delivery_plan.md` §513 那張表其實正確地把清冊與明細分開 ——
> 同一份文件裡兩個版本並存。

> 清冊列舉的是發放工資、工資各項目計算方式明細、工資總額，同樣全是金額。）

## 2. 那為什麼還要做這一頁（20260914 更新：**沒有法定理由**）

### 2.0 §23 II 核對結果：清冊也沒有要求雇主名稱

> **第 23 條**
> 工資之給付，除當事人有特別約定或按月預付者外，每月至少定期發給二次，
> 並應提供工資各項目計算方式明細；按件計酬者亦同。
>
> 雇主應置備勞工工資清冊，將**發放工資、工資各項目計算方式明細、工資總額**
> 等事項記入。工資清冊應保存五年。

列舉三項，**全是金額**。「等事項」是開放的，但條文沒有任何一處指名事業單位。

**所以 R1 也不成立。** 明細（§14-1）與清冊（§23 II）兩邊都查過了，
**雇主名稱在兩邊都不是法定必載**。這一頁沒有法遵依據。

原本的三個案由現在只剩兩個軟的：

| #      | 理由                                                                                                    | 強度                |
| ------ | ------------------------------------------------------------------------------------------------------- | ------------------- |
| ~~R1~~ | ~~工資清冊沒有雇主識別~~                                                                                | **已否證**（§2.0）  |
| R2     | 薪資單上有公司抬頭是實務慣例，員工與勞檢都預期看到                                                      | 中                  |
| R3     | 公司資訊（統編、地址、負責人）目前無處可存，報表抬頭等日後也要用                                        | 中                  |
| **R4** | **「特休年度制度」是事業單位層級的法定選擇**（細則 §24 II 三選一），而它是 §38 V 年度通知算得出來的前提 | **實質**（見 §2.1） |

R2 與 R3 都是「有比較好」，沒有一項是「不做會違法」。

**但 R4 不一樣。** 細則 §24 II 給了特休年度三種制度（週年制／曆年制／
約定年度），由勞雇雙方協商 —— 那是**事業單位層級**的選擇，而且不知道採哪一制
就算不出「年度終結」是哪一天，§38 V 的年度通知也就發不出去。

所以結論是：**這一頁的正當理由不是雇主名稱，是特休年度制度。**
若要開這一頁，那個欄位比公司抬頭更該優先放進去；而公司抬頭可以順路一起收，
但它不該是排程的理由。

### 2.1 ⚠️ 但核對 §23 的時候，撞到一個**真的**清冊缺口

工資清冊的法定記載事項不只在 §23 II。**§38 第五項另外加了兩件事：**

> **第 38 條 第五項**
> 雇主應將勞工**每年特別休假之期日**及**未休之日數所發給之工資數額**，
> 記載於第二十三條所定之勞工工資清冊，並**每年定期將其內容以書面通知勞工**。

對照現況（CSV ＝ 本專案的工資清冊）：

| 應記載                       | 現況                                                              |
| ---------------------------- | ----------------------------------------------------------------- |
| 每年特別休假之**期日**       | **完全沒有** —— 全庫 `lib/`、`services/` 查無「特別休假」這個概念 |
| **未休之日數**               | **沒有**。使用者輸入的是「休假折抵薪資**時數**」，日數沒有留下    |
| 未休日數所發給之**工資數額** | 有：CSV 的「休假折抵薪資（免稅）」欄                              |
| **每年定期書面通知勞工**     | **整個功能不存在**                                                |

三缺一。而通知那一項有明確的期限與形式（細則 §24-2）：
應於發給工資的期限前發給，得以紙本、電子資料傳輸方式或其他勞工可隨時取得
及得列印之資料為之 —— 也就是**本模組現有的寄信管道就做得到**。

> **這才是「工資清冊有法定缺口」的正確版本。**
> 我原本寫的 R1（清冊沒有署名）是猜的，而且猜錯了；真正缺的不是抬頭，
> 是特休的期日與日數，以及那封年度通知。
>
> 它與 §7.1 的 `vacationToPay` 缺陷**是同一個欄位**：
> 「未休之日數所發給之工資數額」就是 `vacationToPay`。
> 兩件事應該一起處理，而且都排在本計劃之前。

## 3. 資料放哪裡

> **以下 §3–§6、§9–§10 都以「已經決定要做這一頁」為前提。**
> 而 §2 的結論是它**沒有法遵依據、應該當產品選項排優先度** ——
> 排程的理由是 R4（特休年度制度），不是公司抬頭。
> 決定不做的話，這幾節就是備查，不是待辦。

### 3.1 ⚠️ 不要用既有的 `Company` model

schema 裡有一個 `Company`，搜尋一定先撞到它。**它不是要找的東西。**

```prisma
model Company {
  stockId      String  @id @map("stock_id") // 公司代號 (如 "1101")
  name         String  // 公司全稱
  marketType   String  // 市場別 ("sii" 或 "otc")
  taxId        String? // 營利事業統一編號
  tasks        ReportDownloadTask[]
}
```

主鍵是**股票代號**、有市場別、關聯到 `ReportDownloadTask` —— 它是上市櫃公司
的參考資料表，服務 ESG 報告抓取。它描述「外面那些公司」，不是「用這個帳本的
這家公司」。非上市櫃使用者根本沒有 `stockId` 可以當主鍵。

### 3.2 三個候選

| 方案                                | 好處                                   | 代價                                                         |
| ----------------------------------- | -------------------------------------- | ------------------------------------------------------------ |
| A. `AccountBook` 直接加欄           | 1:1、不用新表                          | `AccountBook` 全模組共用，衝突面最高；公司資訊也不只薪資要用 |
| B. 新表 `AccountBookCompanyProfile` | 與帳本 1:1，日後報表抬頭、發票都用得到 | 多一張表                                                     |
| C. 併進 `/admin/settings`           | 有現成簽章機制                         | **層級錯了**：那是整個部署一份，帳本有很多個                 |

**建議 B。** 理由是這份資料的生命週期與**帳本**一致、與**薪資模組**不一致。

### 3.3 建議的 schema

```prisma
// Info: (20260914 - Julian) 帳本的公司抬頭。與帳本 1:1。
//
// **不是 `Company`** —— 那張表是上市櫃公司的參考資料（主鍵是股票代號，
// 服務 ESG 報告抓取）。這張描述的是「使用這個帳本的這家公司」。
//
// 全部欄位可空以外 `entityName` 必填：它是清冊與薪資單的署名。
// 注意這**不是** §14-1 的必載欄位（那四款全是金額，見計劃書 §1）。
model AccountBookCompanyProfile {
  id String @id @default(uuid())

  accountBookId String      @unique @map("account_book_id")
  accountBook   AccountBook @relation(fields: [accountBookId], references: [id])

  entityName String @map("entity_name")

  taxId             String? @map("tax_id")
  responsiblePerson String? @map("responsible_person")
  address           String?

  // Info: (20260914 - Julian) 特休年度制度（細則 §24 II 三選一）。
  //
  // **這一欄才是這張表真正的法定理由**（見計劃書 §2.1／R4）：
  // 不知道採哪一制，就算不出「年度終結」是哪一天，§38 V 的年度通知
  // 也就發不出去。公司抬頭反而沒有任何條文要求。
  //
  // 週年制不需要起日（由各員工到職日決定）；曆年制固定 1/1；
  // 約定年度才需要 `leaveYearStartMonth` / `leaveYearStartDay`。
  leaveYearScheme     LeaveYearScheme @default(ANNIVERSARY) @map("leave_year_scheme")
  leaveYearStartMonth Int?            @map("leave_year_start_month")
  leaveYearStartDay   Int?            @map("leave_year_start_day")

  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  @@map("account_book_company_profile")
}

// Info: (20260914 - Julian) 細則 §24 II 的三種，由勞雇雙方協商
enum LeaveYearScheme {
  ANNIVERSARY // 週年制：受僱日起每滿一年
  CALENDAR    // 曆年制：1/1 – 12/31
  CUSTOM      // 學年度／會計年度／雙方約定年度
}
```

沒有 `deletedAt`：1:1 且沒有「刪除公司」這個動作，只有改內容，
軌跡由 §5.4 的 AuditLog 承擔。

> **`leaveYearScheme` 的 `@default` 要小心**：給了預設值，舊帳本會「看起來
> 已經設定好」而其實沒有人選過 —— 那正是 `base_salary_snapshot`（§4.1）
> 與部署檢查表 §1.4.1 記過的形狀：**合法但錯的預設值不會噴錯**。
> 週年制是最常見的，但「最常見」不等於「這家公司選的」。
>
> 建議改成可空，讓「還沒選」是一個看得出來的狀態；
> §38 V 的年度通知在沒選之前不發，並在設定頁講明為什麼。
> 這一點與 R4 一起決定（§8）。

## 4. 快照還是現值

**公司在 2027 年改名，2026 年 8 月那張薪資單重印，該印哪個名字？**

答案仍然是**當時的名字** —— 但請注意，前提改了之後這一題的性質也變了：
它不再是法遵問題（那一格根本不是必載），而是**這份文件在講哪一段時間**
的一致性問題。同一份明細上四個金額都是 2026 年 8 月的，抬頭卻是今天的，
讀起來是自相矛盾的。

與本模組已記載過的同類問題同形（`pay_slip_meta.ts`）：

| 欄位         | 來源                    | 性質         |
| ------------ | ----------------------- | ------------ |
| 投保狀態     | 這筆紀錄的 `input` 快照 | **月別**事實 |
| 到職日       | 員工檔**現值**          | **人**的事實 |
| **公司抬頭** | **這筆紀錄的快照**      | **期間**事實 |

### 4.1 ⚠️ 不要做成 `SalaryRecord` 的新欄位

一旦存快照，既有的列就沒有那一格；而本專案無 `prisma/migrations/`、
走 `db push`，新增必填欄位必須給 `@default` —— 舊列會拿到 `@default("")`。

**這正是 20260909 `base_salary_snapshot` 的形狀**（部署檢查表 §1.4.1）：
`@default` 給的是一個合法但錯的值，不噴錯，只有數字（這裡是字串）是錯的。

**處置：寫進 `inputSnapshot` 這個 Json，不動 schema。**

- `inputSnapshot` 本來就是「這筆是用什麼算出來的」的容器
- 讀取端對「舊紀錄沒有這個鍵」的處置是**明確的降級**：回退到現值
- 這個回退要寫進註解，並且說明為什麼不是空字串

> 上次學到的不是「記得跑回填」，而是
> **當回填無從補起時，不要製造一個需要回填的欄位**。
> 舊紀錄當時的抬頭已經不可考，沒有任何腳本補得出來。

因為這一格不是必載，回退到現值是可接受的降級 —— 這一點比原版計劃輕鬆，
值得明講。

## 5. 實作範圍

### 5.1 欄位設計：「公司名稱」與「雇主名稱」收成一格 ⚠️

UI 草稿目前有**兩個必填欄位**：公司名稱、雇主名稱。建議**收成一格**。

勞基法 §2① 的「雇主」是一個涵蓋事業主、負責人、代表事業主處理勞工事務之人
的**法律定義**，不是一個表單欄位。而清冊與明細上要的是**事業單位名稱**。

兩格並排、都標紅星、長得幾乎一樣，最可能的結果是兩格填一樣的字，
或其中一格填了負責人姓名 —— 然後那個人的名字印上每一張薪資單。

建議：一格 `entityName`，標籤「公司名稱（會印在薪資單與工資清冊上）」。
負責人另設**可空**的 `responsiblePerson`，並講明它不印在薪資單上。

| 欄位                           | 必填 | 印在薪資單 | 進 CSV 前言 | 法源                  |
| ------------------------------ | ---- | ---------- | ----------- | --------------------- |
| `leaveYearScheme` 特休年度制度 | ✅   | —          | —           | **細則 §24 II**（R4） |
| `entityName` 公司名稱          | ✅   | ✅         | ✅          | 無（實務慣例）        |
| `taxId` 統一編號               | —    | —          | ✅          | 無                    |
| `responsiblePerson` 負責人     | —    | —          | ✅          | 無                    |
| `address` 公司地址             | —    | —          | ✅          | 無                    |

**這張表讀起來有點反直覺，而那正是重點**：唯一有法源的欄位是特休年度制度，
而它既不印在薪資單、也不進 CSV —— 它的用途是讓 §38 V 的年度通知算得出
「年度終結」是哪一天。公司抬頭那幾格反過來，看得見但沒有條文要求。

### 5.2 資料層與 API

- `account_book_company_profile.repo.ts`：租戶過濾一律是 `where` 的第一個 key
- **不需要回填**：沒有這一列＝還沒設定

```
GET  …/salary_calculator/company_profile
PUT  …/salary_calculator/company_profile
```

比照既有結構（route 只做接收 → 驗證 → 呼叫，zod schema 不寫在 route）；

### 7.1 O1：語意確認之後的兩個缺陷

**確認結果**：「休假折抵薪資時數」＝**特休未休、年度終結折發工資**
（勞基法 §38 IV、細則 §24-1）。不是休假日出勤加給，也不是補休折發。

引擎現況（`salary_calculator.ts`）：

```ts
const hoursInMonth = daysInMonth * 8;          // daysInMonth 預設是當月實際日數
const baseSalaryPerHour = baseSalaryTaxable / hoursInMonth
                        + baseSalaryTaxFree / hoursInMonth;
const vacationToPay = Math.round(baseSalaryPerHour * vacationToPayHours);
...
const totalSalaryTaxFree = … + vacationToPay;   // ← 進免稅
```

#### 缺陷 1：稅務分類錯了（影響扣繳憑單）

特休未休折發工資是**薪資所得**，不是免稅項目。目前它被加進
`totalSalaryTaxFree`，而 `totalSalaryTaxable` 正是薪資單上標示為
**「扣繳憑單金額」**的那個數字（`pay_slip_labels.ts:67`）。

於是：**系統告訴員工的扣繳憑單金額，少計了這一筆應稅所得。**

這個判斷是 2025-08-25 加的，而**程式碼註解、commit 訊息、文件三處都沒有寫理由**
（`git log -S'vacationToPay'` 的三次改動訊息分別是
「update salary calculator interface」「initial rc3 version」
「add salary calculator components」）。

對照之下不一致的地方很明顯：**加班費的免稅／應稅是讓使用者自己選的**
（畫面上「加班時數（免稅）」與「加班時數（應稅）」兩組獨立輸入），
唯獨這一格由系統寫死免稅、使用者沒有選擇權。

#### 缺陷 2：費率基礎與 §24-1 不一致

細則 §24-1 對計月者的規定是：

> 一日工資，為……年度終結或契約終止前最近一個月正常工作時間所得之工資
> **除以三十**所得之金額。

也就是 **月薪 ÷ 30**。而引擎算的是 月薪 ÷（**當月實際日數** × 8）每小時，
且 `baseSalary30Days` **預設為 `false`**（`salary_calculator.ts:280`）。

| 月份          | 條文的一日工資 | 引擎的一日工資（預設） | 差       |
| ------------- | -------------- | ---------------------- | -------- |
| 31 天         | 月薪 ÷ 30      | 月薪 ÷ 31              | **少給** |
| 30 天         | 月薪 ÷ 30      | 月薪 ÷ 30              | 相同     |
| 2 月（28 天） | 月薪 ÷ 30      | 月薪 ÷ 28              | 多給     |

只有把 30 天制打開才與條文一致 —— 而那個開關預設是關的。

#### 順帶：一個**不**在本次範圍、但看到了的疑問

代扣所得稅查表用的是 `totalSalary`（＝應稅＋免稅），
而「扣繳憑單金額」顯示的是 `totalSalaryTaxable`（只有應稅）。
兩者基礎不同：伙食費與免稅加班費**進了扣繳計算、卻不進扣繳憑單**。

這是既有設計，我沒有追出團隊當初的判斷，**所以不在這裡斷定它是缺陷** ——
但它與缺陷 1 相鄰，修 O1 的時候會再撞到一次，值得一併問清楚。

#### 版面

特休未休折發既不是請假、也不是補休，卻和病假／事假同列在
「請假 / 補休時數」區。這個歸類本身可能就是語意被誤讀的來源之一
（它也是 `work_hours_form.tsx` 那段「三格加起來沒有意義」註解的成因）。
