## 1. 三個症狀，同一個形狀

實測「可以繼續了」那則通知時，三件事分屬三個地方，但它們是同一個形狀：

> 畫面在告訴使用者一件系統做不到、或使用者找不到的事。

- 「補上點數後可以從這裡接著匯入」—— **做不到**（加購改變不了翻面判準）
- 「點數已補回」—— **沒發生**（翻面的原因是額度視窗重置或方案變更）
- 「回到智能溫盤按『繼續匯入』」—— **找不到**（UI 裡沒有這五個字）

合成一份修的實質理由只有一個：分開修會把「誰有資格說可以繼續、那句話要帶哪些事實」
判斷兩次，而兩處文案會再次分岔。

## 2. 深連結：去處要深到會話（已做）

`NOTIFICATION_LINK_PATH[JOB_RESUMABLE]` = `/user/carbon_chatbot?session=:sessionId&openImport=1`。

`sessionId` 由 `notification.service.ts` 從 `resourceKey` 切出來放進 payload。
解析函式 `parseCarbonChatChannel()` 與 `buildCarbonChatChannel()` **成對放在
`constants/carbon_chatbot.ts`** —— 兩支互為反函數，放在一起才測得出 round-trip；
放在通知那層則會讓它懂碳盤查的頻道格式，下一種 `JOB_TYPE` 出現時就要懂第二種。

切不出來時**不放那個鍵**（不是空字串）：`resolvePathTokens` 的約定是
「任一 token 代不出來就整條回 `null`」，那一則因此渲染成不可點。

### 2.1 直覺的修法會靜靜地壞掉（實作時發現的兩道）

把常數改成帶 token 的樣板就好 —— 但當時的程式碼有兩道會讓它無聲失敗：

|     | 問題                                                                                                                                                   | 修法                                                              |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| a   | `notificationHrefOf()` **只有分析類那條分支**才呼叫 `resolvePathTokens`，其餘型別直接回原始字串 → `:sessionId` 原封不動出現在 href 裡，正是 D43 的症狀 | fallback 也送進 `resolvePathTokens`，所有型別走同一條代入         |
| b   | `resolvePathTokens` 只認「整段就是 token」（`split("/")` 後看 `startsWith(":")`），query 裡的 token 代不進去                                           | 改成逐 token 的 regex 取代，維持「任一個代不出來就整條回 `null`」 |

(a) 的教訓：「只有分析類需要 token」是**當時的巧合，不是規則**，留著它等於埋下第二次 D43。
(b) 的代價要記住：query string 裡的**冒號字面值**（`?t=12:30`）現在會被當成 token，
代不出來 → 整條回 `null` → 通知變不可點且沒有錯誤訊息。要放冒號請先 encode。

那條回歸測試**先寫先跑**：改之前它是紅的，確認 (a) 是真的而不是讀錯。

### 2.2 落地要直接把預覽卡打開

深連結只解決了「哪一個會話」。`/user/carbon_chatbot` 支援 `?openImport=1`：
還原完該會話的 `pendingImport` 之後直接 `openImportPreview()`。

三個實作決定：

- **`ImportDeepLink` 是一個只回 `null` 的子元件**：`useSearchParams()` 需要 Suspense
  邊界，而頁面元件包不住自己（同 `(landing)/analysis/page.tsx` 的做法）。
- **參數讀完就抹，未完成的指令留在 ref 裡**：這是一次*指令*不是狀態。留著的話
  重新整理會再開一次卡，而任何依 `searchParams` 重跑的 effect 會在使用者手動切
  會話時把他拉回來。抹掉的時機**不該取決於後續有沒有成功**（review 1-H）。
- **等清單「問完」，不是等它非空**：見 §6.1。

## 3. 通知文案（已做）

原本：`點數已補回，「{{completed}}/{{total}}」的匯入可以繼續了 —— 回到智能溫盤按「繼續匯入」`

一句話裡三個問題：引號裡塞的是分數不是名稱（讀起來像有個東西叫「0/14」）、
「點數已補回」是假的、指名的按鈕不存在。

現在（五語系）：

| 情況                              | 文案                                                |
| --------------------------------- | --------------------------------------------------- |
| `completed > 0`                   | 這份匯入可以接著做了，還有 {{remaining}} 章沒有匯入 |
| `completed === 0`／算不出剩餘章數 | 這份報告的匯入可以開始了                            |

三個決定：

- **不宣稱原因。** 先從「點數已補回」改成「額度已恢復」，仍然只對一半 ——
  個人付款那條路恢復的不是額度，是那筆款項付掉了（review 1-A）。兩條路共用一句，
  是因為翻面時 `pauseReason` 已被清成 null，要分辨得先做 `resumedBy`（§5）。
  `notification_i18n_placeholders.test.ts` 現在同時禁「點數」與「額度」——
  哪天真的拆成兩句，那一條會紅並要求回來重新決定。
- **不指名按鈕。** 深連結落地就是能動手的地方，通知不需要教路。指名按鈕等於把 UI
  的字串複製到另一個模組，而改按鈕的人不會知道要回來改通知。
- **帶剩餘章數而不是分數。**「還有 14 章」是一個**決定**（現在值不值得回去），
  `0/14` 只是一個狀態。`remaining <= 0` 也退回「還沒開始」那句 ——
  「還有 0 章沒有匯入，可以接著做了」是一句自相矛盾的話。

## 4. 暫停畫面的文案（**未做**）

`carbon_chatbot.import_paused_chapters` 今天是：

> 點數已用完，以下章節還沒開始解析：{{chapters}}。**補上點數後**可以從這裡接著匯入，已完成的部分不會重跑。

伺服器那邊事實是齊的。`buildQuotaExceededPayload` 回的 402 payload 已經帶著
`exceeded`（哪個視窗先卡）、`quota5h` / `quotaWeek` 各自的 `limit`/`used`/`resetAt`、
以及 `exceedsWindowLimit`（單筆金額就超過視窗上限時，**等重置永遠不會好**）。

丟掉它的是前端 `resolveCreditPauseReason()` —— 它只取 `errorCode`，其餘整包不看；
`import_preview.tsx` 連 `pauseReason` 那個 prop 都宣告了卻沒讀。

於是三種處置完全不同的情況，使用者看到的是同一句「點數已用完」：

| 事實                 | 該說的話                                                   |
| -------------------- | ---------------------------------------------------------- |
| 5 小時視窗卡住       | 今天的額度用完了，◯◯:◯◯ 重置後可以接著匯入                 |
| 週視窗卡住           | 本週的額度用完了，X 月 X 日重置後可以接著匯入              |
| `exceedsWindowLimit` | 這份報告單次就超過方案上限，等重置不會有幫助，需要升級方案 |

**這一句同時踩到兩個缺陷**：沒說重置時間，而且「補上點數後」正是那條不存在的出路
—— 使用者照著做（我們實測時就是照著做的）會完全沒有反應。

改法：`resolveCreditPauseReason()` 從回傳 `JobPauseReason | null` 改成
`{ reason, quota } | null`（**不要另寫一支解析函式**：同一個錯誤被解析兩次，
兩次的判準遲早分岔），文案依事實三選一，五語系一起。

## 5. 待決定：要不要記「是什麼讓它可以繼續」

文案若要分辨「額度回來了」與「款項已到帳」，讀 `pauseReason` 行不通 ——
`markResumable` 翻面時已經把它清成 `null`（schema 的定義：null＝不是暫停狀態）。
要分辨就得另存一個 `resumedBy`。

**建議先不做。** 兩條路的使用者接下來要做的事完全一樣（回去按接著匯入），
而通知的職責是把人放在能動手的地方，不是報告原因。等到兩條路真的需要不同的
下一步時再加，那時 `resumedBy` 才有承載的內容。

## 6. 實機三次都沒過，每次的根因不同

深連結與文案都完成之後，實機驗收連續三次失敗。三個根因彼此無關，
但都屬於同一類：**功能是對的，只是使用者看不到它**。

### 6.1 第一次：清單「非空」不等於「載好了」

點通知之後人落在**預設會話**上。守衛寫的是

```ts
if (sessionIds.length === 0) return; // 清單還沒載進來，等下一輪
```

而會話清單是非同步問伺服器的（`GET /api/v1/chat/carbon/sessions`）。在它回來之前
`sessionsData` 裡已經有預設會話 —— **非空，但不完整**。於是守衛放行、
`includes(sessionParam)` 得到 false、判定「查無此會話」而放棄。

**兩種狀態被壓成同一個觀察值**：「還沒問到」與「問過了，沒有」在 `sessionIds` 上
長得一樣（都是「裡面沒有那個 id」），而它們的正確處置相反 —— 一個要等，一個要放棄。

修法是讓兩件事分開：`use_carbon_chat` 多回一個 `sessionsIndexSettled`，
在那支 request 的 `.finally()` 設成 true（成功或失敗都算問完 —— 失敗時清單不會再補，
繼續等就變成永遠不動作）。**不要沿用 `sessionsIndexLoadedRef`**：
它是「請求發過了」的去重旗標，在 `request()` 之前就設 true，拿它當「載好了」
會犯一模一樣的錯。

### 6.2 第二次：卡片開了，裡面是空的

`persistPendingImport` 把存檔的形狀**逐欄位手寫**成一個物件字面量，
而 #6713 為斷點加的三個欄位（`pausedChapters` / `pausedUnits` / `pauseReason`）
沒有被加進去。三件事讓它一直沒被發現：

1. schema 把那三個欄位定義成**選填**（為了讓舊紀錄還存得進去），驗證照樣通過；
2. 記憶體裡的物件帶著它們，所以**匯入當下**的畫面完全正常；
3. 還原端是 `...restored.pending`，看起來也完全正常。

症狀只有重載之後才看得到 —— 而**重載正是這件事唯一的使用情境**：通知在幾分鐘或
幾天後才響。也就是說，接續功能在它唯一會被用到的路徑上是不可達的，
而掃描、活算通知、五語系文案、深連結全部正確。

修法兩層：形狀抽成純函式 `buildPendingImportRecord()`（抽出來的實質理由是
**它原本測不到** —— 一個 5000 行 hook 裡 `useCallback` 內的物件字面量）；
`carbon_pending_import_record.test.ts` 釘住三個欄位存得下去、且走一趟 schema 之後
還在（只斷言「鍵存在」擋不住「形狀不合被 `safeParse` 整筆丟掉」，症狀一模一樣）。

**最後一條測試由 schema 自己長出來**：凡是 schema 認得的 `pending` 欄位，
只要輸入有值，建出來的紀錄就必須帶著它。釘的不是這三個欄位，是那個手法 ——
schema 加一個選填欄位、存檔的字面量忘了跟上，而選填讓驗證閉嘴。

刻意**沒有**把缺席補成 `[]`：那會把「這份匯入沒有暫停過」與「暫停過但我忘了存」
寫成同一個值，而還原端分不出來 —— 正是這一節的病本身。

### 6.3 第三次：匯入完全沒有回饋

上傳檔案之後畫面上什麼都沒有。兩個原因疊在一起。

**（一）「收起」這個旗標沾到了下一份解析結果（已修）。**
`deferredPreviewSessions` 記的是「使用者把那張卡收起來了」，但它**只以 session 為鍵**，
於是那個旗標會沾到同一個會話往後的每一份解析結果。而它幾乎一定是開著的：
重載時的還原一律以收起狀態進來（那是刻意的 ——「一進聊天室就被一張蓋住全螢幕的
預覽卡攔住，而它講的可能是幾天前的事」）。修法是在解析結果落地時清掉該會話的旗標：
**收起的是那一張卡，不是這個會話往後的每一張。**

**（二）匯入的每一個回饋面都住在 `ChatInput` 裡，而它只在解鎖後才渲染（未完）。**
`page.tsx` 的結構是 `{isUnlocked ? <ChatArea/><ChatInput/> : 解鎖提示}`，而進度
（`draftNotice`）、收起中的待匯入橘色列、以及 `importReportFile()` 開頭那兩道早退的
訊息全都掛在 `ChatInput` 上。但「匯入報告」的入口在**報告工具列**，
而帳本綁定的會話**不需要解鎖**就能匯入。

那兩道早退是使用者實際撞到的：

| 早退                          | 什麼時候                                                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `importInFlightRef.current`   | 已經有一份匯入在跑（第二次之後的上傳全部被擋）                                                             |
| `willChunk && !accountBookId` | PDF／大檔 + **未綁帳本的會話** —— 逐章匯入要 14 次呼叫，個人點數那條路會變成 14 筆訂單，所以在送出前就擋下 |

用瀏覽器查 API 證實了沒有東西擁塞：7 個會話的 `pending-import` 全部是 `null`，
也就是那幾次上傳一次都沒有真的跑起來。訊息本身寫得很清楚，
只是被送到一個「鎖著時不存在」的元件裡。

**這是同一個病的第二次發作。** `page.tsx` 那段解鎖失敗訊息旁邊就寫著（20260812）：
「原本失敗只 `appendMessageLocally()` 到聊天區，而那個區塊在解鎖前還鎖著 ——
使用者的體驗是『點了完全沒有反應』。」根源是判斷「訊息該說在哪裡」的依據一直是
**它屬於哪個元件**，而不是**使用者在那個狀態下看得到哪裡**。

已補最小的兩件事到解鎖畫面：正在發生什麼、以及有一份結果等著看。
橘色列還沒搬出來（§8）。

## 7. Code review #6732 的修正（20260831）

報告在 `code_review_pr6732.md`，§一那八條全數處理。兩條「應修」值得記**為什麼會漏**。

**1-A 釋放與付款沒有關聯。** `releasePaymentBlockedJobs` 撈的是使用者全部的
`PAUSED + PAYMENT_REQUIRED`。漏掉的原因是**我把「這個人付了款」當成「這件事可以
繼續了」**，中間少了一步：**哪一件事**。設計時只有一份匯入，兩者剛好等價。
修法與 fail-closed 的取捨見 notification 文件 §4.2；文案那一半見 §3。

**1-B 兩支讀取查詢沒有守門。** 把 `listResumableByUser` 的 `where` 拿掉 `userId`，
**527 個測試全綠** —— 不是沒人測到，是兩個消費端都把整支 repo 整包 mock 掉了，
而 repo 自己沒有測試（檢查清單 §1.2）。後果是外洩：任何人打開小鈴鐺會看到全站
所有人的可繼續任務，payload 帶著別人的錢包位址與會話 id。

新增 `resumable_job_read_scope.test.ts`，mock 的是 `prisma`，斷言**交給資料庫的條件**；
最後一條由原始碼長出來（每一支 `findMany` 都要帶 `userId`，或登記在 `CROSS_USER_READS`，
今天只有 `listPausedForScan`）。**寫這條掃描時第一版自己就犯了它要抓的錯**：
用 `indexOf(line)` 回頭找位置，而每一支的 `findMany(` 是同一個字串，
於是每一支都拿第一支的條件來檢查，永遠是綠的。

其餘六條：

| 條  | 做了什麼                                                                                                                          |
| --- | --------------------------------------------------------------------------------------------------------------------------------- |
| 1-C | 接線掃描從 `indexOf`（只驗第一個呼叫點）改成**計次**：釋放呼叫的次數要等於標 `PAID` 的次數，且每一處都包 `try`、都帶 `order.data` |
| 1-D | 補上本 PR 自己承諾的釘子（`spend_second_layer_inert.test.ts` 的 D 類）                                                            |
| 1-E | 刪掉「那一頁不吃 searchParams」的過期註解 —— 照著它寫會產出帶他人錢包位址的網址                                                   |
| 1-F | 「代入是逐段做的」改成逐 token，並記下冒號字面值的新坑（§2.1）                                                                    |
| 1-G | ADR 025 補 `JOB_RESUMABLE`；計畫書發射點欄補 `order.tracker.service.ts` 並註明活算來源不在該欄；`readme.md` 登記兩份文件          |
| 1-H | 深連結參數讀完就抹（§2.2）                                                                                                        |

另補了表格裡標為「次要」的 §1.13：`CATEGORIES` 與 `ANALYSIS_LINK_PATH_BY_CATEGORY`
的**聯集**必須蓋滿 15 種 `ANALYSIS_CATEGORY`。§3.5（payload 的三個鍵無消費者）沒有動：
`resourceKey` 現在是 `sessionId` 的來源、`jobId` 是接續 API 的參數。

> R1 的形狀值得記：**過期的文件不只是不準，它會讓掛在它下面的待辦失去觸發條件。**
> 「`accountBookId` 目前沒有」那句話下面接著「真的出現時要一併決定軟刪除怎麼辦」——
> 於是 `accountBookId` 真的出現時，沒有人回頭看那句話。

## 9. 不要做的事

- **不要在 `notification_message.ts` 裡解析 `resourceKey`。** 那一層不該懂任何一種
  `JOB_TYPE` 的資源格式（§2）。
- **不要只改文案不做深連結。** 短期止血（把「繼續匯入」改成畫面上真的有的字）
  只是把四層路徑寫進一句話，而那句話會在按鈕改名時再次過期。
- **不要為了分辨兩條路而保留 `pauseReason`。** 見 §5，也見 `markResumable` 的註解。
- **不要把「沒有暫停」與「忘了存」寫成同一個值。** 見 §6.2 最後一段。
