# PDF 光柵化驗證工具

> 開發輔助工具,不進 build。`npm i` 後以 `node <檔名>.mjs` 執行。
> Playwright 找不到瀏覽器時,把各檔的 `executablePath` 改成本機 Chrome 路徑。

## 為什麼這些工具存在

2026-08-07 的 UAT 回歸中,PDF 匯出的修正被這套工具**推翻了四次**,
而四次在單元測試裡都是綠的:

- jsdom 沒有真實 canvas,假探針的 `drawImage` 是空實作 ——
  座標語意、降採樣、貼圖位移這三類錯誤只活在真實瀏覽器的光柵化路徑上。
- 表格與圖表的版面問題發生在**光柵化之前**(列印樣式),
  單元測試看不到 layout。

也就是說:這一層不是單元測試的補充,是單元測試看不見的地方。
每次要動 `PDF_PRINT_STYLE` 或 `renderSegmentedPdf`,先跑對應的工具再改。

## 各工具對應的問題

| 檔案 | 驗什麼 |
| --- | --- |
| `variants.mjs` | html2canvas 的 `x`/`y` 是元素內偏移還是文件座標 |
| `blank.mjs` / `probe_size.mjs` | 空白偵測的降採樣策略與探針大小 |
| `pages.mjs` | 單頁切分的貼圖位移(小數位移會整頁模糊) |
| `blocks.mjs` | 分頁避開圖表時的 DOM 量測是否正確 |
| `overrun.mjs` | 提前分頁後每頁是否溢出到下一頁 |
| `table17.mjs` | 列印樣式對表格欄寬的影響(`table-layout: fixed`) |

# html2canvas 分段座標驗證工具

用途:驗證 `pdf_editor.tsx` 的 `renderSegmentedPdf` 傳給 html2canvas 的 `x`/`y` 語意。

## 結論(2026-08-07 實測)

html2canvas 1.4.1 的 `x`/`y` 是**元素內偏移**,不是文件座標。

| 寫法 | 結果 |
|---|---|
| `x: elLeft, y: elTop + sliceTop` | ❌ 內容整體下移 elTop,最後一段全白 |
| `x: 0, y: sliceTop` | ✅ 四段頂底全部命中,右緣為內容色 |

測試條件刻意包含:元素不在文件頂端(top=137)、有水平位移(left=41)、
頁面已捲動(scrollY=420)—— 三者都是實際匯出時的常態。

## 跑法

```
npm i html2canvas@1.4.1 playwright
node variants.mjs
```

若 Playwright 找不到瀏覽器,把 `variants.mjs` 裡的 `executablePath` 改成本機 Chrome 路徑。

## 原理

`page.html` 產生 1200 條 10px 高的橫紋,每條用顏色編碼自己的索引
(r = idx & 255, g = idx >> 8)。讀回任一段 canvas 的某一列像素就能反解
「這是第幾條」,於是「有沒有錯位、有沒有漏行」變成可以自動判定的事,
而不是靠肉眼看 PDF。

# 空白偵測驗證(blank.mjs / probe_size.mjs)

`blank.mjs` 比較三種降採樣策略,`probe_size.mjs` 掃描探針大小對邊際的影響。

## 結論(2026-08-07 實測,單位:128×128 探針下的非背景像素數)

| 頁面 | 一次縮到 32 | 逐次減半→128 |
|---|---|---|
| 真空白(白 / 深色 / 灰底) | 0 | **0** |
| 只有一個 8px 圖示 | 0 ❌ | **4** |
| 只有右下角頁碼 | 0 ❌ | **9** |
| 只有一行標題 | 0 ❌ | **103** |
| 末頁兩行內文+頁碼 | 0 ❌ | **132** |
| 一般滿版內文 | 98 | 16000+ |

一次縮到位會讓 Chrome 走近似最鄰近取樣,細內容整條被跳過 ——
四種合法的稀疏頁面全部量到 0,會被判成空白而中止輸出。

逐次減半後,真空白與最稀疏的合法內容分別是 0 與 4,
分界在「0 與非 0」而不在某個比例上,所以門檻改用絕對像素數(3)。

# 單頁切分驗證(pages.mjs)

段落座標正確不代表頁面座標正確。`pages.mjs` 驗證第二層:
每一段畫完之後,`drawImage(segmentCanvas, 0, -offset * pageHeightPx * SCALE)`
切出的**每一頁**內容是否落在正確位置。

## 結論(2026-08-07 實測)

`pageHeightPx = 267mm × (794px / 180mm) = 1177.7667` —— 小數。
× scale 2 之後,每段中 offset > 0 的頁貼圖位移是 `-2355.53` 這種值。
drawImage 收到小數 y 會用雙線性重採樣整張圖。

| | 取整前 | 取整後 |
|---|---|---|
| 頁 5 取樣點解碼 | 2642(亂碼) | 588(正確) |
| 頁 5 取樣色 b | 201(混色) | 200(原色) |
| 混色頁數 | 1 / 11 | **0 / 11** |

修法:`-Math.round(offset * pageHeightPx * SCALE)`。
整數位移是純複製,不做內插;每頁最多偏半個像素,且因為每次都從
offset 重算而非累加,誤差不會沿著 153 頁累積。

## 注意:條紋圖低估了實際影響

條紋只在條與條的交界處看得出混色,所以 11 頁裡只有 1 頁被量到。
真實文字到處都是邊緣 —— 實際上是**每一個小數位移的頁面整頁輕微模糊**,
約佔全部頁面的三分之二。

## 已知的量測誤差(不是程式問題)

- 頁 9 頂端差一條:切片起點落在小數上,期望值取 floor 本來就偏一格。
- 頁 10 底端全白:最後一頁只剩 222px 內容,其餘留白是正確的。

# 分頁避開圖表(blocks.mjs)

驗證 `computePageStarts` 的**輸入**是對的 —— 純函式的單元測試只能證明邏輯,
證明不了 DOM 量測給了它正確的座標(x/y 那個錯就是這樣溜過去的)。

測試條件同樣包含元素不在文件頂端(top=137)、有水平位移、頁面已捲動(scrollY=420)。

## 結論(2026-08-07 實測)

`rect.top - element.getBoundingClientRect().top` 得到的是正確的元素內偏移:

| 區塊 | 量到 | 期望 |
|---|---|---|
| svg | 800.0 → 1200.0 | 800 → 1200 |
| table | 2700.0 → 3000.0 | 2700 → 3000 |

分頁起點 `[0, 800, 1800, 2700, 3700]` —— 第 0 頁在 800 提前結束(讓 svg 完整落在第 1 頁),
第 3 頁從 2700 起(讓 table 完整)。兩個區塊都沒有被分頁線切開。

# 溢出驗證(overrun.mjs)

提前分頁之後每頁高度不同,但貼圖若仍畫滿一整頁,多出來的部分正好是下一頁的開頭。
UAT 看到的「圖切一半印在上一頁、下一頁又完整印一次」就是這個溢出,不是重複渲染。

## 結論(2026-08-07 實測)

以 400 條編碼橫紋 + 一張 400px 圖表測試,分頁起點 `[0, 900, 1900, 2900, 3900]`
(第 0 頁被縮短到 900px 讓圖表完整落在下一頁):

- 修正前:第 0 頁畫滿 1000px,溢出 100px = 第 1 頁的前 10 條橫紋。
- 修正後:**沒有任何一條橫紋出現在兩頁上。**

修法:改用來源矩形版本的 `drawImage(src, sx, sy, sw, sh, dx, dy, dw, dh)`,
把來源高度限制在這一頁自己的高度,不足一頁的部分留白。
