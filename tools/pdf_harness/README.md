# PDF 光柵化驗證工具

> 開發輔助工具,不進 build。`npm i` 後以 `node <檔名>.mjs` 執行。
> Playwright 找不到瀏覽器時,用環境變數指路:
> `CHROMIUM_PATH=/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome node final.mjs`

## 為什麼這些工具存在

2026-08-07 的 UAT 回歸中,PDF 匯出的修正被這套工具**推翻了四次**,
而四次在單元測試裡都是綠的:jsdom 沒有真實 canvas,假探針的 `drawImage` 是空實作;
而表格與圖表的版面問題發生在**光柵化之前**(列印樣式),單元測試看不到 layout。

也就是說:這一層不是單元測試的補充,是單元測試看不見的地方。
**每次要動 `PDF_PRINT_STYLE` 或 `renderSegmentedPdf`,先跑對應的工具再改。**

## 各工具對應的問題

| 檔案 | 驗什麼 |
| --- | --- |
| `variants.mjs` | html2canvas 的 `x`/`y` 是元素內偏移還是文件座標 |
| `blank.mjs` / `probe_size.mjs` | 空白偵測的降採樣策略與探針大小 |
| `pages.mjs` | 單頁切分的貼圖位移(小數位移會整頁模糊) |
| `blocks.mjs` | 分頁避開圖表時的 DOM 量測是否正確 |
| `overrun.mjs` | 提前分頁後每頁是否溢出到下一頁 |
| `table17.mjs` | 列印樣式對表格欄寬的影響(`table-layout: fixed`) |
| `thead.mjs` | html2canvas 支援哪些色彩函式(`oklch` / `color-mix` 會**拋錯**) |
| `color_safe.mjs` | 用 canvas 把不支援的顏色轉成 rgb,以及能否還原 |
| `fit.mjs` | 表格內在寬度的量測與等比縮放 |
| `proxy.mjs` | **getComputedStyle 攔截器**:塗黑 vs 等價換算(黑表頭的真因) |
| `tables2.mjs` | `width:100%` 與 `table-layout` 的四種組合對表寬的影響 |
| `overflow2.mjs` | 超寬表把 scrollWidth 撐大之後,整份內容被縮到多小 |
| `charts2.mjs` | 圖表 SVG 的寬高規則:過高、信箱框空白 |
| `final.mjs` | **端到端**:套上全部修正後真的光柵化一次,六項一起驗 |
| `important.mjs` | 列印樣式的 `!important` 會不會把 JS 的量測手法架空 |

# html2canvas 分段座標驗證工具

用途:驗證 `pdf_editor.tsx` 的 `renderSegmentedPdf` 傳給 html2canvas 的 `x`/`y` 語意。

## 結論(2026-08-07 實測)

html2canvas 1.4.1 的 `x`/`y` 是**元素內偏移**,不是文件座標。

| 寫法 | 結果 |
|---|---|
| `x: elLeft, y: elTop + sliceTop` | ❌ 內容整體下移 elTop,最後一段全白 |
| `x: 0, y: sliceTop` | ✅ 四段頂底全部命中,右緣為內容色 |

測試條件刻意包含:元素不在文件頂端(top=137)、有水平位移(left=41)、
頁面已捲動(scrollY=420)—— 三者都是實際匯出時的常態。

## 跑法

```
npm i html2canvas@1.4.1 playwright
node variants.mjs
```

若 Playwright 找不到瀏覽器,把 `variants.mjs` 裡的 `executablePath` 改成本機 Chrome 路徑。

## 原理

`page.html` 產生 1200 條 10px 高的橫紋,每條用顏色編碼自己的索引
(r = idx & 255, g = idx >> 8)。讀回任一段 canvas 的某一列像素就能反解
「這是第幾條」,於是「有沒有錯位、有沒有漏行」變成可以自動判定的事,
而不是靠肉眼看 PDF。

# 空白偵測驗證(blank.mjs / probe_size.mjs)

`blank.mjs` 比較三種降採樣策略,`probe_size.mjs` 掃描探針大小對邊際的影響。

## 結論(2026-08-07 實測,單位:128×128 探針下的非背景像素數)

| 頁面 | 一次縮到 32 | 逐次減半→128 |
|---|---|---|
| 真空白(白 / 深色 / 灰底) | 0 | **0** |
| 只有一個 8px 圖示 | 0 ❌ | **4** |
| 只有右下角頁碼 | 0 ❌ | **9** |
| 只有一行標題 | 0 ❌ | **103** |
| 末頁兩行內文+頁碼 | 0 ❌ | **132** |
| 一般滿版內文 | 98 | 16000+ |

一次縮到位會讓 Chrome 走近似最鄰近取樣,細內容整條被跳過 ——
四種合法的稀疏頁面全部量到 0,會被判成空白而中止輸出。

逐次減半後,真空白與最稀疏的合法內容分別是 0 與 4,
分界在「0 與非 0」而不在某個比例上,所以門檻改用絕對像素數(3)。

# 單頁切分驗證(pages.mjs)

段落座標正確不代表頁面座標正確。`pages.mjs` 驗證第二層:
每一段畫完之後,`drawImage(segmentCanvas, 0, -offset * pageHeightPx * SCALE)`
切出的**每一頁**內容是否落在正確位置。

## 結論(2026-08-07 實測)

`pageHeightPx = 267mm × (794px / 180mm) = 1177.7667` —— 小數。
× scale 2 之後,每段中 offset > 0 的頁貼圖位移是 `-2355.53` 這種值。
drawImage 收到小數 y 會用雙線性重採樣整張圖。

| | 取整前 | 取整後 |
|---|---|---|
| 頁 5 取樣點解碼 | 2642(亂碼) | 588(正確) |
| 頁 5 取樣色 b | 201(混色) | 200(原色) |
| 混色頁數 | 1 / 11 | **0 / 11** |

修法:`-Math.round(offset * pageHeightPx * SCALE)`。
整數位移是純複製,不做內插;每頁最多偏半個像素,且因為每次都從
offset 重算而非累加,誤差不會沿著 153 頁累積。

## 注意:條紋圖低估了實際影響

條紋只在條與條的交界處看得出混色,所以 11 頁裡只有 1 頁被量到。
真實文字到處都是邊緣 —— 實際上是**每一個小數位移的頁面整頁輕微模糊**,
約佔全部頁面的三分之二。

## 已知的量測誤差(不是程式問題)

- 頁 9 頂端差一條:切片起點落在小數上,期望值取 floor 本來就偏一格。
- 頁 10 底端全白:最後一頁只剩 222px 內容,其餘留白是正確的。

# 分頁避開圖表(blocks.mjs)

驗證 `computePageStarts` 的**輸入**是對的 —— 純函式的單元測試只能證明邏輯,
證明不了 DOM 量測給了它正確的座標(x/y 那個錯就是這樣溜過去的)。

測試條件同樣包含元素不在文件頂端(top=137)、有水平位移、頁面已捲動(scrollY=420)。

## 結論(2026-08-07 實測)

`rect.top - element.getBoundingClientRect().top` 得到的是正確的元素內偏移:

| 區塊 | 量到 | 期望 |
|---|---|---|
| svg | 800.0 → 1200.0 | 800 → 1200 |
| table | 2700.0 → 3000.0 | 2700 → 3000 |

分頁起點 `[0, 800, 1800, 2700, 3700]` —— 第 0 頁在 800 提前結束(讓 svg 完整落在第 1 頁),
第 3 頁從 2700 起(讓 table 完整)。兩個區塊都沒有被分頁線切開。

# 溢出驗證(overrun.mjs)

提前分頁之後每頁高度不同,但貼圖若仍畫滿一整頁,多出來的部分正好是下一頁的開頭。
UAT 看到的「圖切一半印在上一頁、下一頁又完整印一次」就是這個溢出,不是重複渲染。

## 結論(2026-08-07 實測)

以 400 條編碼橫紋 + 一張 400px 圖表測試,分頁起點 `[0, 900, 1900, 2900, 3900]`
(第 0 頁被縮短到 900px 讓圖表完整落在下一頁):

- 修正前:第 0 頁畫滿 1000px,溢出 100px = 第 1 頁的前 10 條橫紋。
- 修正後:**沒有任何一條橫紋出現在兩頁上。**

修法:改用來源矩形版本的 `drawImage(src, sx, sy, sw, sh, dx, dy, dw, dh)`,
把來源高度限制在這一頁自己的高度,不足一頁的部分留白。

# 票 17:下載的 PDF 版面(2026-08-10 實測)

8/07 的假設是「三個症狀同一個根因:光柵化時的版面寬度與預覽不一致」。
**假設不成立**,實測是四個各自獨立的成因,其中三個是 8/10 那一版自己造成的。

## 1. 表頭全黑 —— 不是 html2canvas 拋錯,是我們自己塗的

`pdf_editor.tsx` 從 2026-04-26 起攔截 `getComputedStyle`,
把任何含 `lab` / `lch` / `color(` 的值換成 `rgb(17, 24, 39)` 當「安全退路」。
Tailwind v4 的 `bg-gray-50` computed 值是 `oklch(0.985 0.002 247.839)` —— 字串裡有 "lch"。

`proxy.mjs` 實測(表頭底色真值 rgb(249,250,251)):

| 情境 | 畫出來 |
|---|---|
| 無攔截 | 💥 `unsupported color function "oklch"` |
| 既有攔截 | rgb(17, 24, 39) ← 黑 |
| 等價換算 | rgb(249, 250, 251) ✅ |

這也解釋了 8/10 在 DOM 上做的顏色修正為什麼一點作用都沒有:
它讀到的已經是攔截後的 `rgb(17, 24, 39)`,永遠不會有 oklch 可以修。
**攔截器要換算,不是塗色。**

## 2. 表格寬度不一 —— `width: 100%` 不能拿掉

`tables2.mjs` 實測(容器 794px,窄表 2 欄、寬表 11 欄):

| 列印樣式 | 窄表 | 寬表 | 寬表首欄 |
|---|---|---|---|
| `width:100%` + `fixed`(原本) | 794px | 794px | 72px / 7 行 ← 直排 |
| 只有 `auto`(8/10 改的) | **148px** | 794px | 221px / 2 行 ← 寬度不一 |
| `width:100%` + `auto` | 794px | 794px | 221px / 2 行 ✅ |

`table-layout: fixed` 是「欄寬平均分配」的成因,`width: 100%` 是「整體撐滿」的來源 ——
是兩件事。8/10 把兩個一起拿掉了。

## 3. 沒有滿版、圖太小 —— 一張表把整份內容縮到 49%

`overflow2.mjs` 實測:一張 16 欄的表在 `overflow-x: visible` 下把
`#pdf-content` 的 scrollWidth 從 794px 撐成 1614px。
而 `renderSegmentedPdf` 是拿 scrollWidth 對映頁寬的 —— 其餘內容因此全部縮到 **49%**,
右半頁空白。這就是使用者說的「排版沒有滿版」「有的圖太小」「奇怪的空白」。

`withFittedTables` 本來就是為了擋這件事,但它的簽章寫成同步
(`run: () => T`)卻傳進 async callback:`try { return run() } finally { restore() }`
在 promise **建立完成**時就還原,光柵化還沒開始 —— 縮放等於沒有發生,而且是靜默的。
回歸測試在 `src/__tests__/pdf_color_safety.test.ts`。

## 4. 圖太大、信箱框空白 —— 別強制撐滿頁寬

`charts2.mjs` 實測(可列印寬 794px):

| SVG | `width:100%` `max-height:none` | `width:100%` `max-height:900` | `width:auto` `max-height:900` |
|---|---|---|---|
| viewBox 200×120 | 794×476 | 794×476 | 200×120 |
| viewBox 1200×700 | 794×463 | 794×463 | 794×463 |
| viewBox 600×2400 | 794×**3176** ← 跨三頁 | 794×900 ← 左右各空 285px | 225×900 ✅ |

補上 `max-height` 而不改 `width`,SVG 的 preserveAspectRatio 會在框裡置中並留下信箱框空白 ——
那是另一種「奇怪的空白」。`width: auto` 之後框就等於內容。

## 修正後(`final.mjs`,端到端光柵化)

```
✅ 表頭顏色        rgb(249,250,251)（修正前 17,24,39）
✅ 表格等寬        窄表 794px、11 欄表 794px
✅ 版面滿版不溢出   scrollWidth 794px / clientWidth 794px
✅ 超寬表已縮放     16 欄表內在 1678px → ×0.473
✅ 圖表高度不超過一頁 200×120、794×463、225×900
✅ 圖表無信箱框空白  每張圖的框等於內容
```

## 但這些都不夠 —— 8/10 下午的 UAT

上面六項在無頭 Chromium 端到端全過,實際下載的 112 頁 PDF 仍然:
一行字被從中間橫切成兩頁、表格列被切開、表格欄位仍然是直排、
圖表縮成一條而容器留著一大片白、流程圖右側被裁掉。
只有表頭顏色是真的修好了。

### 一、`!important` 把量測架空(`important.mjs`)

```
容器約束下的表寬          794px
量內在寬（無 important）   794px  ← withFittedTables 現在的寫法
量內在寬（有 important）   1651px ← 真值
```

`#pdf-content table { width: 100% !important }` 蓋過 JS 為了量內在寬而設的
inline `max-content`,於是內在寬永遠回報成可列印寬,**縮放從頭到尾沒有觸發過一次**。
同一個失敗模式的第五次:改對了一件事,而那件事在真實環境裡被另一條規則靜默架空。

### 二、根本原因:html2canvas 沒有「頁」

`page-break-inside`、`break-inside`、`thead { display: table-header-group }`
是給**瀏覽器列印引擎**看的規則。html2canvas 一條都不執行 ——
它只是把 DOM 畫成一張大圖,html2pdf 再在像素上橫切。
所以「不要切開這一列」「跨頁重印表頭」這些話寫了但沒有任何東西在聽:
文字行與表格列被切一半,在這個架構下不是 bug,是它的工作方式。

而且輸出是 112 頁的點陣圖 —— 查證人員不能搜尋、不能複製任何一個排放量數字。
一份 ISO 14064 查證文件不該是圖片。

### 三、結論:這一層不再修

2026-08-10 決定改做**伺服器端向量列印**(Chrome 的 `page.pdf()`)——
那是真的列印引擎,上面那些列印 CSS 到那邊才第一次真的生效,
而且文字是文字、圖是向量。

前端這條路保留給任務板、文件工具那些短文件(它們現在是好的),
但**不再為長報告的版面問題往 `PDF_PRINT_STYLE` 疊新規則**。
本目錄的工具改為記錄「為什麼不走這條路」的證據。

## 這次學到的

8/07 寫在這裡的「先驗證,再動手」只做了一半:8/10 驗證了 `table-layout` 與顏色轉換
**各自**成立,卻沒有把整份版面端到端跑過一次 —— 於是 `width:100%` 被順手拿掉、
async 簽章寫錯、DOM 修色被上游攔截器架空,三件事全都沒被任何一支工具看見。
`final.mjs` 補的就是這一段:改完之後整份跑一次。

但 8/10 下午證明連這樣也不夠:`final.mjs` 六項全過,真實下載仍然是壞的。
差別在於工具驗的是「我寫的規則有沒有照我想的方式生效」,
而沒有驗「這個引擎會不會執行這類規則」—— 答案是不會。
**下次要問的第一個問題不是「我改對了嗎」,是「這個引擎聽得懂我在說什麼嗎」。**
