## 做了什麼

### 1. 讓失敗說得出原因

| 位置 | 原本 | 現在 |
| :--- | :--- | :--- |
| `fetchSectionPageIndex` | 成功時**零 log** | 記錄索引結果與每章實際切片 |
| `source table dropped` | 只記 `reason` | 加記被拒內容的開頭三行 |
| 缺表3.8 | 靜默少一張圖 | 報告裡寫出原因與後果 |
| `loadHistory` 解密失敗 | 空 catch | 記下解不開的則數 |
| 推播連線 | 只寫進沒人消費的 `isError` | 輸入列顯示連線中/已中斷 |

**原則:被擋下的東西,要連「擋它的那個依據」一起記。**
`not_a_table` 檢查的正是前兩行 —— 不印出來就等於「知道被擋了,但永遠不知道為什麼」。

### 2. 表3.8 的四種版面各留一份 fixture

同一份 PDF、同一組提示詞,**版面至今換過四次**:

1. 廠址欄逐列重複(合併儲存格攤平)
2. 廠址與類別小計各自獨立成列,每廠址前重複表頭
3. 拆成三張子表格,廠址名在**表格外**的純文字行
4. 廠址名成為表格內的粗體列 + 開放類別的無細分項獨立成列

四份都留 —— 只留新的等於把前幾輪的迴歸風險丟掉,而版面隨時會變回來。

判準一律**收緊到明表,不用排除法**。例:第三種版面的廠址標籤要求
`(n)` 前綴 + 短名 + 整行到此為止 —— 沿用 `isSiteCell` 的「含公司」備援訊號
會把表格標題「表3.8 **各公司**溫室氣體…」認成廠址。

### 3. 未解析列的否決權:粒度不對

test5 那輪**勾稽 16 項全通過**(全公司 8332.5812 vs 原文 8332.581),卻仍不入帳。
擋住它的是 `| 類別六 | | NA | |` 後面那行 `| - | NA | | |` ——
前一行已產出該類別的資料列,這一行沒有新資料,但「有數值卻認不出主體」
於是被記成未解析,而未解析列有獨立的否決權。

那個否決權是對的(少讀一列時小計與總計往往一起少,勾稽反而會通過)。
**問題在粒度**:純粹的佔位標記不該與「真的讀不懂一列資料」同等對待。
判準收緊到「非空儲存格恰好是一個 `-` 加一個數值」,並補測試證明
把 `1.1 固定式燃燒` 改成看不懂的字樣時**仍會記成未解析** —— 放寬不等於放行。

### 4. 排版不是內容:`<br>` 在讀取時清除

畫面把 `工業<br>冷<br>凍` 原樣印出(`rehype-raw` **刻意不開**,理由是 XSS;
下載 PDF 走同一個 DOM,沒有第二套渲染能救)。

但顯示只是最表面。整條匯入路徑**一處都沒清洗儲存格文字**,
`<br>` 一路帶進解析器造成四個**靜默**錯誤:數字解不出、
`(1) 總公<br>司` 成為污染的廠址名一路帶進桑基圖節點、子代碼對不到、重複表頭被當成資料列。

存下來的原文一字不改(逐字照錄的合約),清除發生在讀取時;
**兩個呼叫端、一份實作** —— 兩層各寫一份 regex 遲早不一致,
而不一致的表現是「圖上的廠址名跟畫面上的不一樣」。

補空白的判準改過一次(見「我今天犯的錯」)。

### 5. 桑基圖改五層

    全公司 → (3) 屏東分公司 → (3) 範疇一 → (3) 類別一 → (3) 1.1

原本三層,而且三個廠址**共用同一個類別節點**:總量守恆但線互相交叉,
也看不出「屏東的類別一」與「總公司的類別一」誰是誰 ——
那不是一棵樹,是把三棵樹疊在一起。第三層之後帶廠址序號前綴才是真的層級。

- **範疇層**需要 GHG 15 類 → Scope 1/2/3 的映射:**明表列舉,不從 enum 名稱前綴推導**。
  `SCOPE_3_CAT_n` 看起來可以字串切割,但那把分類規則寄託在命名慣例上;
  命名一改就靜默給出錯的範疇,而範疇是報告的第一層分類。
- **標籤縮短**:完整類別名 18 個字 × 數十個節點必然重疊,重疊之後連看得見的流量也讀不出來。
  新增短名映射(`類別一`),完整名仍在敘述與表格裡。
- **第五層是子代碼,不是燃料實體**(見「已知限制」)。
- **門檻只套最細一層**(見「我今天犯的錯」)。

### 6. 匯入在聊天室留下持久記錄

匯入原本**全程不產生任何聊天訊息** —— 一份 64 頁的報告落地 33 個段落,
對話裡卻只剩招呼語。段落層的 `origin` 會被編輯抹掉,
報告層的 `importedFrom` 只有檔名與時間;「當時發生了什麼」需要一則
按時序排在對話裡、**且能撐過重載**的記錄。

新端點走既有的 `recordAndPublishAiReply`(加密 → 入庫 → 推播),
與 AI 回覆同一條路:同樣加密、同樣以 `message.id` 去重、推播斷線時靠 HTTP 回帶保底。

- **文案由伺服端組出,前端只送事實。** schema 沒有任何可放文字的欄位 ——
  入庫的是系統的陳述,不能讓呼叫端塞任意字串進使用者的對話紀錄。有測試盯著。
- **走 SAVE bucket 不走 LLM bucket。** 它不呼叫 LLM;算進去會讓匯入本來就吃緊的額度再少一格。
- **「未查核」那句不因勾稽通過而省略。** 勾稽通過只代表數字與原文自洽,不代表有人看過。

### 7. 聊天室斷線:我們自己弄斷的

`WebSocket is closed before the connection is established` 是
**客戶端在 CONNECTING 狀態呼叫 close()** 才會印的(伺服端拒絕會是 403/502)。

`subscribeChatroom` 每次呼叫都 `new Centrifuge()`、清理時 `disconnect()`;
而訂閱 effect 的依賴鏈一路連到 `sessionAccess`,它在掛載後至少三處會非同步寫入。
每寫一次 → effect 重跑 → 連線關掉重建,頁面剛載入那幾百毫秒內連續數次。

**連線不該隨 React 的 render 生命週期起落。** 改為單一實例,換房只換訂閱的 channel。

這件事直接關係到「聊天室斷掉」:`/api/v1/chat/carbon` **早就是雙軌**
(推播 + HTTP 回帶),斷線保底一直都寫好了,只是推播那一軌沒在運作。
實測已回到 `101 Switching Protocols`。

### 8. 使用者訊息先入庫,再呼叫 LLM

`recordUserMessage` 原本排在 LLM 呼叫**之後**。逾時或撞額度,那則訊息就永遠不進 DB ——
畫面上還在(本機 echo),重載就沒了。而匯入正是最會燒額度的操作
(11 章 + 最多 11 次 gap-fill + 5 次結構圖,額度 12 次/分鐘)。

**使用者說過的話不該因為系統回不出來就消失**:那是他的輸入,不是系統的產出。

### 9. 不靠拉長連線解長請求

`proxy_read_timeout 300s` **被否決**(全站共用、把慢速連線攻擊的成本降低五倍,
而且只是把 60 秒的轉圈變成 300 秒)。誤提交進功能分支的那份已退回,
`chore/gateway_proxy_timeout` 標為 wontfix。

改為縮小工作本身:章切成最多 4 節的工作單元,ch1(7 節)、ch3(6)、ch9(5)各切兩份。
切的單位是**節不是頁** —— 以頁切會把跨頁表格切成兩半(表4.8 跨 8 頁),
那是拿無聲的資料損失換請求跑得完。

### 10. 封存清單自己捲動

封存區塊是 `flex-1` 捲動區的兄弟節點,而側邊欄根容器沒有高度上限。
16 筆展開時整個側邊欄被撐過視窗高度,「設定」被推出畫面。
