## 症狀 1:末端節點只有代碼,讀者不知道那是什麼,也看不出流向

第一張圖(全公司 → 前九大項目)的末端節點寫的是:

```
2.1 3470.34
1.1 2592.3
3.2 927.46
```

`2.1`、`1.1`、`3.2` 是 ISO 14064-1 的子代碼。**這份圖是給查證人員與主管看的,
而「2.1」對他們不是資訊** —— 要對照原文表格才知道 2.1 是外購電力。
更麻煩的是末端節點沒有下一層,視覺上像斷掉:看不出這條流「流向哪裡」。

第二張圖(廠址 → 範疇 → 子代碼)同樣問題,而且更密:
`#3 2.1 3325.02`、`#3 3.2 927.46`…… 一整排代碼。

### 建議改法

1. **末端標籤補上名稱**:`2.1 外購電力 3470.34`。子代碼 → 名稱的對照表已經在
   `src/constants/carbon_source_tables.ts` / ISO 對照那一組常數裡,不必新查資料。
   長度風險:mermaid 的標籤畫在節點右側,名稱會讓標籤更長 ——
   需搭配 `CARBON_SANKEY_LABEL_MAX_CHARS` 之類的截斷(截斷要留原文可查的代碼在前)。
2. **末端加一層「範疇」收束**,讓流向有終點:
   `全公司 → 前九大項目 → 範疇一/二/三`。
   代價是又回到 3 層(先前為了可讀性才降到 2 層),需實測比較。
3. 或**在圖下方保留一份對照清單**(代碼 → 名稱 → 數值),圖只負責比重。
   這是最保守的:不動佈局,把「那是什麼」交給文字。

> 判斷:1 + 3 一起做,2 先不做。名稱是缺的資訊,補上;層數是佈局取捨,不要再加回去。

## 症狀 2:第二張圖線太細,看不出比重

第二張圖有 3 個廠址 × 3 個範疇 × N 個子代碼 = 21 條末端流,
其中 `#3 屏東分公司 8121.92` 佔全體 97%,其餘廠址的線幾乎是髮絲。
畫面上「看得出誰大」是唯一目的,而現在得靠讀數字。

### 建議改法

- **只畫主要廠址,其餘合併**:與第一張圖同一手法(前 N + 其他)。
  廠址數在真實報告裡通常 2~5 個,可設 `TOP_SITE_COUNT = 2` + 其他。
- **或拆成每廠址一張小圖**(小倍數):比重在單張圖內部就看得出來,
  跨廠址的比較交給第一張圖。
- **最小改動**:把佔比低於門檻(如 1%)的流合併為「其他」節點並在圖下註明,
  現有 `CARBON_SANKEY_MIN_SHARE` 相關常數可沿用。

> 判斷:先做門檻合併(最小改動、可測),小倍數留待有實際多廠址樣本再說。
