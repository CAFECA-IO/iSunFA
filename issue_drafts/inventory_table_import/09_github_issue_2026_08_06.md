## 一、長呼叫必然超過閘道的忍耐度

### 現象

匯入完成但一張結構圖都沒有;或匯入本身回 504 而伺服端其實跑完了。

### 成因

閘道 `dockerfiles/gateway/nginx.conf` 未設 `proxy_read_timeout`,套用 nginx 預設 **60 秒**。而:

| 常數 | 值 | 能不能調小 |
| :-- | --: | :-- |
| `LLM_DIAGRAM_TIMEOUT_MS` | 90s | **不能**。45s 版本在 1.1 節(23 個里程碑的沿革時間軸)第一次 `latencyMs 45,003` 逾時、退避重試 `44,992` 才過 —— 8 毫秒之差 |
| `LLM_REPORT_IMPORT_TIMEOUT_MS` | 240s | 切節有限度且已寫成測試:ch4 只有 3 節卻跑 2.5 分鐘,再往下切會把跨頁的表格切成兩半 |

diagram 端點特別貴:它是純端口、**不寫入任何資料**,結果只存在於那個 HTTP 回應裡。
連線被切 = 推理白燒,而前端接著還會退避重試一次,再燒一次。

拉長 `proxy_read_timeout` 的提案已於 2026-08-04 被否決(允許連線長時間空掛是安全隱患,
而且該設定全站共用)。那張票留下的結論是「該調整的是呼叫的形狀:改推播、切小、非同步」。

### 那張票漏掉的第四種形狀

**那 60 秒是「閒置」逾時。** nginx 文件:「只計算兩次連續讀取之間的間隔」。
等 LLM 期間一個位元組都沒送,整段都算閒置 —— 所以還有一種作法是**讓連線不閒置**。

`streamingJson`(`src/lib/utils/streaming_response.ts`):
立即送 200 表頭,等 LLM 期間每 20 秒寫一個換行,結束才寫完整信封。

- 連線一直是活的,閘道對「閒置多久算死」的判斷維持原樣 —— **nginx 一行都不動**
- 方向與被否決的提案相反:那個是允許連線長時間空掛,這個是讓它不要空著
- 客戶端零改動 —— `JSON.parse` 依規範忽略前導空白,而 `Response.json()` 走的就是它

### 代價(採用前必讀)

串流一開始 HTTP 狀態就鎖成 200,失敗只能寫在信封裡。因此:

1. 授權、限流、Schema 驗證、檔案型別/大小、magic bytes、來源裁決
   **一律留在串流之前**用 `jsonFail` 回 —— 那些失敗要落在正確的狀態碼上,
   而它們全都在 LLM 之前,天然做得到。
2. **端點改用它時必須同時把前端改成判 `success`。** `unwrapEnvelope`
   把信封裡的失敗轉回拋出,呼叫端既有的 catch 路徑因此語意不變,
   而 `isQuotaApiError` 等型別守衛讀的正是 `data.errorCode`,分類照樣成立。
3. **漏改的表現是「失敗被當成成功」** —— 沒結果、沒錯誤、console 一片乾淨,
   比原本的 504 更難查。反向情形有測試(`unwrap_envelope.test.ts`)。

### 範圍

已套用:`/chat/carbon/diagram`、`/chat/carbon/import`(INDEX / DRAFT / VERBATIM)。
前端四個匯入呼叫點一起改;其中單發全綱那支原本 `?? { segments: [] … }`
會把失敗變成「空匯入」,而空匯入走的是「檔案裡找不到內容」那條文案。

**未套用**:`/chat/carbon` 主對話 —— 它已用「邊做邊推」讓結果不依賴連線存活,
504 不會遺失結果,只是使用者會多看到一次錯誤提示。另開票。

## 二、提示只有一格,所以會被別的房間吃掉

### 現象

A 房匯入跑著、切到 B 房、再切回 A 房 → 進度提示不見了,而匯入其實還在跑。
使用者只能重新上傳,而兩份匯入同時跑會各自燒 11 章額度、互相搶限流,
先完成的還會被後完成的覆蓋。

### 兩個根因(止盲已在前一個分支,根因在此)

**一、`draftNotice` 只有一格。** 原本是 `{ sessionId, notice }` ——
它記得「這則屬於哪一房」所以不會顯示錯的進度,但同時只存得下一則。
B 房任何會設提示的動作(綁帳本、生成草稿、存檔、匯入帳本紀錄)都會蓋掉 A 房那則。

→ 改 `Record<sessionId, IDraftNotice>`;清除時移除鍵而非留 null
(沿用 `pendingImportBySession` 的慣例:留著空鍵會讓「有沒有提示」多一種等價表示)。

**二、長流程仍在問「現在人在哪一房」。** `runImportChapters` /
`runGapFillSections` / 結構圖階段內部都直接呼叫不帶 sessionId 的 `setDraftNotice`,
而這三段都跑好幾分鐘。

→ 四處(含 `retryFailedImportChapters`)改為由呼叫端注入已釘住 sessionId 的 `notify`。
函式只管回報,不管人在哪。`importReportFile` 其實早就備好了一個,只是沒傳進去。

### 順帶兩個一樣會清錯房間的

- **自動消失的計時器也只有一格。** A 房排了「三秒後清掉」,期間 B 房設了提示,
  計時器一到就清掉「當前那一房」—— 清錯房間,而且不會有任何跡象,
  使用者只覺得提示閃一下就沒了。改為逐會話一個。
- **待決的自動消失屬於排它的那一則提示。** 換了一則之後它就不再有效,
  否則新提示會被上一則的計時器提早清掉。原本靠呼叫端自己記得,只有一處寫了 ——
  移進 `setDraftNotice` 就不會有人漏。同時把散在七處的計時器樣板收成
  `dismissDraftNoticeAfter`。

### 測試

`reduceDraftNotice` 抽成純函式,6 條,核心是反向測試「**寫 B 房不得動到 A 房**」。
症狀是「畫面看起來沒事」,人工測最容易漏,所以更需要釘住。

hook 本體沒有測試環境(`@testing-library/react` 未安裝,見 `../enterprise/40_test_coverage.md`),
把不變式放進純函式是現在唯一測得到它的方式。

## 三、帳本的日期一直都在,是介面漏了欄位

### 現象

使用者要求桑基圖分層加月份。

### 查證結果

`EsgRecord.tradingDate` 是真實交易日期,但:

- `IActivityRecord` 沒有時間欄位 → `carbon_esg_link.service.ts` 映射那一步就丟了
- `IComputedLedgerEntry` 也沒有 → 進圖之前補不回來

後果是所有圖表只畫得出年度合計,而 `TREND_LINE` 模板還因為
「單期 ledger 無時間序列」被註記成「永不可滿足的模板即地雷」而刻意不上架。
**那個前提從一開始就不成立** —— 缺的是三個欄位,不是資料。

### 處置

新層:**月別 → 憑證 → 排放源 → 範疇**。

- 存原始時間戳(Unix 秒)而非 `YYYY-MM`:月別只是其中一種聚合,
  先把粒度砍到月,以後要季/週就得回頭改資料模型
- 用 number 而非 `Date`:整個 state 要 JSON 序列化後 E2EE 入庫
- 兩個 push 點都帶。漏一個的表現是「有些筆沒有月份」——
  看起來像資料缺日期,不像程式漏了一行

三個刻意的行為:

1. **一筆日期都沒有時不加這一層**(否則只是一個「未標註期間」的漏斗節點,純噪音)
2. **有無日期混在一起時,沒日期的走「未標註期間」**。併進某個月份是編造;
   整批丟掉會讓總流入不等於總流出,而這張圖的意義正是守恆的視覺化
3. **月別數超過 24(兩個年度)即整層略過並明說**。跨數年時該畫的是趨勢圖;
   少一層而不講,讀者會以為這份帳本根本沒有日期

### 月份取 UTC 曆日 —— 這是選擇,不是意外

schema 上沒有逐筆時區。寫入端絕大多數是憑證上抓到的日期字串(UTC 午夜),
那種值在 UTC 下讀出來就是憑證上的月份;但退路 `new Date(Date.now())` 會帶真實時刻,
於是月初/月末各有一段八小時的窗口 UTC 與台北會落在不同月份。

取 UTC 的理由是**決定性**:改用瀏覽器時區的話,同一份 ledger 在台北與倫敦的
查核者手上會產出不同的月別數字。這是要拿去對帳的文件,同資料同結果比
「對某一個人更直覺」重要。界線寫成測試釘住。

誤把毫秒當秒一律判為「未標註期間」而不是印出五萬年後的月份 ——
本專案兩種慣例並存(repo 轉秒、`Date.now()` 是毫秒),而那種錯不噴任何錯誤。

### 範圍限制

3.6 的自動附圖以 `entries.some(isImportedEntry)` 二選一,
匯入過報告的會話畫的是**匯入桑基圖,它仍然沒有月份**(表3.8 是年度表,
月份不存在於任何被匯入的資料裡;硬加只能按月分攤,那是編造)。
月別層出現在帳本憑證那條路。兩張圖並存的可能性模板註解裡保留了,本次沒動。

## 追加(08-06 下半場,同一支分支)

UAT 又跑了幾輪,以下都在同一支分支上處理完 —— 症狀不同,形狀是同一個:
**畫面看起來沒事,但東西不在。**

### 5. 匯入通知端點從上線起一次都沒成功過

`recipientPublicKey ?? sessionUser.address`:address 是 `0x…` 十六進位,
不是 base58 xpub,ECIES 在第一個 `0` 就 `invalid base58 value` 炸開,每一次都 500。
而那個補位的理由是我自己寫的註解「與 report PUT 同一慣例」—— 那句話不成立,
report PUT 的 address 補位只發生在**明文模式**(那時 address 是擁有者標記,不是金鑰)。
**我把一個慣例跨過了它不成立的邊界,並且把那個錯誤寫進註解替它背書。**
這解釋了使用者連兩輪的「匯入後聊天室依舊沒有記錄」。

### 6. 兩個廠址一直共用同一棵子樹

表3.8 的「總公司」與「屏東分公司」編號都是 `(1)`,而我拿那個編號當節點前綴,
於是第 3 層以下兩個廠址完全併在一起(`(1) 範疇一` = 17.8494 + 2814.0773)。

**所有守恆測試都通過** —— 因為合併不改變總量。我用一組通不過就會壞的測試,
「證明」了一件它測不到的事;找出來是靠一個臨時的 PROBE 測試,不是靠推理。
現在補一條:某廠址底下的每一條邊,廠址標籤必須一致。

### 7. 超長標籤一票否決整張圖

一個 43 字元的合法里程碑標籤,讓另外 30 個有效節點的整張圖被拒。
接地檢查本來就該在長度檢查之前;時間軸與清單類略過該節點並說出略過幾個,
樹狀類仍整張拒(節點少於三個的樹畫出來會誤導),超長比例過半才整張否決。

### 8. 解析完的報告「不套用就消失」

十幾次 LLM、好幾分鐘的解析結果原本只活在 React state,
而介面只有套用與捨棄兩條路 —— 「我想先看看報告再決定」沒有位置。
新增 `CarbonPendingImport`(E2EE,1:1 chatroom)、對話裡留一則
「報告解析完成:檔名」的入庫訊息、預覽卡多一條「稍後再說」。
連 cid / pageIndex / activities 一起存,否則重載後看得到卻補不齊、
或套用出「有段落、沒有活動數據」的半套結果。

### 9. 匯入改為先上傳取 cid

原本十幾次 `/import` 每次都重送整份 PDF(2 MB × 14 ≈ 28 MB),
伺服端也重跑十幾次文字層抽取。改走附件那條既有的安全管線拿 cid。
附帶效果:**匯入檔第一次真的被掃毒了**(原本只驗 magic bytes)。

### 10. 月別分層其實只在重載前有效

`CarbonActivityRecordShape` 與 `ComputedLedgerSchema` 都沒宣告 `tradingTimestamp`,
而 Zod 預設 **strip** 未宣告的鍵 —— 解密後過驗證就把時間戳洗掉了。
第 3 節加的月別層在重載之後是死的,而畫面上完全看不出來:
桑基圖只是安靜地退回「未標註期間」一個節點。

**這一條與本文件開頭那顆 NUL 位元組是同一類錯誤**:自己寫的東西自己踩。
(順帶一提,原本連這份文件都被 git 當成 binary —— 講 NUL 的那一格裡有一顆真的 NUL。)
