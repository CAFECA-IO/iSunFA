## 一、先回答問題:桑基圖畫在 3.6,不是 3.4

|            | 我們的 3.4 各類排放量計算細節與推理                | 我們的 3.6 溫室氣體排放總量匯總表                    |
| :--------- | :------------------------------------------------- | :--------------------------------------------------- |
| 對應原文   | 表3.1 鑑別表、表3.2 係數管理表、表3.4 活動數據種類 | 表3.5 七大氣體、表3.6/3.7 各類別、表3.8 各公司各類別 |
| 資料形狀   | 逐排放源的屬性清單(來源、係數、依據)               | 帶總計的多軸交叉表                                   |
| 適合的視覺 | 明細表(既有 `SOURCE_TABLE`)                        | **桑基**(流量守恆)                                   |

三個理由:

1. **桑基需要至少兩跳流量,3.4 沒有。** 表3.1/3.2 是「排放源 × 屬性」的清單,不是流量;硬畫會變成一排單跳的平行線,資訊量低於表格本身。
2. **3.6 有可勾稽的三軸總計。** 表3.8 給出 廠址 → 類別 → 子類別(1.1~5.4) 的完整分解,且每軸都有小計與總計:Σ 廠址(201.465 + 9.1982 + 8121.918) = 8332.5812,對上表3.6 全公司 8332.581(差 0.0002,發布數字四捨五入)。「總流入 = 總流出」正是桑基圖的原生語意,也是 #22 質量守恆的同一哲學。
3. **現有程式碼已經站在 3.6。** `CARBON_AUTO_SANKEY_PARAGRAPH_ID = "ch3-6"` 早已把桑基圖自動掛在 3.6;缺的不是落點,是**資料**——桑基取值於 `computedLedger`,而匯入的報告 ledger 是空的。

表3.5(七大溫室氣體 CO2/CH4/N2O/HFCs/PFCs/SF6/NF3)是**單層組成**,適合圓餅或長條(既有 `SCOPE_PIE` / `SCOPE_BAR`),不適合桑基;它掛 3.4 或 3.6 皆可,建議 3.6(與總量同一節對照)。

## 二、與現有護欄的正面衝突(必須先解決)

**現況**:3.6 是「數據段落」,而數據段落有兩道刻意設計的封鎖:

- `stripLlmTables()` 丟棄 LLM 草稿夾帶的**任何** markdown 表格
- 匯入提示詞明寫「數據段落不得自行產生統計表格或加總數字,僅撰寫方法說明文字」

也就是說,**現行系統會主動刪掉使用者要求匯入的那些表格**。這不是 bug,是 zero fabrication 的執行面:它假設「表格 = LLM 產生 = 不可信」。

**破解的關鍵是區分「照抄」與「產生」**:

|                | 系統表格                    | 原文表格(本次新增)                |
| :------------- | :-------------------------- | :-------------------------------- |
| 數值來源       | `computedLedger` 決定論計算 | 上傳文件的文字層,逐字照抄         |
| provenance     | `COMPUTED`                  | `IMPORTED`                        |
| 可否被重算取代 | 是(錨點替換)                | **否**(原文是事實,不隨重算變動)   |
| 呈現           | 現行錨點區塊                | 獨立錨點 + 「原文照錄」標籤與頁碼 |

兩者**並存但絕不合併**,且在同一節內做**對帳**:原文總量 vs 系統計算總量,差異明白寫出來。這其實是這套系統最有價值的功能——查核者手上要做的第一件事就是 tie-out。

## 三、拆成三張 issue

### Issue A — 第 3 章表格逐字匯入(原文表格通道)

**範圍**:表3.1 排放鑑別表、表3.2 排放係數管理表、表3.3 IPCC GWP 值、表3.4 活動數據種類、表3.5 類別一七大溫室氣體、表3.6 各類別(所在地基準)、表3.7 各類別(市場基準)、表3.8 各公司各類別。

**做法**

1. 匯入提示詞新增表格照抄規則:表格以 markdown 表格輸出,**儲存格內容逐字照抄,嚴禁重排、合併、換算或補值**;跨頁表格合併為一張並保留頁碼。文字層抽取已用 `cellSeparator = "\t"` 保住儲存格結構,這是照抄可行的前提。
2. `IImportedTable { tableNo, caption, sourcePages, markdown, provenance: IMPORTED }`,隨段落一起進匯入預覽,人工逐張勾選(沿用既有預覽卡)。
3. `stripLlmTables()` 改為**只剝除未標記 provenance 的表格**:原文表格帶錨點 `<!-- carbon-source-table:表3.8:start -->`,不受剝除;系統表格錨點不變。兩種錨點命名空間分離,重算互不干擾。
4. 段落內順序固定:敘述 → 原文表格(標「原文照錄 p.41」)→ 系統表格 → 對帳說明。順序寫死在 builder,不由 LLM 決定。

**驗收**:匯入高興昌那份後,3.4 / 3.6 出現 8 張原文表格,數字與 PDF 逐格一致(抽驗表3.8 三個廠址的總計列),且重算報告不會動到原文表格。

### Issue B — 表3.8 決定性解析進帳本(provenance = IMPORTED)

這是桑基圖能畫出來的唯一路徑。**LLM 只照抄,解析與勾稽全在 TypeScript。**

**必須處理的四件事(都來自實測)**

1. **子代碼才是可映射的層級。** `IComputedLedgerEntry.scopeCategory` 是 `GhgProtocolCategory`(範疇一/二/三 + 15 類),而報告用 `Iso14064Category`(類別一~六)。類別層是 1:多,無法映射;但表3.8 的**子代碼**可以:

   | 表3.8 子代碼                                                                         | GhgProtocolCategory |
   | :----------------------------------------------------------------------------------- | :------------------ |
   | 1.1 固定式燃燒 / 1.2 移動式燃燒 / 1.3 產業過程 / 1.4 人為系統逸散 / 1.5 土地使用變更 | `SCOPE_1_DIRECT`    |
   | 2.1 外購電力 / 2.2 外購能源                                                          | `SCOPE_2_INDIRECT`  |
   | 3.1 上游運輸                                                                         | `SCOPE_3_CAT_4`     |
   | 3.2 下游運輸                                                                         | `SCOPE_3_CAT_9`     |
   | 3.3 員工通勤                                                                         | `SCOPE_3_CAT_7`     |
   | 3.4 客戶與訪客運輸                                                                   | `SCOPE_3_CAT_9`     |
   | 3.5 業務旅運                                                                         | `SCOPE_3_CAT_6`     |
   | 4.1 採購貨物                                                                         | `SCOPE_3_CAT_1`     |
   | 4.2 資本財                                                                           | `SCOPE_3_CAT_2`     |
   | 4.3 固體或液體廢棄物                                                                 | `SCOPE_3_CAT_5`     |
   | 4.4 資產使用                                                                         | `SCOPE_3_CAT_8`     |
   | 4.5 服務使用                                                                         | `SCOPE_3_CAT_1`     |
   | 5.1 產品使用階段                                                                     | `SCOPE_3_CAT_11`    |
   | 5.2 下游承租資產                                                                     | `SCOPE_3_CAT_13`    |
   | 5.3 產品生命終止                                                                     | `SCOPE_3_CAT_12`    |
   | 5.4 投資運作                                                                         | `SCOPE_3_CAT_15`    |

   映射表放 `src/constants/`(唯讀 const,附 ISO 14064-1:2018 條號),**不得由 LLM 判斷歸類**。3.4 → CAT_9 與 4.5 → CAT_1 兩處是近似,需在常數註解標明並於報告對帳處揭露。

2. **`NA` / `NS` / `0.0000` 是三種不同的事實,不可壓成 0。** `NA` = 不適用、`NS` = 不顯著(未量化)、`0.0000` = 已鑑別且為零。壓成 0 會讓「沒盤查」看起來像「盤查後為零」,這是實質的誤導。以 enum `ImportedQuantityStateEnum { REPORTED, NOT_APPLICABLE, NOT_SIGNIFICANT }` 保存,桑基圖只畫 `REPORTED` 且 > 0 者,被排除的項目列在圖下方說明。

3. **單位換算與容差。** 報告是公噸 CO2e,ledger 是 `co2eKg` → ×1000,全程 `Prisma.Decimal`。勾稽三條,任一不過即拒絕寫入 ledger 並顯示告警(比照 #22 的凍結行為):
   - Σ 子代碼 = 各類別小計
   - Σ 類別 = 該廠址總計
   - Σ 廠址 = 表3.6 全公司總計
     實測 Σ 廠址 = 8332.5812 vs 表3.6 = 8332.581,**容差必須容納發布數字的四捨五入**:建議相對容差 1e-6 或絕對 0.001 公噸,並把實際差額寫進對帳說明(不靜默吸收)。

4. **所在地 / 市場基準是新維度。** 表3.6 與表3.7 在這份報告數字相同(無再生能源採購),但一旦不同就會重複計算。ledger 目前沒有這個維度 → 新增 `emissionBasis: LOCATION | MARKET`,匯入預設 `LOCATION` 並在圖表標題標示;兩表數字相異時兩者都存,由 UI 切換。

**驗收**:匯入後 `computedLedger` 有 3 廠址 × 子代碼的項目,provenance 全為 `IMPORTED`,總量勾稽通過,勾稽徽章從「資料不足」變為「已勾稽」;篡改任一格數字會讓勾稽失敗並凍結表格。

### Issue C — 3.6 三層桑基圖

**節點**:`廠址(3) → 類別(6) → 排放形式(≤16 子代碼)`,權重為公噸 CO2e。

**追加需求(2026-07-31,Emily):範疇 / 類別 / 月份 / 細項(同類收據如電費)**

前兩個維度已在上述三層內(類別 = ISO 類別一~六;範疇 = 映射後的 GHG Protocol 範疇,同一份資料的另一種切面)。後兩個維度**這份盤查報告給不出來**:

| 維度           | 盤查報告(匯入)                                                                          | 憑證級資料(EsgRecord)         |
| :------------- | :-------------------------------------------------------------------------------------- | :---------------------------- |
| 範疇 / 類別    | ✅ 表3.6/3.8                                                                            | ✅ 既有映射                   |
| 月份           | ❌ **全部是年度總量**。全文只在方法說明提到「2023 年每月份人工總時數」,無任何月度分解表 | ✅ 憑證有日期                 |
| 細項(如電費單) | ⚠️ 只到子代碼「2.1 外購電力」,無逐張單據                                                | ✅ 單一憑證(#54 證據鏈已做到) |

所以月份與細項只能走**憑證級通道**,不能從匯入的報告變出來——硬要拆月會是憑空捏造(直接違反零捏造)。

**決策建議**:桑基圖的切面由資料的 provenance 決定,並在圖上明示可用維度:

- `IMPORTED`(報告匯入):廠址 → 類別 → 排放形式,標註「年度總量,原文無月度分解」
- `VOUCHER`(憑證級):範疇 → 類別 → 月份 → 細項(單張憑證),即現行 #53/#54 的延伸
- 兩者並存時**分成兩張圖**,不合併——一張是外部已查證的年度事實,一張是我們自建的可下鑽帳本,混在同一張圖裡會讓查核者無法判斷任一條流量的來源。

四層(範疇 → 類別 → 月份 → 細項)節點數會暴增(12 月 × 細項),必須沿用節點上限並提供維度開關;預設兩層,由使用者逐層展開。此部分依賴憑證資料,列為 Issue D,不阻擋 A/B/C。

**已備的東西**:`EMISSION_SANKEY` 模板與 `CARBON_AUTO_SANKEY_PARAGRAPH_ID = "ch3-6"` 已存在;中文節點名的 mermaid sankey ASCII 限制已由 `aliasNonAsciiSankeyNodes` / `restoreSankeyLabels` 解決(渲染前換 ASCII 佔位,渲染後還原)。

**要做的**:

1. 桑基資料來源從「憑證 → 排放源 → Scope」擴充為兩種切面,由 provenance 決定:憑證級資料走原本三層;`IMPORTED` 資料走 廠址 → 類別 → 排放形式。切面以 enum 鎖死,不新增可自由組合的參數。
2. 零與 `NA`/`NS` 的連結一律不畫(mermaid sankey 的零權重連結無意義),圖下方以文字列出被排除者及其狀態。
3. 節點上限沿用 `CARBON_SANKEY_MAX_EVIDENCE_NODES` 的哲學:超過即降為兩層(廠址 → 類別),寧可少一層也不畫成毛線團。
4. 圖標題必須帶基準與單位:「溫室氣體排放流向(所在地基準,公噸 CO2e/年)」。

**驗收**:匯入高興昌那份後 3.6 出現三層桑基,總流入 = 總流出 = 8332.581,屏東分公司佔比明顯(8121.918 / 97.5%),`NA`/`NS` 項目不出現在圖中但列於說明。

## 四、執行順序與風險

```
A(原文表格通道)→ B(解析進帳本)→ C(桑基三層)
```

A 是 B 的前提(沒有照抄的表格就沒有可解析的來源),B 是 C 的前提(桑基取值於 ledger)。A 單獨上線即有價值(原文表格可見),C 之前每一步都可獨立驗收。

| 風險                                      | 處置                                                                                                                                                                                                                          |
| :---------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **本機文字層抽不出來(`charsPerPage: 0`)** | **這是 A 的硬前提**:走視覺模型時表格會被改寫,逐字照抄不可能成立。已定位到 `@napi-rs/canvas` 這個原生綁定(pdfjs 無條件載入,而純文字抽取根本不需要繪圖);`scripts/probe_pdf_text_layer.ts` 一次跑完即可定案。詳見 ADR 014 第四節 |
| 外部數字與自建帳本混流                    | provenance 欄位 + 三層勾稽 + 徽章;報告內任何數字都能回答「這是誰算的」                                                                                                                                                        |
| 子代碼映射的兩處近似(3.4、4.5)            | 常數註解標明 + 對帳處揭露,不隱藏判斷                                                                                                                                                                                          |
| 跨頁表格(表3.8 跨 3 頁)                   | 頁標記已在文字層中,合併時保留起訖頁;合併後仍須通過小計勾稽才寫入                                                                                                                                                              |

## 五、需要新增的測試

- 表3.8 解析:三廠址 × 全子代碼,含 `NA`/`NS`/`0.0000` 三態
- 勾稽三條各自的失敗案例(篡改子代碼、篡改類別小計、篡改全公司總計)

- 桑基:零/NA 連結不畫、超過節點上限降兩層、總流入 = 總流出
