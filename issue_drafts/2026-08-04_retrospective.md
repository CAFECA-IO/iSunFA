## 三、為什麼做這麼久

### 3.1 最大的結構性瓶頸:我驗不了

沙箱**跑不了瀏覽器、跑不了真實 PDF 上傳、連不到 DB**。整條管線的驗收條件都在瀏覽器裡:
上傳 → 11 章 LLM 解析 → 落地 → 畫圖 → 渲染。

代價是**每一輪都要你手動測,而且一輪要數分鐘**。這決定了整天的節奏:
我改完 → 你測 → 回報 → 我改。單日大約只跑了 5 輪。

### 3.2 錯誤是層層堆疊的,只能一層一層剝

這不是「有 20 個並列的 bug」,而是**一條管線上的 20 道關卡,每修好一道才看得到下一道**:

```
表格進不來(被護欄剝掉)
  → 進來了,但逐章合併時被丟掉(型別漏宣告)
    → 沒丟了,但頁碼切片把表格切掉一半
      → 完整了,但表號格式被驗證擋下
        → 過了,但沒進 ledger
          → 進了,但畫不出圖
            → 畫出來了,但 mermaid 語法錯
              → 語法對了,但廠址名帶粗體星號
                → 乾淨了,但單位是公斤不是公噸
                  → 對了,但系統表格說「資料不足」
```

**無法並行,也無法預先看到全貌。** 每一層都要一次實測才會暴露下一層。

### 3.3 我自己造成的往返

有四次是我沒查證就下結論,各花掉一個回合:

| 錯誤 | 實況 |
| :--- | :--- |
| 斷定 `MoneyUtil` 沒有 `add` | 我只讀了 money.ts 前 80 行,`add` 在第 86 行 |
| `MeasurementUnit` 從 `@/constants/esg` import | 它在 `@/constants/enums` |
| `GhgProtocolCategory.SCOPE_1` | 正確是 `SCOPE_1_DIRECT` |
| 說 nginx 改動「只在工作區未合」 | `chore/gateway_proxy_timeout` 早就存在且已推 origin,我等於重做一次 |

前三個 CLAUDE.md 第 3 條「停看聽」寫得很清楚,我沒做到。

## 四、為什麼有那麼多錯誤要修

把 28 個 commit 依失敗模式分類,五類,而且**分布極不平均**:

### A. 護欄互相打架(最多,約 8 次)

兩條各自正確的規則,合起來產生錯誤行為:

- `stripLlmTables`(丟棄 LLM 表格)vs 原文照錄的表格 —— 前者不知道後者存在
- mermaid 的**驗證**(用原始字串)vs **渲染**(用 ASCII 別名字串)—— 驗證先失敗,繞道永遠走不到
- 系統表格排除匯入項目 vs 徽章看未過濾的 entries —— 同一份資料,兩個相反的結論
- 匯入項目排除 vs 範疇小計表 —— 排除收得太寬,連不重複的彙總也砍掉

**共同結構:後加的護欄不知道先前的繞道解法存在。** 每一道護欄單獨看都對。

### B. 對外部輸入做了隱含假設(約 6 次)

- 表3.8 的版面(同一份 PDF、同一組提示詞,模型換一輪就改攤平策略)
- 表號格式(驗證比真實世界嚴)
- markdown 粗體(模型會自己加 `**`)
- mermaid 對重複連結的行為(規格沒明文保證)
- 頁碼上界(用「最後一節起始頁」當終點,漏掉那一節的內容)

**共同結構:把「我看到的那一次」當成規格。**

### C. 型別漏宣告導致靜默丟資料(1 次,但最貴)

`IImportChunkPayload` 漏宣告 `sourceTables`,API 一直有回,逐章合併時**靜默丟棄**。
沒有錯誤、沒有 log、沒有任何症狀,只是表格一張都沒進報告。這種最難發現。

### D. 非同步時序(3 次)

`setState` 尚未生效就讀狀態:落地那一 tick 的 `sessionsData` 是舊值、
`computedLedgerRef` 尚未含匯入項目、diagram 階段拿到空內容。

### E. 失敗沒有痕跡(貫穿全程)

結構圖失敗靜默、匯入 blocked 沒 log、進度看不出還在不在跑。
**這一類不製造 bug,但讓每一個 bug 的定位成本翻倍。**

## 六、下次規劃同類功能的做法

以下每一條都對應今天實際踩到的坑,不是通則。

### 6.1 先打通最窄的一條端到端,再加寬

今天是**分層完工**:先把解析做完、再做 ledger、再做圖。
結果是接縫上的問題全部堆到最後才爆(表格丟失、單位、時序、渲染)。

下次:**一張表、一個段落、一張圖,先讓它從上傳到畫面走完**。
哪怕只支援一種版面、寫死一個章節。走通之後再擴充版面、章節、圖種。
接縫的問題會在第一天就暴露,而不是第五輪實測。

### 6.2 護欄要登記「它會擋掉什麼」

A 類(護欄打架)佔了最多。根因是**每道護欄各自為政,新增時沒人檢查既有的繞道**。

具體做法:在 `documents/` 維護一份「受管內容通道」清單——
`carbon-source-table`、`carbon-data-table`、`carbon-chart`、`carbon-diagram`、
ASCII 別名替換……每一項記錄「誰會剝除它、誰必須放行它」。
新增護欄或新增通道時,先讀這張表。

### 6.3 契約測試放在模組邊界,不是模組內部

07-31 的 issue 03 已經記過這個教訓(「產生器測試全綠,但沒驗產出物能否被渲染端接受」),
**今天同一類問題又發生了兩次**(mermaid 驗證 vs 渲染、徽章 vs 表格)。

教訓寫進 issue 沒有用,要寫成測試。凡是「A 產出、B 消費」的地方,
測試要跨過那條邊界斷言,而不是各自測各自的輸出。

### 6.4 對 LLM 的輸出寫 fixture 迴歸,不要相信提示詞

表3.8 版面變異是最典型的:同一份 PDF、同一組提示詞,**換一輪就換攤平策略**。

做法:每次實測看到的真實輸出**都留成 fixture**,不刪舊的。
今天保留了兩種版面各一份——只留新的等於把第一輪的迴歸風險丟掉,而版面隨時會變回來。

### 6.5 可觀測性當作驗收條件,不是事後補

E 類貫穿全程。凡是**會失敗、會耗時、會被限流**的流程,開工時就要決定:

- 失敗時 log 什麼(足以分辨「沒觸發 / 被擋 / 呼叫失敗」)
- 進行中畫面顯示什麼(**能分辨「還在跑」與「已經死了」**)
- 完成與未完成在資料上如何區分

今天「切房回來看不出還在不在跑」導致重新上傳,就是因為這三件事都沒在開工時定義。

### 6.6 實測回合要批次化

一輪實測要數分鐘,而且只有你能跑。所以**每一輪都要問到最多的問題**。

做法:改動完成後給一份帶編號的驗收清單(今天有做,但太晚才開始),
你一次跑完回報全部結果,而不是發現一個問題就中斷。

### 6.7 我這邊的三條紀律

1. **停看聽要做完整。** 讀函式定義就讀完整份檔案的 API 列表,不要讀 80 行就下結論。
2. **改動前先查分支狀態。** nginx 那次是查 `git log` 一秒就能避免的重工。
3. **tsc 與 jest 都要跑。** Jest 走 babel 不檢型別,測試綠燈不代表型別對。
